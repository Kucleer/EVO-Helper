接 `#297`（展示侧：图不再内联进列表页）。这一条管**写入侧**。

## 先量的（生产库 2026-09-09）

    带图的行  852 条 / payload 114.14 MB   起于 08-26 14:46，平均 60.6 条/天

    nav_readback（导航栏回读对不上）  633 条  91.29 MB

    起点核对不过                      40 条   3.83 MB
    切不回恒星系                      23 条   2.99 MB

⚠️ 超大行只占 **0.5%**，却占 payload 总体积的 **89.8%**。

## ⚠️ 诊断被推翻两处，这两条比结论更值得留

**① 不是「四个写入点一个限流都没有」。** `1532` 那个点本来就有
（`OVERLAY_EVIDENCE_INTERVAL_S = 120.0`）。真正无条件写的只有 `2572`；
`5062` / `5410` 有名额，但**名额挂在实例上、每轮跟着新实例复位** ——
633 条就是这么攒的（一轮 2 张 × 14 天）。
⇒ **「有名额」不等于「有限流」**，跨轮复位的名额约束不了总量。

**② ⚠️⚠️ 限流几乎不省体积，省下来的基本全靠 webp。**
14 天里同类相邻两条落在 120 秒内的只有 **46 对（5.4%）** ——
**慢滴漏（几十分钟一条）掐不到**。120 秒管的是 2026-08-17 那种「两分钟 25 条」的爆发。

试过更大的窗口（300s 掐 131 / 600s 掐 229 / 1800s 掐 419）**没采用**：
那会开始吃掉真正不同时刻的现场，而最值钱的「画面认不出」那一类首当其冲。

⇒ 主 agent 把限流排在第一位是**排错了**。这一条记下来：
**「同一句话重复很多次」不必然意味着「它们挨得很近」。**

## 1. webp q60

判据是**实拍 40 张生产缩略图（480×229）压出来的**，不是拍的：

    PNG 平均 84.5 KB → q90 12.8 / q80 7.4 / **q60 4.9** / q50 4.4 / q40 3.8 KB

q60 往下每档只多省 0.5–1 KB，**收益已平**；肉眼比对同一帧，
q60 面板轮廓、导航条、行星都认得出，**q40 已经开始糊**。

⚠️ 比战报截图那条路的 q90 低，理由是**这张图不需要读字**：
`thumbnail_base64` 答的是「当时屏上**大致**是什么」，读字归 `crop_png_base64`
（那个函数的 docstring 里写着为什么 480 宽答不了后一个问题）。

⚠️ **键名 `thumbnail_png_base64` 故意不改**（现在装的是 webp）。这个名字已经写在
16.4 万行历史数据里，还同时被查询层的「有没有图」判断和显示层摘图认着 ——
改名换不来任何东西，格式那件事由新键 `thumbnail_image_format` 回答。

## 2. 按类限流（管爆发，不管滴漏）

`EVIDENCE_FRAME_INTERVAL_S = 120.0` + 模块级 `_last_evidence_frame_at`，
**四类各一个阀门**：`planet_list_overlay` / `origin_mismatch` /
`system_view_failure` / `nav_readback`。

⚠️ **按类分开不是讲究**：全局一个阀门会让 633 条的 `nav_readback`
把只有 88 条的「画面认不出」挤掉，而后者正是最值钱的那一类
（待办二：图对「判据把活儿挡掉的那一刻」最值钱）。

⚠️⚠️ **只掐整帧缩略图，不掐日志、不掐裁片。** 待办二的硬要求：
「**不能因为存不了图就让日志整条丢掉**」（`pirate_loop.py:1105` 那条
「轻量驱动不具备截图能力，跳过现场保存」是先例）。
被掐掉的那条在 payload 里留 `evidence_frame_throttled`（哪一类、窗口多少），
这样「本该有图但被掐了几次」查得出来。

⚠️ 限流状态是**进程级**的，所以新增 `tests/unit/tools/conftest.py` 在用例之间清 ——
不清的话红不红全看用例顺序（`-k` 单跑就绿）。第一版就撞上了这个。

顺手改掉三处**已经说了假话**的注释（`2572` 的「不限流」、`5410` 的
「不必按时间限流」、`MAX_NAV_READBACK_FRAMES` 的「留 2 够了」）。

## 3. 与 `#297` 的耦合（第二个 commit）

`#297` 的 `/system-log/{id}/image` 与 `payload_image` 都**写死 `image/png`**。
新增 `screenshot_format()` / `screenshot_media_type()`：

- **白名单只认 `png` / `webp`** —— ⚠️ `payload_json` 是**数据**（runner 写的、
  行里存的），把它的字符串直接拼进 `Content-Type` 或 `data:` URI，
  等于让一行日志决定响应头。认不出一律回落，不原样透传。
- **缺键按 png 认** —— ⚠️ 这不是兜底而是**历史事实**：库里 **846 行**装的确实是 PNG，
  那时还没有这个键。改成别的默认值就等于把那 846 行读成打不开的图。
  同 `battle_report_screenshots.image_format` 单独设一列那条理由：
  「接口靠它填 `Content-Type`，猜错就是浏览器直接下载而不显示」。

## ⚠️ 变异验证抓到一个真缺口

第一版只有单元用例 + 那条「缺键 = png」的集成用例。把 `media_type`
写回死的 `image/png` 时 **31 条全过、没红** —— 因为集成种子里**只有缺键那一种行**，
「写死 png」和「按键取值」分辨不出来。

补了带 webp 行的集成用例（自带种子，**不并进那批 4 条种子**，
免得弄红「共 4 条」那些断言）之后，重跑该变异**当场红**。

⇒ 记下来：**用例覆盖了默认分支，不等于覆盖了那个判据。**

- Configuration: 无新增配置项。限流窗口与 webp 质量都是**标定常量**
  （判据见上），不是运维旋钮。
- Database: **无迁移。**
- Verification: `ruff check` / `ruff format --check`（483 文件）通过；`mypy src` 0 错；
  **裸 `pytest` 4409 passed / 256 skipped**。
  变异 **9 条**：全局一个阀门 / 被限流不留痕 / 限流连日志一起掐 /
  缩略图和裁片一起限流 / 退回存 PNG / 截不到图也声明编码 / 键名跟着编码改名 /
  接口写死 `image/png` / 白名单拆掉 —— 各点名了具体用例。
  ⚠️ 两条支线的子 agent 一度共用同一个 worktree（主 agent 操作失误），
  它们各自的自测都跑在被对方污染的树上；**上面这一轮是在清干净的树上单独跑的**。
- Safety: 只掐整帧缩略图 —— 文字照写、裁片照写；键名未改，
  查询层与显示层的「有没有图」判断一个字没动；846 行老 PNG 有用例钉着仍能回放。
- Rollback: `EVIDENCE_THUMBNAIL_FORMAT` 改回 `"png"` 即退回旧编码；
  `EVIDENCE_FRAME_INTERVAL_S` 调成 0 即退回不限流。两者互不依赖。

## ⚠️ 顺带发现一件要拍板的（没改）

`scan_coordinates.record_unrecognised_screen` 被限流时是 **`return False`
把整条日志一起丢掉**的，调用点也不看返回值 —— 违反待办二那句
「不能因为存不了图就让日志整条丢掉」。生产库那 156 条只是**漏过闸门的那些**，
一次长时间认不出的空转在库里每 120 秒只留一条。

所以这是取舍不是 bug，留给用户。
