两个 runner 侧的毛病，都是 2026-08-13 通宵实机跑出来的：海盗把配额烧在重复侦察上
（111 发侦察 / 12 发攻击），bot 派了 17 发 BBB 却一份战报都没收到。

## 一、海盗当日去重：判据早就有，缺的只是接线

实机账（UTC 15:00–19:00）：**侦察 111 发打在 54 个坐标上**（2:137:1~4 各 5 发），
攻击只有 12 发。`domain.pirate_round.phase_for` 的七态与
`storage.repository.pirate_progress` 的按目标聚合 2026-08-11 就写好了，而且窗口口径
本来就是「游戏内那一天（UTC+0）」——但那个方法的注释写着「供控制台显示」，
`tools.pirate_loop._find_pirates` / `_decide_and_attack` **一次都没问过它**。

用户口径（2026-08-13）：海盗刷新是当日内（游戏内 UTC+0）。落成一张态 → 动作表
（新增 `domain.pirate_round.action_for` / `PirateAction`，纯函数）：

| 态 | 动作 |
|---|---|
| 待侦察 | 侦察 |
| 待侦察报告 | 等 |
| 待触发攻击 | **直接攻击，不重新侦察** |
| 已触发攻击 · 待战报 | 等 |
| 攻击完成 / 不触发攻击 | 当天不再碰 |
| 侦察没看清 | 当天补一次为限（`MAX_SCOUTS_PER_DAY = 2`） |

「补过一次」怎么算：`PirateProgress` 新增 `scout_count`（窗口内 `accepted` 的
`SCOUT` 派遣条数）。只有 `scouted` 那个布尔时，「补过一次」和「补过四次」在数据上
长得一模一样，`SCOUT_UNREADABLE` 就是一条无限重侦的路——而实机上「收割者」那一格
一份报告都没读出来过，这一档是常态不是边角。被游戏拒掉的那一发不占额度
（口径与攻击那一侧同源）。

日界一律 `domain.scheduler.quota_day_start_utc`，链路里没有任何 `replace(hour=0)`。

⚠️ **`pirate_progress` 另加了一个 `scout_not_before`，只有活链路传。** 原来的
「侦察报告不按窗口筛、按目标取最近一份」在**显示**上是对的（要解释窗口里那一发），
但活链路是拿它去决定打不打的：海盗每天刷新，昨天那份报告说的是昨天那批舰队。
2:137:1~4 天天侦察，库里永远躺着昨天那份；今天的侦察发刚出去、报告还没回的那十几
分钟，不设下界这四个坐标全会判成「待触发攻击」，照着过期情报把舰队扔出去。
控制台那一侧一个字没改。

## 二、bot 的 17 发 0 战报：信箱根本没被拖回顶部

根因是一段算术，不是主题串味：

- 一次慢拖走 `PANEL_DRAG_FROM_Y - PANEL_DRAG_TO_Y` = 400px，行距 86px ≈ **4.6 行**；
  原先 `MAIL_SCROLL_TO_TOP_DRAGS` 写死 3，回顶只有约 **14 行**。
- 一趟开工对账要往下翻 `RECONCILE_MAX_PAGES` = 8 屏 ≈ **32 行**。
- 列表**会记住上次滚到哪**（`_enter_mailbox` 的注释早就写着）。

每趟净往下沉约 18 行，信箱 600 封（用户实测），永远沉不到底。

证据：现场图 `var/logs/dump-mail-detail-unrendered-053043.png`，本地 05:30 = **21:30
UTC**，列表最上面几行是 16:42–17:02 的侦察报告，**比墙钟旧四个半钟头**；同一张图上
二级角标写着「战斗 10」未读，正好等于那时已经落地的 10 发攻击（19:51、19:52、19:54、
20:12、20:14、20:53、20:54、21:00、21:02、21:10）。战报就躺在列表顶上，扫描窗口停在
四个半小时之前，七趟信箱一次都没够到过。日志侧对得上：窗口内 7 次开工对账
**每一趟**都以「这一趟已经开了 8 封，到上限」收尾、每一趟都报「今天已有 0 份」，
`战报入库` 出现 0 次；239 条被跳过的行主题里 186 条「侦察报告」、43 条「海盗攻击
报告」、**非海盗的「攻击报告」一条都没有**。

改法：`_scroll_mail_list_to_top()` 拖到**拖不动为止**（判据「还是那几封」，与
`_scan_mail_rows` 判「翻到底了」、`domain.planet_switch.list_exhausted` 同一条），
`MAIL_SCROLL_TO_TOP_MAX_DRAGS = 40` 只是兜底上限、走满要在日志里说出来。
一屏读不出来（空清单）**不算**到顶。

顺手补掉一个日志盲区：开封的那些行原先一个字都不打印，只有被跳过的行有日志——
正好是不需要的那一半，复盘时「那 59 封开的到底是什么」在证据上是个黑洞。

- Configuration: 无新增环境变量；用户的控制台配置一个字未改。
- Database: 无迁移、无新表、无新列。`PirateProgress.scout_count` 与
  `pirate_progress(scout_not_before=)` 都是从已有四张表现算的。
- Verification: `pytest tests` 1834 passed / 80 skipped、`ruff check src tests`、
  `ruff format --check src tests`、`mypy src` 全绿。**25 条变异逐条确认变红后还原**
  （封顶去掉 / 封顶改 3 / 七个态各自改错 / 侦察发数退回布尔 / 算进被拒的派遣 /
  攻击发数进侦察数 / 报告下界失效 · 写反 · 连控制台一起加 / 不带时区的下界不拒收 /
  DONE 不拦 · WAIT 不拦 · 直接攻击那档去掉 / 日界挪一天 / 读完信箱不重取 /
  回到写死 3 次拖动 / 空清单当成到顶 / 拖满上限不吭声）。
- Safety: 去重只会让链路**少派**，不会多派；`_decide_and_attack` 的 `WAIT` 一档
  尤其守着「战报还没回来的那一发也占着这个坐标」。回顶只往上拖，不点任何按钮。
- Rollback: `action_for` 一律返回 `SCOUT` 即回到事故前的行为；
  `_scroll_mail_list_to_top` 换回 `for _ in range(3)` 即回到写死三次那版。
