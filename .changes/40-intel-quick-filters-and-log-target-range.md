页面上的三件事（用户口径 2026-08-11）：情报中心加预设 / 结果 / 战果三个快速过滤、
bot 与海盗用不同配色；攻击日志的目标坐标筛选支持范围；情报中心显示深空吞噬者、
噬能截击者、钛能守卫者、收割者四个舰种的数量。

## 甲、四个触发舰种「没显示」的正因：海盗根本不在这张表里

`LIST_SHIP_COLUMNS` 里本来就是那四个舰种，列也一直在渲染——每一格显示的是
`counts[name] ?? 0`，而 `counts` 来自战报的逐舰种行。于是：

- **海盗一行都没有。** 情报中心的候选集是 `bot_targets WHERE is_bot`，而那张表由
  坐标扫描写；海盗是在星系视图上认出来的，一行都不会写进去。四个舰种的数量在
  `scout_reports` + `scout_trigger_ships` 里躺着，而这一页压根不去看那两张表。
- **bot 那边显示的是假的 0。** 探路战报只读详情页、不写逐舰种行，于是四列全是
  `?? 0`——「对方没有这种船」和「这份战报没读逐舰种」在页面上长得一模一样。

所以 `_rows_in_span` 的候选集改成三者的并集：bot 目标、有过海盗派遣的坐标、
有过侦察报告的坐标。四列的取数按行分流：海盗看最近一份侦察报告，bot 看战报的
逐舰种行。

**`NULL` 不是 0，一路保到像素。** `scout_trigger_ships.count` 的 `NULL` 是「这一格
没读出来」，与 0 相反（`storage.models.ScoutTriggerShipRow` 写着完整的来龙去脉：
数量为 0 的格子是个孤零零的 `0`，实测最容易读空，而整套 ATTACK/SKIP/UNREADABLE
判定就建立在这个区分上）。仓储层原样读回 `int | None`，接口层
`ScoutShipOut.count` 是 `int | null`，页面把 `0` 显示成 `0`、把 `null` 显示成 `—`。
中间三层一个 `or 0` 都没有。同一条改动顺手治了 bot 那边的假 0：一份逐舰种行都
没有的战报，四列显示 `—` 而不是 `0`。

`display.LIST_SHIP_COLUMNS` 改成直接引用 `game.pirate_ui.PIRATE_TRIGGER_SHIPS`，
不再抄一份字面量——这四列存在的理由就是「侦察判定看的是这四个」。

## 乙、三个快速过滤的语义：按**最近一次派遣**判，而且写在页面上

预设 / 结果 / 战果全都挂在**派遣**上（`attack_intents` / `attack_dispatches` /
`battle_reports`），而这张表一行是一个**目标星球**——同一个目标可能被打过很多次。
取「最近一次派遣」而不是「打过就算」：

- 「打过就算」会让战果筛选自相矛盾——一个赢过也输过的目标同时落进「胜」和
  「负」，两个筛选谁都答不上「它现在什么情况」。
- 预设那一档更明显：探路是每个 bot 都走过的第一步，「打过就算」等于全选，
  而用户点它是想找「还停在探路阶段的」。
- 这一页存在的理由是决定**下一发打谁**，而那看的是它现在的样子。

口径写在筛选栏右边（「按最近一次派遣筛，不是『历史上打过就算』」），
`test_the_page_says_the_filters_read_the_latest_attempt` 钉着这句话。

档位（库与接口里是英文常量，界面只显示中文）：

- 结果 `DISPATCH_*`：已派出 / 未派出（本地闸门拦下）/ 被拒（游戏没接受）/
  从未派遣。**拦下与被拒分成两档**——合成一档的话，「为什么这个目标没打」在页面上
  就没有答案了。
- 战果 `RESULT_*`：胜 / 负 / 平 / 待战报 / 不适用。「待战报」只给**真的会有战报的
  那一发**：派出、被接受、而且是攻击发。侦察发不产生战报，算成「待战报」会让页面上
  永远挂着一批等不到的行（PR #95 是在认领那一侧踩的同一个坑）。认不出来的
  `outcome` 原样显示，不拿「不是胜就是负」兜底。
- 预设下拉框的选项取自 `attack_intents` 里真的出现过的名字（`/api/intel/presets`），
  不写死一张表：预设是用户在游戏里配的，写死就意味着新加一个之后这一页安静地
  筛不到它。

空串一律等同于「不筛」（下拉框里「不限」那一项的 value 就是空串），
认不出来的档位当场 422 并把打错的那个词回显——安静地筛出 0 条是最坏的一种。

## 丙、bot 与海盗的配色

`.chip.kind-bot`（青）/ `.chip.kind-pirate`（紫，新增 `--pirate`），外加整行第一格
一条同色左边框。**刻意避开 ok/warn/danger 三色**：那三个说的是「好 / 要留意 /
出事了」，而 bot 和海盗之间没有好坏之分，借用状态色会让人以为海盗行出了问题。
按仓里那条规矩，色永远配一个字形和一个词（chip 里写着「bot」「海盗」），
灰度下与色盲用户照样读得懂；`test_bot_and_pirate_do_not_share_a_colour_or_a_glyph`
钉着这一点。

## 丁、取数从 N+1 改成成批，顺带把排序修对

原先每个目标单独查一次最新战报、再查一次逐舰种——全宇宙 4000 多个 bot 就是
8000 多次往返。现在一次检索是五条成批查询，每条都用 `row_number()` 在 SQL 里挑出
「每个目标最新那一份」，行数仍由坐标区间兜住。

筛选（条件树 + 三个快速过滤）仍在内存里做，这与攻击日志那条「必须下推 SQL」的
教训**不矛盾**：那边是先按 limit 砍掉历史再筛，查旧账必得空页；这边候选集是区间内
的全部目标、分页在筛选**之后**才切，一行都没被提前砍掉。`search()` 的 docstring 写着
这条区别。

排序 `snapshot_desc` 改看 `intel_at`（战报时间与侦察报告时间取晚的那个），下拉框
文案跟着从「战报时间 ↓」改成「情报时间 ↓」：海盗一份战报都没有，只按战报时间排
会把「刚侦察完的海盗」整批沉到几百行开外，而那恰恰是最该顶在前面的一批。

## 戊、攻击日志：目标坐标范围，下推 SQL

`/logs` 新增 `target_start` / `target_end`，两端都可以只写到星系
（`2:130` – `2:140` = 这十一个星系的所有位号，起点补 `:1`、终点补 `:999`，
复用 `domain.intel_query.parse_coordinate_span`）；只填一端时另一端跟着它，
也就是「只看这一个星系」。页面把补位之后的区间原样写出来
（`只看 2:130:1 – 2:140:999（两端都含）`）——不写的话，「为什么 2:130:14 也在里面」
用户只能从结果里反推。

三处必须钉死的地方：

1. **比的是打包坐标，不是逐分量。** `2:130:15` – `2:140:3` 这种区间里，起点位号比
   终点位号大是常态；逐分量比较会拿 `position BETWEEN 15 AND 3` 去卡，整段中间星系
   一条都留不下。情报中心的 `_within` 是同一条判据，用例也照着这个形状写
   （用 `2:130` – `2:140` 那种简写试不出来：简写把位号补成 1..999，两种实现看起来
   一模一样）。
2. **筛选下推到 SQL。** 这一页只取最近 `ATTACK_LOG_LIMIT` 条，在内存里筛坐标等于
   「先砍掉历史再问历史」——查一个旧坐标会得到空页，而空页读起来和「那个坐标一发
   没打」一模一样（PR #77 已经在日期上踩过）。**事件类型那一档原先正是在内存里
   筛的**，这次一并搬下去。
3. **空串是「不筛」，不是错误。** 两个坐标框走表单提交，必然带上
   `target_start=&target_end=`（PR #74 的教训）。新增 `BlankableStr`，与
   `BlankableInt` / `BlankableDate` 同一条路。

坐标写错时**不返回 422**：那是一张 HTML 页，一页 JSON 报错读起来就是「控制台坏了」。
改为照常渲染，并在顶上挂一条红字说明「这一页没有按坐标筛」——默默不筛才是最坏的
一种，用户会以为下面那些行就是筛出来的结果。两张筛选表单各自把对方的值带成
hidden 字段，切换事件类型的链接也把日期与坐标一起带上，所以每种视图都有自己可
分享的链接。
