## 一、bot 攻击侦查之后没有触发正式攻击 —— 链路没坏，是预设不存在

对着 `var/logs/mission-bot.log`（GBK）把 2026-08-11/12 那两夜逐条读完：`NEEDS_ATTACK`
出现 41 次、覆盖 37 个目标，分档全都跑到了，`_tier_and_attack` 一次都没有静默跳过。
**该打的都打了**：37 个目标里 34 个守方 < 2K，判 `NEGLIGIBLE`、不派（按用户定的规则本
来就不该打）；2:10:18（2380 → AAA）与 2:16:7（2050 → AAA）真的打出去了，此前两三趟停在
`NEEDS_ATTACK` 的原因是「同时派遣的舰队数量已达上限」，也不是故障。剩下一个是 2:48:12，
它被判成 `8K+ → CCC`，然后倒在这一句上：`预设条上找不到 'CCC'；这一屏读到的是
['AAA', '探路']`。

所以卡点只有一个，而且不在代码里：**游戏的预设条上只有 `AAA` 和 `探路`，`BBB`（5K–8K）
与 `CCC`（8K+）这两个预设根本不存在。** 按用户口径「预设只按标题匹配，不读不校验」和
「不动用户的控制台配置」，这里一个字都没改——要在游戏里把那两个预设建出来，5K 以上的档
才派得出去。

## 二、海盗侦察之后的状态 —— 四态，不是三态

新增 `domain/pirate_round.py`（`PiratePhase` + `phase_of` / `phase_for`，纯函数）与
`SqlAlchemyRepository.pirate_progress()`。**一张新表、一列新字段都没加**：态全部从
`attack_intents` + `attack_dispatches` + `battle_reports` + `scout_reports` 四张既有表
推出来，判定按现行规则现算——库里不存判定，理由见 `domain.records.ScoutReport` 的注释。

用户列了三态（不触发攻击 / 触发攻击 / 攻击完成），这里落成四个终态，多出来的是
`SCOUT_UNREADABLE`。依据是库里的实测数据，不是洁癖：98 份侦察报告里「收割者」那一格
**一份都没读出来**，于是 28 份非攻击判定**全部**是 `UNREADABLE`、`SKIP` 一份都没有。
三态显示会把这 28 个海盗一律标成「不值得打」，而真相是有一格从来没看清过——正是
`ScoutTriggerShip` 反复在防的那种把「没看清」记成「这里是空的」。拿生产库副本跑一遍
UTC 08-11：侦察没看清 9 · 待侦察报告 3 · 已触发攻击待战报 11 · 攻击完成 5，
「不触发攻击」0 个。

顺带把判定规则从 `game.pirate_ui` 挪进 `domain/scout_verdict.py`：storage 不能 import
vision，而活链路当场那份判定住在 vision，两边各写一份就会出现「界面说不值得打、链路
当时判的是没看清」这种分叉。`game.pirate_ui` 原样 re-export，调用方一个都没改。

## 三、坐标 2:48:12 舰队识别错误 —— 小数点在 OCR 那一层掉了

先查库（生产库拷到临时目录，没碰原库）：`battle_reports` 里 2:48:12 那一行
`defender_units = 122000`，而全库其余 60 行最大只有 4353。不是 `k` 后缀没处理：
`parse_fleet_count("1.22K")` 给出 1220（正确）。122000 只能来自 `"122K"` —— 那个几像素
的小圆点在 OCR 时掉了，`1.22K`（1220 艘，2K 以下、**本来就不该打**）于是成了 122000，
分档判成 `8K+` 去挑最重的组合。**分档的三条边界（2K/5K/8K）全落在这两个读数之间，
丢一个点就跨过全部三条。**

修在选票那一层：`vision.fleet_counts.pick_count` 原先只认「前面的字掉了」（短的是长的
后缀），现在同时认「小数点掉了」，方向和后缀那条一样是单向的——带点的候选吸收去点后与它
相同的候选，反过来不成立，依据同为「这个字体只会漏笔画，不会凭空多字」。判据**不放宽成
子序列**：那条会把 `11` 并进 `1.17K`。`M` 后缀仍旧故意不认，理由写进了
`parse_fleet_count` 的注释：识别侧白名单只放行 `0123456789.K`，认了它就等于凭一个从未
见过的后缀把舰队送出去，而「没读到」在调用方那边的处置是不打，那是安全的一侧。

- Configuration: 无新增环境变量；用户的预设配置一个字未改。
- Database: 无迁移，无新表；`pirate_progress()` 只读四张既有表。
- Verification: `pytest tests` 1435 passed / 51 skipped、`ruff check src tests`、
  `ruff format --check src tests`、`mypy src` 全绿。17 条变异逐条确认变红后还原（去掉
  小数点折叠 / 折叠放宽成子序列 / 折叠反向 / 「没看清」当成「不值得打」 / NULL 补成 0
  且不再单列 unread / UNREADABLE 显示成 NO_ATTACK / 判定压过已派出的攻击 / 算进被拒的
  派遣 / 取最早那份报告 / 一份战报就算攻击完成 / 报告不按整坐标认 …）。其中两条第一轮
  是**绿**的：「NULL 补成 0」是等价变异（`unread` 另行算），换成「补成 0 且不再单列
  unread」之后才红；「报告只按银河筛」是断言真的太弱，补了
  `test_each_target_gets_its_own_report` 之后才红。
- Safety: 只读查询与识别配方的修正，未新增任何点击路径；`M` 后缀继续拒收。
- Rollback: 去掉 `pick_count` 里那条小数点折叠即回到原行为（连同 `1.22K` → 122000）；
  `domain/pirate_round.py` 与 `pirate_progress()` 是纯增量。
