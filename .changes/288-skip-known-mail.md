**开封之前按时刻跳过已入库的邮件。每两封就有一封是白开的。**

每趟进信箱都把每封战报点开、读完、解析完，才发现「库里已有，不重复入库」：

    09-07 全天（旧版本）        开封 513 封，其中白开 253 封（49%）
    09-08 07:32 之后（新版本）  开封  39 封，其中白开  19 封（49%）

比例没被回顶那几件影响 —— 它是另一条链路。一封约 20 秒（点开 4.1s +
解析入库 7.4s + 查重 8.5s）。而列表页那一列**开封之前就把时刻读出来了**。

⚠️ **顺带抢回开封预算**：`MAIL_MAX_OPENS` = 8，而实机每趟都撞「开了 8 封到上限」。
那 8 封里有 4 封花在已经读过的邮件上，真正要读的那几封被挤到下一趟。
所以这道闸不只是省时间。

## 判据：比「这一屏同一秒有几行」，不是「库里有没有」

    count_reports_at(t) >= max(这一屏该秒的行数, 1)   ->  跳过

⚠️⚠️ **「有就跳」会把同秒的第二封永久丢掉。** 2026-08-25 20:18:44 那一秒有两份
战报（`2:490:16` 与 `1:439:11`，**两个不同目标**），同一趟里隔 25 秒先后入库。
第二封被评估时库里已经有一份 —— 「有就跳」会让它这一趟跳过、**下一趟同样跳过**，
那一发派遣永远停在「待战报」。

而「比待补派遣数」的保守版也救不了它：那一刻该秒已有 1 份、待补 1 发，
`1 >= 1` 成立，照跳（2026-08-26 的日志实证）。

⚠️ 下界那个 `1` 不许省：算出 0 行时「库里 0 份 >= 0 行」会成立，
于是**库里什么都没有也跳过** —— 静默丢报告，最坏的失效形态。

## 五个前提，缺一不可

1. **只对攻击战报生效** —— 安全告警 / 保护期返航被时刻撞车顺带跳掉的后果是
   丢保护期记录或丢告警，而两者都不报错
2. **时刻读不出的照旧开** —— 那几行正是最该看一眼的（时间格实拍 93.5% 读得出）
3. 库里该秒份数 >= 这一屏该秒行数
4. **补录那一档不跳** —— `exhaustive` 那一档连早停都不走；在它上面开跳过
   等于把「人手动来救」这条最后的路也堵掉
5. **早停仍走 `_stop_after_known()` 本身**，不改写条件

第 5 条的雷写在 `_ingest_report_row` 的注释里：**报告确实在库里、却没接到该接的
那一发派遣上**，那时「库里已有 ⇒ 往下都读过了」会把那几发永久钉在「待战报」
（2026-08-11 那四发）。跳过之后该不该收工必须问同一个判据 —— 不许改写，
也不许省掉这一问（省掉的后果是从「早停」退化成「翻满上限」，
把省下的时间又花回翻页上）。

## 两个前置都已落地

- `#283` 索引 —— 这条查询**每封邮件跑一次**，没索引就是每封一次全表扫，
  省下的开封时间会被查库吃回去，而且分不清是哪一边
- `#286` 每趟补认领 —— 跳过之后那 54 份未认领**再也不会被重新开封**

## 记账

`MailScan.skipped_known` 与 `opened` **分开记**：一个是省下的、一个是花掉的。
混成一个数就看不出这道闸有没有在工作，而**「一直是 0」正是它最可能的失效形态**
（判据永远不成立，和没装这道闸在日志上一模一样）。所以有跳过报、没跳过也报一次。

## 用例

新文件 `test_skip_known_mail.py`（9 条），**按前提逐条钉，不按功能钉**。

变异三条，各被对应那条抓住，一对一：

    >= max(on_screen,1) -> > 0（有就跳）   ->  同秒两行那条红
    去掉类型闸                              ->  「安全告警不许被跳」那条红
    去掉下界 max(...,1)                     ->  「半屏糊掉」那条红

⚠️ 前提④ 那一条**读源码而不是跑流程**：接线错了跑流程也看不出来
（两个入口的 `visit` 不同，而跳过发生在 `visit` 之前）。断言是
「`skip_known=True` 全仓恰好一处，且落在 `_scan_for_reconcile` 里」。

⚠️ 顺带给 `test_mailbox_reconciliation.py` 的假仓储补上 `count_reports_at`，
**默认值必须是 0**：少了它整个文件报 `AttributeError`（那还算好，一眼能看见）；
默认给非 0 才是真陷阱 —— 那个文件全在验「开封与早停」，非 0 会让每一封都被跳过，
于是它们全在测一条什么都不开的路径。

- Configuration: 无新增配置项。
- Database: 无迁移（`count_reports_at` 只读）。
- Verification: `ruff check` / `ruff format --check` / `pytest -q`
  （4314 passed / 256 skipped）全绿。
- Safety: **判据一个字没动**（`_stop_after_known` / `_ingest_report_row` /
  三类邮件分流）。
- Rollback: 把 `_scan_for_reconcile` 那一处的 `skip_known=True` 去掉即可 —— 一行。
