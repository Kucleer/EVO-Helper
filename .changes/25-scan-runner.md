坐标扫描器正式化：按优先级顺序逐坐标扫描，把 bot 位置写进数据库，中断后从游标续扫。

扫描脚本此前一直在 scratchpad 里。现在搬进 `tools/scan_coordinates.py`，接上了已有的四块：
`scan_plan`（顺序 + 跳过海盗位）、`ensure_game_window`（窗口没了自己拉起）、
`SessionKeeper`（10 分钟巡检重连）、`run_instances` 的持久化游标。

- `domain/scan_plan.py`：把优先级分段展开成坐标流。**续扫按计划顺序，不按字典序**——
  计划里 `2:201–499` 排在 `1:001–499` 之前，拿字典序比大小会把整个 1 系判成已扫过。
  游标不在计划里时抛 `CursorNotInPlanError` 而不是从头重扫或当成扫完：前者白跑几万个坐标，
  后者留下看不见的数据缺口。
- `vision/scan_reading.py`：面板 ROI 与「这次读数算不算数」的判据，**只此一份**。
  `tools/ingest_scan.py` 改为从这里导入——判定规则各留一份的坑已经踩过（改一处，另一处继续放行）。
- `game/system_navigator.py`：导航栏几何 + 一次只设一个字段（点开字段会弹出覆盖整条导航栏的
  编辑浮层）。银河系/恒星系只在变化时重设，同一系连扫 16 位时省下的就是这部分。
- 游标只在坐标**读完并落库之后**才前进，所以中断最多重扫一个坐标。

## 本轮实机发现

- **游戏会自己回到行星视图**（会话刷新时实测发生），导航栏随之消失。这时再往 `(795, 71)`
  点就是在认不出的画面上乱点。`ensure_system_view()` 用导航栏**标签**判位置，不在就走
  「星球按钮 → 恒星系」切回来，三次切不回去就停。判据要求三个标签命中两个——
  `行星` 在底部导航条上也有，单个命中证明不了在哪一屏。
- **会话巡检的裁剪连图标一起裁会时好时坏**。同一屏两次读出 `区 Y ASA 商店 o j` 和 `6S BOD ®@`，
  前者恰好含「商店」，后者不含，于是在线的会话被随机判成「认不出」。改成只裁文字那一行
  `(800, 878, 1215, 908)` 放大 3×，读出「行星 舰队 … 联盟」。
- **核对失败一次就放弃会留下静默缺口**。那个坐标既没入库、游标又会被后面成功的坐标带过去，
  此后再也不会回来。现在同一坐标最多重试 3 轮，仍不过才记进 `var/logs/scan-gaps.txt`；
  `--rescan-missing` 直接对着「计划 vs 已入库」求差来补，不依赖任何日志。
- **相邻的 `1` 会粘成一根竖条，这是最大的一类失败**。游戏的数字字体把 `1` 画成没有衬线的
  竖条：`2:2:11` → `2:2:1`、`2:111:11` → `2:10:11`、`2:112:6` → `2:12:6`。
  影响面不是零星几个——**位 11 占全宇宙 1/16**，含 `11` 的恒星系约 2.8%。
  **重新导航没用**（实测读三遍错在同一处）：要换的是配方，不是画面。两条对策都是实测挑出来的：
  **放大要用最近邻**（LANCZOS 把两根竖条之间那道缝插值糊掉），**白名单去掉方括号**
  （`]` 被读成 `3`）。最终四套配方逐套试，在**同一张截图**上换，任一套通过就采信；
  都不过才重新导航。172 张样本（含 63 张实机失败样本）通过 140，救回 67 张。
- **ROI 带进了「坐标：」的尾巴**。数字白名单把它读成 `4:`（实机 `4:[2:6:15]`），
  多出来的 `4` 让核对失败。比对前先取方括号里的部分——**只挡前缀，不放松判据**。
- 剩下两个不过的历史样本读出的是**上一个坐标**（`2:123:5` → `[2:123:4]`）：那不是读错，
  是跳晚了，归重新导航那条路径管。两条恢复路径职责不同，都要留。
- **恒星系视图的快筛路线不可行**。交接文档把「一屏能看到几个行星位」列为待测；实测答案是
  这个问题本身不成立——恒星系视图是一张**可平移的散点图**，行星没有位号标签，
  边缘的名字还会被裁掉。看不出「20 个位是不是都看到了」，覆盖度无法自证。
  所以主路径仍是逐坐标导航，`«` / `»` 不参与扫描（它们切恒星系并关掉详情面板）。

- **右方括号会被读成数字**。有主布局的 `[2:12:9]` 稳定读成 `[2:12:93]` / `[2:12:39]`——
  那个 `3` 是右括号，两个放大档、三次重试全都一样。扫了一圈 ROI 边界也解决不了。
  这条不是小数：那个坐标上住着 `bot_2_12_9`，**丢的是 bot 本身**。
  核对改为两条互补判据取或：① 请求串原样出现在读数里（结构完整时最严，
  银河系是一位数、分隔符位置固定，别的合法坐标凑不出请求串）；② 数字序列相等（分隔符
  被漏读时兜底）。81 张样本 76 → 79 通过，`2:12:9` 已回收入库并正确判为 bot。

## 掉线恢复（本轮打通并实机验证）

实机上会话掉了一次，暴露出两个问题：

- **`ensure_game_window` 把「加载中」当成「窗口没了」，多拉了一个游戏窗口**。页面重连时
  标题会临时退回 `eternal-void.online`，精确匹配 `EVO` 便找不到。后果不是重试一次，
  而是桌面上多出第二个游戏窗口，`find_game_window()` 见到两个直接拒绝工作——
  扫描再也起不来，还得人工关窗口。现在先查有没有窗口在加载：有就等（180s），绝不再拉；
  冷启动上限 30s → 120s（要开 Chrome、下资源、初始化 WebGL）。
- **`SessionKeeper` 先前配的是「拒绝重连」占位实现**（没有已验证的按钮坐标）。现在补齐：
  入口页 → `进入` → START → 游戏内，三屏各有判据 ROI，**读到按钮才点**。
  两条要点：整屏 OCR 读不出 START（半透明大字压在星空上，psm 6/11/12 全败），
  必须紧凑裁剪 + 二值化；**判入口页要排在判 START 之前**，因为入口页是浮层、
  底下那个 START 仍在画面里，反过来判就会在入口页上去点 START。
  实机验证：一次 `ensure_connected` 走完全程返回 `reconnected=True`。

## 顺带修掉的缺陷

`claim_next_coordinate` 拿 `coordinates.POSITION_LIMIT`（499）当每恒星系的行星位上限。
499 是**每银河系的恒星系数**，用它做游标进位会让扫描在每个恒星系里空转 479 个不存在的位——
看起来一直在跑，实际一个新坐标都没到，而且没有任何报错。改为取区间自己的
`start_position` / `end_position`（本计划是 5–20），进位也落到 5 而不是海盗位 1。

- 配置：无变更
- 数据库：无迁移。首次运行会建一条计划「全宇宙优先级扫描」+ 10 条区间 + 一个运行实例
  （幂等键 `priority-scan-0001`，重跑即续扫）
- 验证：`pytest`（539 passed）、`ruff check`、`ruff format --check`、`mypy src`；
  实机从 2:1:5 连扫过 2:19 段，稳态 7.2s/坐标；坐标读数在 81 张历史+实机样本上 79/81 通过，
  剩下 2 张是面板停在上一坐标（属重新导航路径，非读数问题）；
  掉线恢复实机走通；`--rescan-missing` 三次运行共回收 5 个坐标（含 1 个 bot），0 残留缺口
- 安全：只读。全程只有导航点击，没有派遣/领奖/删信路径；`HumanInput` 拒绝动作类标签，
  `pyautogui.FAILSAFE` 保持开启；连续 5 个坐标核对失败即停，认不出的画面不点击
## bot 名前缀被读坏 → bot 被当成空位入库

`bot_2_9_5` 读成 `botleao.-`，连 `bot_` 前缀都糊了。**bot 判定就是看这个前缀**，
所以那颗星球作为普通空位入了库——丢的正是要找的东西。这类失败不报错、不进缺口清单，
是靠「每个恒星系恰好一个 bot」的分布规律才发现的（111 个完整扫过的系里只有那一个是 0）。

- `reread_owner()`：名字「以 bot 开头但下一个字符不是下划线」时换配方重读。
  **只有真的读出 `bot_` 才采纳**，绝不放宽前缀判定——真有玩家叫 `botanist`，
  放宽就会把人当成 bot，而 bot 名单最终是要用来派攻击的。
- `--recheck-suspicious`：反查库里已有的这类行并重读。实机跑通，`2:9:5` 已回收为
  `bot_2_9_5`，「每系恰好一个」随之变成 111/111 零例外。

## 每系一个 bot：找到就跳过本系剩余位

**用户已确认这是游戏规则**（实测 111/111 相符，位号分布均匀）。扫描据此提前收工，
期望每系扫 8.5 位而不是 16 位，全宇宙约 144 小时 → **76 小时**。

关键是「本系已扫完」的判据变了：**不是**「16 个位都入库」，而是「找到了 bot 或 16 个位都入库」。
这条判据只有一份（`systems_with_bot()`），主循环和 `--rescan-missing` 共用——
各写一份的话，补缺口会把主循环故意跳过的位当成缺口，每跑一次重扫一遍，永远补不完。
有用例专门钉住这一点。`--scan-full-systems` 可把这条假设撤销回去。

## 抢前台会被 Windows 拒绝

`SetForegroundWindow` 直接调会被拒（Windows 只允许当前拥有前台的线程换前台），
抛出的异常里 `GetLastError` 还是 0，什么信息都没有，整个扫描进程就此崩掉。
改为先 `AttachThreadInput` 把自己挂到前台线程上，**回读 `GetForegroundWindow` 核实**，
并退避重试 5 次——用户在别的窗口打字时被拒是常态，不是故障。
重试耗尽才停止，且停止时说清楚原因，不再是一串 traceback。
