控制台上多了一个「战报补录」，而且**补录优先于所有任务**：点「开始」会先跑一趟
战报对账，跑完才放行任务。

起因是 2026-08-12 那 21 份没能读进库的战报——bot 链路连挂三轮、6 小时追讨窗口过期，
邮件还躺在信箱里（认领窗口是相对战报自己的时间戳算的，所以补得回来）。

## 为什么补录必须排在任务前面

用户口径（2026-08-13）：「因为你补录之后，你就知道你还剩下几次海盗攻击机会，
有哪些 bot 已经攻击了，不要再重复攻击」。机制上是**会白打舰队**的那一档：

- bot 每个目标的态由 `domain.bot_round.phase_of` 判。战报没回来时它是
  `AWAITING_ATTACK_REPORT`（等着，不重打），**但** `bot_dispatch_facts` 会按
  `MAX_REPORT_AGE`（6 小时）把过期派遣整条剔掉，于是这个目标退回成「本轮一发都没
  打过」→ `NEEDS_ATTACK` → 被重打一遍。8-12 那 15 发丢了战报的 bot 攻击此刻正坐在
  这个状态上。
- 海盗当日配额数的是 `count_dispatches_since`，同一个道理。

所以顺序是硬要求，不是优化。

## 四段

1. 请求进来时正在跑**扫描** → 立刻抢占（`StopReason.PREEMPTED`，游标持久化）。
2. 正在跑**海盗 / bot** → 排队等它自己跑完。**绝不硬杀**：它们可能正卡在「点了
   出发」和「把这一发记进库」之间，硬杀会留下一发飞出去了却没记账的舰队。
   页面上写明在等谁。
3. 窗口空出来 → 起补录，**期间一个任务都不起**（闸门在 `MissionScheduler._act`，
   手动补录与启动对账共用这一道，不是两套）。
4. 跑完**不自动放行**：把「改了什么」摆出来，等用户点「继续任务」。

## 接口

| 接口 | 方法 | 作用 |
|---|---|---|
| `/api/backfill` | GET | 状态、日志尾巴、摘要 |
| `/api/backfill` | POST | 排一趟（`{"kind":"pirate\|bot","since":"YYYY-MM-DD"}`）→ **202** |
| `/api/backfill/cancel` | POST | 排队中撤掉 / 跑着杀掉，之后立刻放行 |
| `/api/backfill/resume` | POST | 「继续任务」：看过摘要，放行 |
| `/api/scheduler/start` | POST | 多收一个可选体 `{"reconcile": true}`，**不给就是做** |

202 而不是 201：这一下只是排上了，窗口可能还在海盗那一轮手上。

## 摘要摆哪三个数

补进来几份、**认领上几发**（认领上了才影响任务决策——没认领的战报 `phase_of`
根本看不见）、**几个 bot 目标从「还要打」变成了「已完成」**（这就是省下来的重复
攻击）。三个数都是补录前后各量一次数据库的差值，不解析子进程的输出——那种约定
断了不会报错，只会让页面上永远显示 0。

- 配置：**没有新配置项**。页面上两个新控件：「先对账再跑任务」（默认勾着）、
  「战报补录」面板（链路 + 起始日期，默认**昨天** UTC——默认今天会把昨夜漏掉的
  那批整批藏起来，而漏掉的恰恰是昨夜的）
- 数据库：**无迁移，一行都没写**。补录进程本身只读信箱、只写它自己入库的战报
- 验证：`pytest`（1747 passed / 56 skipped）、`ruff check src tests`、
  `ruff format --check src tests`、`mypy src`。27 条变异逐条确认变红（闸门放行、
  blocking 少算排队 / 少算「跑完没确认」、放宽抢占判据、扫描不抢占、点开始不对账、
  两处 reconcile 默认值各一条、409 去掉 / 409 不看「已经开着」、默认日期改成今天、
  命令行去掉 `-u` / 写死 python、同链路排两趟、提前确认也算数、摘要不数「变完成」、
  没参与调度的任务也量、取消不杀进程、关闭不收进程、失败还接着跑下一趟、第二趟另量
  底数、日志尾巴按链路名猜路径、未来日期也收、少一档色调字形、去掉 token 中间件、
  「等任务结束」不说等谁、摘要不分认领与入库）
- 安全：**这个 PR 里没有任何一行代码在 CI 上驱动过游戏**。两侧的 `launch` 在测试里
  一律注入假的——补录是第二个进程管理器，漏注入会真的去 `Popen` 一个翻信箱的进程
  （实测漏过一次，工作区里落下了 `var/logs/backfill-pirate.log`）。为此
  `MissionScheduler.start()` 的 `reconcile` 默认是 **False**，「默认要对账」放在有
  用户的那一层（`MissionConsoleService` 与 `SchedulerStartIn`）——同 `freeze_log`
  那条：真的起一个子进程必须是组装点明确决定的事。
  写接口照旧要 token / 同源（`web/security.py`），三个新接口各有一条用例钉着
- 回滚：revert 本次提交。回滚之后「开始」不再对账，补录只能手工敲命令行；
  已经补进库的战报不受影响（这条路径不写任何调度状态）
