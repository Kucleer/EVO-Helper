派遣链路两处耗时优化，各自独立：**预设条先看打开时这一屏再决定要不要拖**，
**切完出发星球后用「回读导航栏」代替「清空导航缓存」**。合计约 15 分钟／天。

实测数据全部来自生产 `system_log`（2026-08-17 一天，177 次派遣）。

## A. 预设条：先看打开时这一屏（约 12 分钟／天）

`PresetPicker.pick()` 原先固定「展开 → 拖到左端夹住 → 逐屏往右找」。而
`scroll_to_left_end` 的判据是「往左拖一次之后名字没变」，所以**条本来就开在左端时
也必然白拖一次、白读一屏**。

实测「翻预设条」这一步：9–10 秒 137 次（最短路径）、13–14 秒 40 次。
137/177 落在最短路径上，说明条绝大多数时候本来就开在左端。用户口径（2026-08-18）：
「目前首屏预设就是 AAA 和 BBB，我已经调整了，并且 CCC 场景为兜底场景，出场较少」。

改法只有一处：`expand()` 之后先读一屏当前画面直接试命中，命中就点（零次拖动），
没命中就原封不动走老路。多读的那一屏**不浪费**——它作为 `scroll_to_left_end` 的
起点（新增的 `seen` 参数）传下去，所以驱动上的动作序列与改动前**逐字相同**，
连 OCR 次数都没变。测试里留了一份改动前 `pick()` 的参照实现来钉这条等价性。

三条守住的：

- 点击仍旧走同一个 `_clickable_hit`，安全区 x 与「保存」关键字两道闸原样生效。
- **首屏读空绝不当成「这儿没有」**，而且不许拿那份空清单当老路的起点（拿空清单
  当起点，「拖了一次还是空」会被误判成「已经夹住了」）。这正是 2026-08-13 通宵
  事故的形态：一屏读空被当成「这一段没有预设」，白跑 145 次约两小时。
- 位置只来自当前这一屏的 OCR（用户 2026-08-11 口径）。

**下游坐标的残留风险已经排除**（这是动手前必须验的那条假设）：实拍
`var/logs/atk-2-presets.png` → `atk-3-selected.png` 显示，选中预设之后**预设条整个
收起来**，派遣面板回到「起点 / 终点 + 绿 ✓」那副样子，所以
`DISPATCH_CONFIRM` (1156, 763) 落在哪与条被拖到过哪里无关。没点中那一支仍旧照旧
把条拖回左端。

## B. 切完出发星球：回读导航栏而不是清缓存（约 3.6 分钟／天）

`ensure_origin_planet` 原先切完无条件 `invalidate()`，于是下一个目标的 `goto`
三个字段全设——哪怕出发星是 `4:277:15`、目标是 `4:273:12`，那个银河系 `4` 一个字
都没变。实测导航耗时两簇：设两个字段 150 次均值 14.02 秒、设三个字段 37 次均值
20.65 秒，**一个字段 = 6.6 秒**；37 次三字段里 33 次紧跟在「出发星球：切到 …」之后。
（`SystemNavigator` 注释里原写的「约 3 秒」是按等待常量估的，实测翻倍，顺手改对。）

新流程：切换成功 → `_require_system_view` → **回读导航栏三个值框** →
读出来逐字就是出发星才 `adopt_readback()`，否则照旧 `invalidate()`。
顺带白捡一档：目标与出发星同恒星系时连恒星系字段也省，再省 6.6 秒。

⚠️ **顺序是承重的**：回读必须排在 `_require_system_view` **之后**——那个函数一旦
需要切视图，`ensure_system_view` 内部自己就 `invalidate()`，放前面会被当场抹掉
（功能一次都不生效，而且日志照样说「确认停在 …」）。

### 为什么读导航栏，而不是拿切星球那次回读将就

`game.planet_list._confirm` 切完确实回读过一次坐标（日志里那行「起点回读 …」），
零成本。但它读的是**派遣面板的起点**，证明的是「我现在站在这颗星球上」；而缓存要
描述的是**导航栏三个输入框里的值**。两者在游戏里应该耦合，实拍
`var/logs/calib-恒星系-client.png` 也支持这一点（刚登录、一个字都没往框里打过，
从地表切到恒星系视图后三个框就是当前星球 `2:137:18`——那三个数只可能是游戏自己
填的）。**但样本里只有主星一颗**，分不开「显示当前星球」与「显示主星」，所以那仍是
观察不是证明。

于是没有采用零成本那条，改成老老实实读那三个框本身：每轮一次 OCR（一轮只切一次
星球），换来的是这条捷径不依赖任何未证实的耦合。日志里那行读数顺带把耦合到底成不
成立记进库——想省掉这次 OCR 的人以后有真实证据可查。

### 新增的标定常量

`NAV_VALUE_ROIS`（三个值框，下界与 `NAV_LABEL_ROI` 上界贴齐但不重叠）与
`NAV_VALUE_RECIPES`（`(放大倍数, 二值化阈值)`，**每个框各自**逐套试到读出为止）。
两条都注明了「这不是偏好项」：取值由屏幕几何与 OCR 配方决定，改了就是错。

配方是在九张实拍上扫出来的（三张 `calib-*恒星系-client.png` + 六张
`dump-*-coord-mismatch-*.png`，真值人工核对）：**八张三个框全对、一张的行星框读成
空串、零张读错**。挑这三套的理由是它们**只会读空、不会读错**——被剔掉的 `(3,140)`
与 `(4,140)` 会把 `11` 读成 `1`、把 `9` 读成 `93`，而读空只是白设两个字段，读错是往
缓存里塞假证据。新增实拍守卫 `tests/integration/vision/test_nav_bar_values_live.py`。

- Configuration: **两处都不加开关。** A 的判据是「这一屏读到的名字里有没有它」，
  B 的判据是「三个框读出来是不是这个坐标」——两者都由画面回答，没有哪种用户处境
  下把它调成别的会让结果「更合用」，只会更错。按仓库口径这是标定常量而不是运维
  旋钮。新增的 ROI 与配方注释里各写了一句「这不是偏好项」。
- Database: 无迁移，无 schema 变更。整个过程没有连过任何数据库。
- Verification: `pytest -q`（2687 passed / 78 skipped）、`ruff check src tests`、
  `ruff format --check src tests`、`mypy src` 全绿。skipped 是缺实拍截图 / Tesseract
  的那批 vision 实拍用例，属正常。含四处变异测试，各自确认对应用例转红（见 PR 正文）。
  全程没启动游戏、没动鼠标键盘、没起 runner。
- Safety: 两处都只改**要不要重复做一件已经做过的事**，不改任何一次点击的落点。
  A 的点击仍旧只用当屏 OCR 出来的 x，且必须过 `_clickable_hit` 那两道闸；
  B 的缓存仍旧只接受回读确认过的坐标，读不出与读出别的坐标一律 `invalidate()`——
  **方向永远是「拿不准就多设」**。万一记忆终究不作数，下一个目标的面板核对会当场
  核不过，走 `_goto_checked` 自愈（这条路径本来就在）。
- Rollback: 两处互相独立、各自一个 commit，单独回退任一处都不影响另一处。
  回退 A 恢复「每次都先白拖一次」；回退 B 恢复「切完星球下一个目标三字段全设」。
