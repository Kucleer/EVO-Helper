**周期统计与按星球效率各加三列基础资源的收入。** 用户口径 2026-09-13，原话记在
`domain.overview.BASIC_SLOTS` 上。格子里是**攻击 + 回收的合计**，鼠标停上去写
「攻击 X · 回收 Y」。

## ⚠️ 分开写不能省

攻击捞回的这三样由**我方货舱容量**决定、与目标无关（实测 2026-08-20，同一预设
6 条战报的变异系数 0.0001）；回收捞回来的才是真正随目标变的收成，而回收报告
**只有**这三样。只给一个合计，这一列就退化成「这颗星球的货舱有多大」——
而用户看它正是为了判断回收那条链路值不值。

⚠️ 两份是**减出来**的（合计 − 回收），不另查一趟：各查一趟的话，两趟之间入了
一份战报，页面上就会出现「攻击 + 回收 ≠ 合计」。回收那一份靠 `outcome = RECYCLE`
这个记号数出来（回收报告复用 `battle_reports`，理由在 `to_recycle_report` 上）。

## ⚠️⚠️ 进表不等于进指标

「每线」「每线小时」的分子**仍然只算稀有三样**，`domain.origin_efficiency` 里
那两个数一个字没动——掺进基础三样会让「预设大的星球」无脑领先。

原来那条用例判的是「页面上一格都不许多」，而它现在会把**正确显示了收入**也判成错。
改判**分子**：合计 2,161,000 一次都不许出现，右边两个效率数必须只由稀有那 1,000 算出来。

## 布局

导航 208px → 150px（下限由「数据概览」四个字与 `.brand` 定）；两张表行高与字号
收紧；首列冻结。实测 1200px 视口下表宽 973，15 列全放得下、页面不横向滚。

## 顺带修了两处

**colspan 那条守卫自己算错了列数。** 原先「这一列展不展开」是调用方传进来的
布尔量，而那是**模板自己的事实**，两处必然分家：加第二组按槽位展开的列之后，
它拿偏小的列数去比，**写对了的 colspan 反而报红**。改成直接从 `<thead>` 源码上
认循环，并加一条「两张表都要有这组列」——只改一张是这次最容易犯的错。

**行首那一格被冻结顶了出来。** 它是 `<th scope="row">`，于是通用表头规则顺带给了
它 `position: sticky; top: 0`；`z-index` 抬到 2 之后这件事才显形——纵向滚动时
每一行的行名会依次钉在容器顶上、叠成一摞。在 `tbody th` 上解掉纵向那一半。
