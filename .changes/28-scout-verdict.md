侦察报告读出海盗的判定舰种，给出「打 / 不打 / 不下结论」三值结论。

- `vision/scout_reports.py`：只读四个判定舰种，不读资源、建筑、全部 21 行
- `report_screens.named_counts()`：在一张清单里**按名字**取数量

## 设计要点

- **判据是三值不是布尔**（`ATTACK` / `SKIP` / `UNREADABLE`），而且不对称：
  读到任一 > 1 就打（缺的格子只会让对方更强，不会让结论反过来）；
  读到的都 ≤ 1 但还有格子没读出来时**不下结论**（缺的那格可能正是一支舰队）；
  四格都读出来且都 ≤ 1 才叫不值得打。合成一个布尔就分不出后两种，
  而「把没看清当成这里是空的」是这条链路唯一会把舰队送错地方的方式。
- **按名字取数，不按行序对位。** 实测逐行对位会掉行（`钛能守卫者` 整行没被认出），
  之后每一行的数字都串位——`拦截导弹` 读成 5，真值是 0。串位比读不出危险得多：
  数字看着都合理，没有任何地方会报错。
- **等距网格在长清单上会漂。** 侦察报告行距 27.5px，取整成 27 到第 12 行就差了
  半行，那一行的数字因此落在裁剪框外。按名字取数改用每行**实测**的 y。
  （`read_fleet_rows` 仍用网格：它要处理「整行没认出来」，网格能补上位置。）
- **坐标那一行中英混读读不出来。** `[2:137:18]` 读成 `[e:137:18]`、`[2:137:4]`
  读成 `[137:4]`——首位被吃掉，而剩下的 `137:4` 仍然像个合法片段。改用数字白名单
  + `eng` 多套配方各读一遍，再按「**恰好**两个坐标且都在银河/恒星系/位号范围内」挑。
  不是「取前两个」：噪声读法 `2:137:18 382:137:4 3` 也有两个，
  多出来的东西说明这一遍读脏了，整遍作废。
- **核对目标坐标。** 信箱按时间倒序，上一轮的侦察报告看起来永远像「最新那封」；
  不核对就会照着旧报告朝没侦察过的坐标打出去。

## 实机事故：全 0 的海盗被读成有舰队，真的挨了一发（2026-08-09，已修）

数量列原先用 `number_column()` 现场量，而「四项全 0」的清单里每格只有一个窄窄的
`0`，够宽的墨迹段只剩面板左边那层水印（`-17003` / `COMMAND OFFICERS`）——量出来的
「数字列」是 `(731, 808)`，读到的「数量」其实是水印里的数字。判定因此把 2:137:2
当成有舰队，`pirate_loop` 打了一发出去。**同一封报告两次读成 `{'噬能截击者': 8}`
与 `{'深空吞噬者': 2}`，前后不一致本身就是这个错的指纹**——当时没当回事。

两条修法，一条挡这次，一条挡这一类：

- **数量列写死**（`SCOUT_COUNT_BAND = (1090, 1195)`）。这一列右对齐、贴着面板右沿，
  位置本来就是固定的；写死既准又把水印挡在外面。`named_counts` 现在要求调用方
  显式传入，不传才退回现场量。
- **非 0 的读数要至少两套配方读出同一个字符串**（`COUNT_MIN_AGREEMENT`）。
  0 只要一套就采信——这条不对称是有意的：非 0 会让判定变成「打」、真的送出舰队，
  所以它需要旁证；假的 0 只会让我们白跑一趟。

回归测试 `tests/integration/vision/test_scout_counts_live.py` 用那两张真实截图
把方向钉住：全 0 那封**一定不能**判成打，有舰队那封一定要判成打。

**教训**：「同一份输入两次读出不同结果」是数据读错了，不是运气不好。
下次看到这种不一致必须当场停下来查，而不是接着往下跑。
