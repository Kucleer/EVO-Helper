**点完标签之后要等列表刷新再判。** 一次没读到就重点，会把刚切好的档位又点回去。

## 实拍证据

2026-09-15 02:31（`#347` 上线后第一趟）：判据连着读到的都还是**舰队类**，
于是判定「切不到战斗」、又点了一次。而失败时存的现场图
（`dump-mail-sub-tab-战斗-unconfirmed-023122.png`）上：

    战斗 [15]   侦察   舰队 [99+]   系统
    第一行：📧 攻击报告   System   14/09/2026 18:30:19

**列表里就是攻击报告 —— 那一下其实成功了**，只是列表刷新比判据慢。

⚠️⚠️ `#336` 当年「战斗那个按钮不响应」的结论，多半也是同一个时序假象。
那个错误结论让「切回战报」整整走错了两天：
先删掉正确的按钮、改成 toggle，再由 toggle 导致列表变空、攻击战报整晚读不到。

**一次没生效 ≠ 这条路不通。** 这一晚我在同一件事上付了两次学费。

## 改

点完之后最多再读 `MAIL_SUB_TAB_SETTLE_READS`（4）次、每次隔
`MAIL_SUB_TAB_SETTLE_WAIT_S`（2 秒），读到就算成功；读不到才进入下一轮重点。

原先是：点一次 → 读一次 → 判失败 → **立刻再点**。
而「再点」在这一排上意味着**把档位切走**。

## 用例

前 3 次读到旧内容、第 4 次才刷新过来时：必须返回成功，且**只点 1 次**。

- Configuration: 无
- Database: 无
- Verification: `ruff` 全绿；`pytest` 4657 passed / 0 failed。
  ⚠️ 实机上 `#347` 已让攻击战报恢复入库（02:38 两份 VICTORY、已认领）；
  本 PR 去掉的是那几次**多余的重点**。
- Safety: 只在原有重试之内多读几次，最坏多花约 8 秒；不新增任何点击
  （恰恰相反：它减少点击）。
- Rollback: 回退即可；回退后回到「读一次就判失败、立刻再点」。
