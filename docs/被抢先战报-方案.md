## 一、结论：用户的描述有一半对不上，方向要改

**「状态是单独的」这句是对的，但它不是「被判成了错的档」，而是「根本没进库」。**

那封 18/08/2026 03:12:28 在生产库里定位到了对应的那一发：

| 事实 | 值 |
|---|---|
| 派遣 | 4:248:11，08-18 10:52:17 CST 派出，飞行 1213s |
| expected_report_at_utc | 08-18 11:12:30 CST = **03:12:30 UTC** |
| 用户截图里那封 | **03:12:28**（差 2 秒） |
| battle_reports 里 4:248:11 的战报 | **一条都没有** |
| 其余 5 封（03:11:27 / 03:08:33 / 03:08:04 / 03:02:01 / 02:56:40） | **全部在库，全部 VICTORY** |

system_log 把它的下场记了**两次**（11:24 与 11:51，同一封、两趟、同样的空读）：
「第 0 行开封（时间读不出 空串）」→「第 0 行的 VS 块读不出来；不猜它是谁的战报」。

**不是 OCR 抖动。** 它走 tools/bot_loop.py:236 的 ReportIngest.UNREADABLE，
**在 decide_outcome 之前就被挡掉**，所以：

- 不会被判成 VICTORY / FAIL / DRAW；
- 也不会落进 outcome IS NULL 那一档（那档要求库里有行）；
- **它什么都不是**：库里没有这一行，页面上那一发**永远显示「待战报」**
  （logs.html：outcome is none 且 report_received 为假 → 灰字，**没有过期机制**）。

### 两个被数据证伪的假设（记下来，别再走一遍）

- 「#174 之后横幅是第一判据，那这类战报横幅上写什么？」→ **走不到那里**，decide_outcome 从未被调用。
- 「查 outcome IS NULL 的 10 行，看 defender_units 是不是 0」→ 那 10 行**不是**这一类。
  逐行看过：08-11 那 6 行是 bot 探路战报四个数全 NULL；一行缺 attacker_losses；
  一行是 defender_units=3550 而 defender_losses=7650（损失多于单位）。
  **没有一行的 defender_units 是 0。**

## 二、机理：粉红底把白字压没了（已在离线样本上复现）

实拍 var/logs/dump-mail-detail-unrendered-234504.png（信箱列表，1920x917）里有唯一一张
带粉红行的截图——最后一行「卫星已形成！/ System / 11/08/2026 15:25:46」整行粉红底、绿角标。

用**生产同一条读法**（crop_to_viewport + ImageReportScreens._read：灰度 + 3x LANCZOS
+ --psm 6，不二值化）对准粉红带 y=678..758 读：

| 读法 | 结果 |
|---|---|
| 粉红行 · 灰度（现状） | 空串 —— **整行读空** |
| 粉红行 · 绿通道 | 「卫星已形成 ! / System / 11/08/2026 15:25:46」**全对** |
| 粉红行 · 灰度+阈值150 | 大体读得出，有零星错字 |
| 上一行（蓝底，同尺寸 ROI）· 灰度 | 正常 |

**这把 11:24:11 那条「时间读不出」在离线样本上复现了**，不用碰游戏就能写回归。

### 「粉红 = 选中/未读」这个竞争解释，被数量证伪

var/logs/dump-mail-*.png **全部 54 张**列表截图逐张扫粉红带（判据：R 比 B 高 25 以上
且 R>70 的像素占该行 60% 以上）——**54 张里只有 1 张有粉红行**。

这 54 张里有大量是**刚点开一封邮件失败后拍的**，如果粉红是「选中/刚打开」，它们里面
应该遍地是粉红行。**一张都没有。**

### 角标颜色是分类信号

- dump-mail-detail-unrendered-025326.png：整屏「攻击报告」，角标全是**红色准星**（对应「战斗」页签）
- dump-mail-detail-unrendered-234504.png：整屏「侦察报告 / 卫星已形成！」，角标全是**绿色齿轮**（对应「系统」页签）

用户截图里那封是**绿角标**——游戏把它归成了「系统」而不是「战斗」，和「舰队飞到时没打起来、
所以它不是一份战斗报告」自洽。

### 零证据的地方

**没有任何一张这类邮件的「详情页」实拍。** 原因在代码：tools/bot_loop.py:236 那条失败路径
**只 say() 一句就 return，不 _dump_frame、不存面板图**（存图那步在下一层，永远走不到）。
battle_report_screenshots 里 27 张全是入库成功的正常战报。

dump-battle-report-unreadable-*.png 那 9 张全部是「海盗攻击报告被拖到底」的截屏，
横幅和 VS 块滚出可视区，是已知的滚动问题，**不是新版式**。

**所以：任何靠「详情页上写着什么」立的判据，此刻都是猜的。方案因此必须分两期。**

## 四、方案

### 第 0 条铁律：不许回填历史行

库里 131 行、10 行 outcome IS NULL，已逐行核过**不是**这一档。新档只对**新采到的**报告生效。

### 第 1 期：先把证据拿到手（必须先做，可独立合并）

**1.1 列表侧：粉红行绿通道回读**（有离线样本可验）

灰度读到某一行**为空**时（不是每行都读，稳态零成本），改用**绿通道**再读一次。
判据来源是第二节的 A/B 实测。**顺带修好第三节 #8 的配额少算。**
绿通道/阈值 150 是由这一屏配色决定的**标定常量**，注释写明「这不是偏好项」。

**1.2 详情侧：失败时把现场存进库**

_ingest_report 现在 VS 块一失败就 return、什么都不留。改成：先读 header / 横幅 / 单位数，
**再**判 VS 块；失败时走 record_system_log，payload_json 带齐列表行原文、header 原文、
VS 块原文、横幅原文、四个数的读数。

**面板图必须进库、不能只落 var/logs**——runner 在另一台机器上，本地取不到。
照抄 record_overlay_evidence 的「缩略图塞 payload_json + 限流」写法，复用
report_panel_image()（WEBP q90，实测约 42 KB）。
限流：**同一封只写一次**（按列表行身份去重）+ 时间窗兜底。

**1.3 验收**：跑 1-2 天，从 system_log 捞出 header 原文 + 面板图。**拿到 3 份以上样本再开第 2 期。**

### 第 2 期：立判据、加档（拿到样本之后）

**2.1 识别判据**——三层，**判档只认第 3 层**：

| 层 | 用途 |
|---|---|
| A. 列表侧「粉红底 + 绿角标」 | **只用来预筛**（开不开封、计不计配额）。颜色 ROI 是标定常量；样本只有 1 张，不足以标定阈值，第 1 期要攒 |
| B. 主题词表 | **只用来写日志**，不参与判档。要扩就走 domain.text.snap_to_vocabulary，别堆子串判断 |
| C. **详情页结构签名** | **唯一判档依据**：VS 块空 **且** 单位行空 **且** 横幅空 **且** 正文块非空 |

**为什么 C 可靠**：单个 ROI 读空既可能是「没有这块内容」也可能是「这一帧没读到」，分不开；
但四块同时空、另一块同时非空，是**结构**而不是**读数**，单次 OCR 抖动做不出这个组合。
**强制两帧一致**（recapture 重拍），两帧不一致 → **回到今天的行为**（拒收 + 留日志 + 存图），
**绝不猜**。游戏改文案不影响 C（它不读字）。

**2.2 数据模型：battle_reports.outcome 加一档，不加新列**

- 生产实测：outcome 是 varchar(16)，battle_reports 上**没有任何 CHECK 约束** ⇒ **不需要迁移**。
- 不用单独一列的理由：AWAITING 的判据是 outcome IS NULL，新开一列而 outcome 留空 =
  这类记录被静默并进「待战报」。
- 取值建议 NO_BATTLE（不超过 16 字符）。
- 代价：outcome 现有语义是「画面横幅上那行大字的原文」，而这一档不是。
  **必须显式选一个**：要么改注释说清「这一列存的是战果档位，其中三档取自横幅原文」，要么别加。

**2.3 全案最大的坑：新档绝对不许进 OUTCOME_LABELS**

OUTCOME_TOLERANCE 是按 OUTCOME_LABELS 里最长那个词算出来的（round(len/3)），
而它同时被 snap_to_vocabulary 当作横幅吸附的最大编辑距离。

把 PREEMPTED（9 字母）加进去，容差从 **2 变成 3**——**四字母的 FAIL / DRAW 会以距离 3
去吸附噪声**，而那行大字是半透明压在星空上、实测会掉字母。pirate_reports.py 的注释已经预警过。

**必须把两个词表拆开**：OUTCOME_BANNER_LABELS（横幅吸附，= VICTORY/FAIL/DRAW，不动）
与 OUTCOME_VALUES（库里取值集合）。decide_outcome **绝不返回新档**。

**2.4 展示层**：web/display.py 三张表各加一行（标签建议「未开打」，色留空不上色——
它是终态不是告警，同 NO_REPORT；字形建议一个划掉的圈）。其余零改动。

**2.5 日志**：三个时刻走 record_system_log 落库——判成新档（INFO，四块 ROI 各读到什么 +
两帧一致）、两帧签名不一致（**WARNING，说清两帧各是什么**）、结构不成立又读不通（升级成带
payload + 缩略图的证据）。每封邮件最多一条，不在 tick 里。

### 第 3 期（可选，独立）：GEF攻击报告 / 矮星系统战报

dump-mail-detail-unrendered-025326.png 上有一批主题「GEF攻击报告」、发件人 **Aries [HQ]**
（不是 System）的邮件，全仓 grep GEF 零命中。而 classify_report_subject 是**裸子串判定**，
含「攻击报告」→ 判成 ReportKind.ATTACK → 照样开封、照样送进 parse_versus_block。

08-18 00:37 那一趟**连续 6 封**全部「VS 块读不出来」。核过：那个时刻**没有任何一发我们的派遣
期望在 16:26 出战报** ⇒ **这 6 封不是我们的战报，和本题不是同一件事**。建议单开任务。

## 六、测试与变异计划

基线：test_battle_outcome.py + test_pirate_reports.py + test_pirate_battle_report_ingest.py **42 passed**。

| # | 钉住什么 | 变异（改坏这里，必须红） |

| 1 | **横幅吸附容差恒为 2** | 把新档塞进 OUTCOME_LABELS → 容差变 3。**这条最重要** |
