## 四、怎么复算（把查询记下来，别每次重想）

全部只读，连接前先 `SET default_transaction_read_only = on`。

**A. 资源识别的覆盖率（先看这个，它决定别的能不能算）**

```sql
SELECT count(*) AS reports,
       count(*) FILTER (WHERE EXISTS (SELECT 1 FROM battle_report_resources r WHERE r.report_id = br.id)) AS with_resources
FROM battle_reports br
WHERE reported_at_utc >= TIMESTAMPTZ '2026-08-18 00:00:00+08';
```

**B. 单位数 → 三种稀有材料（第 7 条）**

```sql
SELECT br.defender_units,
       max(amount) FILTER (WHERE slot = '5') AS 合金碎片,
       max(amount) FILTER (WHERE slot = '8') AS 泰坦立方,
       max(amount) FILTER (WHERE slot = '9') AS 收割者碎片
FROM battle_reports br JOIN battle_report_resources r ON r.report_id = br.id
WHERE br.defender_units IS NOT NULL
GROUP BY br.id, br.defender_units ORDER BY br.defender_units;
```

**C. 运力封顶（第 4 条）**

```sql
SELECT br.attacker_units, sum(r.amount) AS haul,
       round(sum(r.amount) / br.attacker_units) AS per_unit
FROM battle_reports br JOIN battle_report_resources r ON r.report_id = br.id
WHERE br.attacker_units IS NOT NULL
GROUP BY br.id, br.attacker_units ORDER BY br.attacker_units;
```

**D. 军力 ↔ 守方单位（第 5 条）**

```sql
SELECT br.defender_units, bt.military_score
FROM battle_reports br
JOIN bot_targets bt ON bt.galaxy = br.defender_target_galaxy
                   AND bt.system = br.defender_target_system
                   AND bt.position = br.defender_target_position
WHERE br.defender_units IS NOT NULL AND bt.military_score IS NOT NULL;
```

**E. 飞行模型（第 2、3 条）**

对比 `attack_dispatches.flight_seconds` 与
`2 + 26.5165 × sqrt(D)`，其中 `D = 跨银河 ? 20000×银河环距 : 1162 + 31.71×恒星系环距`。
**环形距离**：银河 9 个成环，恒星系 499 个成环，绕近的那边算。

**F. 单位是否衰减（第 8 条）**

```sql
SELECT defender_target_galaxy, defender_target_system, defender_target_position,
       array_agg(defender_units ORDER BY reported_at_utc), count(*)
FROM battle_reports WHERE defender_units IS NOT NULL
GROUP BY 1,2,3 HAVING count(*) > 1 ORDER BY 5 DESC;
```

## 四·五、⚠️ 拟合时必须带上「暴露时长」这个变量（用户 2026-08-18 提出）

> 「攻击触发的快照军力时间要记录，因为这期间可能被其他玩家攻击过，导致实际攻击时，
> 已经被严重削弱了。」

**数据已经在记了**（PR #183 快照 `target_military_score` + `target_military_score_at_utc`，
PR #185 补 `target_military_score_estimated`），落地时刻由 `dispatched_at_utc + flight_seconds`
推出，所以**暴露窗口 = 落地时刻 − 读数时刻**，现成可算。

### 首批 15 条快照实测：大头不是飞行，是读数本身就旧

| 目标 | 军力 | 读→派 | 飞行 | 读数到落地 |
|---|---|---|---|---|
| 9:205:14 | 31,940 | 11.2h | 2.1h | **13.3h** |
| 9:231:7 | 22,050 | 11.1h | 0.3h | 11.4h |
| 4:289:10 | 24,020 | 8.5h | 0.3h | 8.8h |
| 9:237:19 | 30,135 | 9.5h | 0.3h | 9.7h |

**「读数到派出」占 84–98%，飞行只占 2–16%。**
所以「跨银河飞得久所以更容易被别人先打」是**二阶效应**；
一阶的是**军力读数在派出那一刻已经旧了 8–11 小时**。

（成因已知：有效期设 3 小时，但「军力截断 500 > 窗口内 193 个」使每轮都触发放宽，窗口不生效。）

### 拟合时怎么用

把「读数到落地的时长」当**协变量**，或者只用暴露窗口短的样本去拟合
「军力 → 材料」——否则拟出来的曲线里混着「被别人削弱了多少」，而那与军力本身无关。

### 「被别人打过」有一个现成的检测手段

`defender_units` 是目标在**开打那一刻**的强度，而它已被确认是 bot 的**固定属性**
（打光 100% 之后 0.3 小时再看仍是同一个数，见第一节第 8 条）。

⇒ **同一个目标这次的 `defender_units` 明显低于它的历史值，就是「被别人先打过」的证据。**

库里已有 107 个目标的历史单位数，这个判据**现在就能算**，不需要新增记录。
它同时能填上第一节里一直空着的「打空」那一格——之前判断「连自变量都没在记录」，
是因为只想到了「被拦下」事件（`system_log` 里 311 条纯文本、没落库），漏了这一条。

## ★ 八、⚠️ 衰减项**暂不进排序**，先攒数据（2026-08-20 决定）

用户口径（2026-08-20）：「**我认为衰减公式的数据支持太少了，不进行更新，先收集数据。**」

### 8.1 决定是对的，理由比「样本少」更硬

`稀有 ≈ 0.141 × 军力 × exp(−0.068 × 龄)`（n=74、R²=0.781）这条曾被建议接进
`domain.target_order.attack_value`。**不要接。** 2026-08-20 生产库实测：

```
全部有战报有资源的样本                n = 118
其中龄落在实际窗口（0–6h）内          n = 113
龄 > 6h 的                            n =   5   ← −0.068 基本由这 5 个点定出来

只用窗口内样本重拟（军力指数钉死 1.0、过原点）：
   最优 q = +0.000        R² =  0.077
   钉死 q = −0.068        R² = −0.120   ← 比直接取平均还差
```

⚠️ **要害在这里**：`score_max_age_hours` 把龄 > 6h 的目标**全部挡在派遣之外**，
所以定出 −0.068 的那 5 个样本，代表的是**永远不会被派出的目标**。
把一个由窗口外样本定出来的系数，用到窗口内的排序上，是**外推**，不是拟合。

### 8.2 ⚠️ 连带更正：先前报的 R²=0.781 被老读数样本撑起来了

那次拟合（n=74，2026-08-18~19）包含龄最大 21.8h 的样本。它们收获低，模型把这笔
归给了衰减项，于是 R² 从 0.460（无衰减）跳到 0.781。**把范围收进 0–6h，
这份解释力就消失了。** 报那个数时没做窗口切分，是疏漏。

**教训**：⚠️ **拟合的取值范围必须和它将被使用的范围对齐。** 一个在 0–22h 上
拟得很好的系数，在 0–6h 上可能一点用没有——而系统只在 0–6h 里工作。

### 8.3 还有一个没查清的（不要当结论用）

窗口内 `q=0` 时 R² 只有 **0.077**。按理军力单独也该解释更多。可能的成因：

- **过原点模型不合适**——带截距拟出来是 `307 + 0.117 × 军力`（R² 0.936，n=31，单日）；
- **新数据结构不同**——2026-08-20 起多了出发点 `7:228:15`，预设与距离分布都变了。

**没有查清，不下结论。** 复算时先做这两个切分再谈。

### 8.3·五 ⚠️ 比样本量更根本：函数形式错了（2026-08-20 追加）

实测 42 条「打过之后又被扫到」的坐标：**27 个基本不变，14 个崩 20–93%**（最狠 −92.9%）。
**这是双峰分布**，真实机制是「这一发有没有把它打败」这个**离散事件**。

⚠️ **但「函数形式错了」这个说法已经收回**（2026-08-20 同日）。用户给出了机制：
**核心三资源就是舰艇被打爆的产物**，所以「龄越大收获越少」的真实含义是
「别人先到一步把库存取走了」——那是**生存过程**，而 `exp(−λt)` 正是它的生存函数，
**形式是对的，拟的是期望值不是个体轨迹**。双峰只是个体层面的表现。

⇒ **所以本节（8.3·五）不再是「不做」的理由**，8.1 那两条才是：
定出 −0.068 的 5 个样本**落在窗口之外**、代表**永远不会被派出的目标**，
把它用到窗口内是**外推**。

不过有一条实质结论保留：**先搞清「被打败」这个事件本身**
（战果 VICTORY/DRAW 连上去比对、降幅与什么成比例），
比继续拟那个指数更有价值。详见
[`军力被打败会崩-实测.md`](军力被打败会崩-实测.md) 第三节。

### 8.4 要攒到什么程度才回来重议

| 要什么 | 现在 | 够的判据 |
|---|---|---|
| **窗口内（0–6h）的龄跨度** | 0.11–4.91h，中位 0.98h，**绝大多数挤在 1h 以内** | 龄在 1h 以下 / 1–3h / 3–6h 三档**各 ≥ 30 发**，才谈得上在窗口内估斜率 |
| 带截距 vs 过原点 | 只在单日 n=31 上比过 | 两种在同一批 ≥ 100 发上比 |
| 出发点混杂 | 3 个出发点，`7:228:15` 是新的 | 分出发点各 ≥ 40 发，或在模型里带上出发点 |

⚠️ **龄挤在 1 小时以内不是巧合，是配置的必然结果**：军力榜采完就派，所以派出时
读数总是新的。**想要龄的跨度，只能靠「同一批读数被跨几轮反复使用」自然产生**，
或者故意留一批老读数去打——**后者是拿收益换数据，要用户点头才做。**

### 8.5 这期间排序保持不变

`attack_value` 继续是 `军力 ÷ 往返小时`，`score_max_age_hours` 继续由用户手动定。
2026-08-20 已核对：这一套**就是用户要的「按单位时间收益排序 + 手动定有效期」**，
没有需要改的地方（窗口未被放弃：4h 内 538 个 > 门限 300；`max_score` 只砍掉 2 个）。

**真正值钱的不在排序**：同一时刻 500 个新鲜读数里，**497 个是跨银河的**
（4 系 2 个、9 系 1 个、6 系 1 个）。而近目标每航线小时高 **56%**
（[`近弱还是远强-实测.md`](近弱还是远强-实测.md)）。⚠️ **先前把这归因为「扫描够不着」是不准确的**（2026-08-20 更正）：真正的机制是**我们自己打的**——打败 → 军力降 → 掉出全服榜前列 → 扫描再也读不到 → 被窗口筛掉，一个自我收紧的反馈环。**调大 `top_n` 只是把门槛往下推一格，治不了本。**

## 七、⚠️ 2026-08-18 落地了什么，以及**什么时候必须回来重新检验**

`top_n` 保留，但**只剩「窗口门限」这一个身份**（第三步「窗口内够不够用」的尺子），
不再决定打谁。`max_score` 保留作安全线。

代码：`domain/flight_time.py`（新）、`domain/target_order.py`、
`domain/military_attack.py`。

⚠️ 从前那句「军力和收获不相关」为什么站不住，已经写在第六节第 2 条里了
