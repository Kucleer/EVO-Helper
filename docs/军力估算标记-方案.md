## 一、这个字段是什么

**不是「大概齐」**，而是：这一行从榜上读到的分数**破坏了降序、被当作不可信丢掉**，
显示的数是用上下两个好邻居**插出来的中点**。

来自 2026-08-15 的事故（`tools/ranking_scan.py` 注释）：30 个 bot 的军力飞到 10 万以上
（最高 177 万），每一个除以 100 都精确落回正常区间——`17.73K` 读成 `1773K`，丢小数点。
`descending_breaks` 当时在报，**但只打印没据此丢**，于是 18 个错值进库、又经插值传染 12 个。

**当前规模：3225 个有读数的 bot 里，估算 365 个（11.3%）。** 不是罕见情况。

## 二、为什么必须快照，不能现取

这个标记**会被反复重写和清零**：

- 每轮采集覆盖（`repository.py` 的 upsert）
- `clear_pirate_position_bot_candidates` 清成 `False`
- `forget_implausible_military_scores` 清成 `False`（2026-08-18 跑过两次）

事后现取，今天标着估算的记录明天可能变成 `False`——**页面会声称那是实读，而那是假话**。

实证：`3:386:7 = 82,746（估算）`、`4:336:11 = 72,252（估算）` 在 2026-08-18 的清理里
被清掉，它们的 `estimated` 现在都是 `False`。

## 三、改法

| 层 | 改动 |
|---|---|
| 迁移 | `attack_intents` 加 `target_military_score_estimated`，**可空布尔**、无 `server_default` |
| ORM | `storage/models.py` 一列 |
| 快照 | `save_attack_intent` 里，和 #183 那两个字段**同一条 SELECT、同一个事务** |
| 视图 | `AttackLogView` 一个字段 |
| 显示 | 军力值后追加 `(估算)`，**不另开列** |

⚠️ **可空，不是 `default False`。** `False` 的含义是「这是实读的」，而历史行**根本不知道**。
默认成 `False` 等于让历史行冒充实读。

## 四、显示：复用军力榜已有的写法

`web/templates/rankings.html` 已有此约定：

```js
${r.score ?? '—'}${r.estimated ? ' <span class="muted">(估算)</span>' : ''}
```

照抄，追加在 #183 那个军力格里，和角标并存：`72,252 (估算) ⓘ`。

**为什么估算不并进角标**（用户选 A）：估算是**要一眼看见的警示**，快照时刻是**查的时候
才要的**。藏进 hover 等于默认用户不会去看。

## 五、⚠️ 它不是脏数据探测器

**别指望它替代任务参数里的「上限」。** 2026-08-18 的反例：

```
8:452:16  262,899  estimated=True    ← 脏
3:398:19  262,000  estimated=False   ← 一样脏，但是「实读」的
```

后者是榜单名次 4 的**真人玩家**被当成 bot 收进来，262,000 是真读到的——降序判据挑不出
它，因为它在那个位置上本来就该是大数。

**这个标记只回答「这个数是插出来的吗」，不回答「这个数对不对」。**
