# 军力榜补数问题 —— 方案 v2（据 review 重写）

> v1 提议「把 `score_history.clear()` 换成局部裁剪」。**该提议已撤回**，理由见第 1 节。
> 本版把重点从「改阀做什么」移到「先确认阀该不该响」，并新增两项 review 发现的独立缺陷。
> 背景（系统、判据流程、常量）见 v1 文档第 0–2 节，未变动。

---

## 1. v1 提议为什么撤回

三个理由，两个来自 review，一个是它的算术后果：

**(a) 切点取不到可信位置。** 提议用 `max(历史名次) - CURVE_RANK_SPAN` 作为切点。
但名次列本身有高位噪声（仓库里记着实机读到 `[4781]`、`996 = 1000−4` 这类），
一个错名次进了历史就把 `max()` 顶飞，这一刀会静默切掉整个历史。
备选的「用本屏修过的首名次」同样不可信：`repair_ranks` 在共识不足时**原样返回**，
错名次照样在里面（已核实，`domain/ranking.py:216`）。

**(b) 空历史会崩。** 清理后若一直没有新点，阀再次触发时 `max(())` 抛 `ValueError`。

**(c) 裁剪会留下结构上补不了的死带。** 补数要求两侧各两点且四点总跨度 ≤ 60。
旧段保留到名次 939、新段从 1020 起，中间的洞需要跨度 ≥ 81 —— 永远补不上。
每次触发留一条约 80 名的死带。

## 2. review 核实出来的三个既有缺陷（我已独立复核）

### ⚠️ 缺陷 A：阀检查的对象不是「判据采信了什么」

```python
fresh, reached_limit = collect(targets_from_rows(rows, ..., history=score_history))
if any(target.military_score is not None for target in fresh):
    blind_score_screens = 0        # 归零
else:
    blind_score_screens += 1       # 计数，够 2 就清锚点 + 清历史
```

`fresh` 是 `collect()` 的**返回值**，经过了插值、bot 过滤、**按坐标去重**
（`take_batch_targets`：`if target.coordinate in seen: continue`）。

于是两个方向都会错：

- **误触发**：一屏全是已见过的坐标（重叠区），`fresh` 必然为空 ——
  **OCR 再正确、历史再健康，计数器照样加一**。连着两屏就清历史。
- **漏触发**：判据一个值都没采信，但插值给新坐标填出了值 ——
  `fresh` 非空，计数器归零。

**这一条推翻了 v1 文档里的表述**（我写的是「连着 2 屏一个军力值都没采信」）。

**生产迹象**：一趟里阀响 5–8 次。我此前把它读成「发作频繁」，现在看很可能大部分是误触发。

### ⚠️ 缺陷 B：锚点走的是第二遍无曲线判定

```python
def next_score_anchor(rows, *, anchor):
    trusted = [value for value in screen_scores(rows, anchor=anchor) if value]
    return max(trusted) if trusted else anchor
```

`screen_scores` 不传 `history`、不传 `ranks` —— 它是一遍**不用曲线**的重判。
所以锚点不是本屏实际采信的那批值里的最大值，两遍可以给出不同结论。

构造例（review 提供，我认为成立）：健康曲线约 10,000，本屏读出 `[4000, 9990, 3980]`。
曲线只采信 9990；而无曲线那一遍用屏内首尾区间 `(3980, 4000)`，
反而采信 4000 和 3980、丢掉 9990 —— 交出锚点 **4000**。
曲线一旦不表态，这个错锚点就开始参与判定。

（同一个仓库在 #275 里刚写下「理由和参照只能取自 `verdict`，不允许重算」，
这里是同一类问题的另一处。）

### ⚠️ 缺陷 C：同趟内的重复观测被丢弃

```python
for target in targets:
    if target.coordinate in seen:
        continue                    # ← 后来读对的那一次，在这里被扔掉
    seen.add(target.coordinate)
    picked.append(target)
...
unread.extend(target for target in picked if target.military_score is None)
```

带 `military_score=None` 的目标**也会进 `seen`**，并进入 `unread`（等着被估算补）。
所以「先读空、后读对」时，后面那个**实测值**只进得了曲线历史，
**补不回目标本身** —— 那一行最终拿到的是估算值或空值。

相邻两屏重叠 3–6 行、一趟约 100 屏，**每趟有 300–600 次重复观测**。
其中「先空后有值」占多少未知 —— 这是下面 Phase 0 要量的第一件事。

## 3. 重新提出的核心假设

> **补数塌掉（补上率 100% → 25%）可能主要由阀的误触发造成，而不是由阀的动作造成。**

如果一趟里 5–8 次触发中大部分是缺陷 A 的误触发，那么**只修触发条件、
完全不动 `score_history.clear()`**，历史就能保住，补数自然恢复。

这个假设可证伪，且证伪成本很低（Phase 0）。

⚠️ **在它被验证之前，任何「改阀做什么」的方案都是在优化一次误触发。**
v1 提议正是如此。

---

## 4. 分阶段方案

### Phase 0 — 只加计数，不改任何行为

在采集循环里，每屏记一行结构化日志：

| 字段 | 含义 |
|---|---|
| `rows_read` | 本屏读出几行 |
| `judged_trusted` | 判据实际采信的**实测**值个数（`military_score` 非空且非估算） |
| `fresh_valued` | 去重后带值的新目标个数（= 阀现在看的那个数） |
| `dup_skipped` | 因坐标已见过而跳过的个数 |
| `dup_would_fill` | 其中「之前那次是空值、这次有实测值」的个数 |

同时给阀的触发日志补上 `judged_trusted`，好事后区分真触发 / 误触发。

**这一步回答两个问题**：

1. 阀的触发里有多少是缺陷 A 的误触发（比对 `judged_trusted` 与 `fresh_valued`）
2. 缺陷 C 的规模有多大（`dup_would_fill` 的每趟合计）

**风险**：只增加日志，不改判定、不改写库。唯一代价是日志量（每趟 +100 行）。

**验收**：跑满 4–5 趟后能给出上面两个数。不设通过/不通过 —— 这一步是量，不是改。

### Phase 1 — 按 Phase 0 的数据二选一（或都做，但分开提交）

**1a. 修阀的触发条件**（若误触发占比高）

```python
judged = targets_from_rows(rows, ..., history=score_history)
fresh, reached_limit = collect(judged)
# 阀改看 judged，而不是 fresh
if any(t.military_score is not None and not t.military_score_estimated for t in judged):
    blind_score_screens = 0
```

调用处本来就持有去重前的 `judged`（现在是内联传给 `collect`），
**不需要穿透 `targets_from_rows`，也不需要第二遍判定。**

⚠️ 这一改会让阀**响得更少**。若真发作时它响得不够，吸收态会回来 ——
所以必须同时保留 Phase 0 的连续失败长度统计（用真实的 `judged_trusted`，
而不是会被重置归零的那个计数器）。

**1b. 让重复观测补回目标**（若 `dup_would_fill` 规模可观）

在去重处：坐标已见过、且此前记录无值、而这次有**实测**值时，交出一条更新，
并把它从 `unread` 里移除。

⚠️ 只允许「空 → 实测」这一个方向。不许用估算值覆盖，不许用后读的值覆盖已有实测值
（避免把「后读的」当成「更对的」）。

### Phase 2 — 锚点改取自同一次判定

`next_score_anchor` 不再重判，改成取本屏 `Judgement.trusted` 里的最大正值。
**单独提交、单独验证**，避免与 Phase 1 的收益混在一起。

### Phase 3 — 逐屏回放语料，然后再谈裁剪

按屏记录**原始行**（名次、坐标、分数、空值）+ 屏序 + 配置 + 代码版本，
新旧算法各自从同一份原始输入重建历史。

⚠️ 不能用最终数据表重建：被丢的原始读数、屏序、重复观测、每次重置前的状态都已丢失。

有了回放才谈「阀该做什么」（裁剪 / 状态分离 / 其他）。
**按当前判断，如果 Phase 1a 成立，裁剪可能根本不需要。**

## 5. 验收口径（据 review 修正）

| 指标 | 怎么报 |
|---|---|
| 补数 | **分三个数**：曲线推得出、真正写入库、最终仍为空。分母固定为「本趟有名次但没读出军力值的行数」 |
| 估算准确率 | 与下一趟实测按**坐标**配对（不按名次）。报配对成功率、时间间隔。**必须报 P99 和最大偏差** —— 70% 落在 ±3% 内不限制另外 30% 能错多远 |
| 连续整屏全丢 | 用真实的 `judged_trusted`，**不用会被重置归零的计数器** |
| 丢弃率 | 降为诊断指标，不设上下界（下界会拒绝真正的改进） |
| **选靶影响** | 新增：按「军力 ÷ 往返小时」排序后**前列目标有没有变**；单独检查严重高估的尾部 |

**理由**：补数率是数据完整性收益，不等于产出收益。少量严重高估就可能污染选靶前列，
而那才是这条链路的真实目的。

---

## 6. 明确不做的事

- **不做 v1 的局部裁剪** —— 直到 Phase 1a 的结果出来
- **不做 `screen_consensus`（屏内共识否决曲线）** —— 已撤回，独立验证只有 58% 正确率（n=19）
- **不重写整条链路** —— 但也不再拿「改动行数少」当风险低的依据
