### 0.1 `written` 是逐屏落库的计数，不是补数的

v5 §3.2.4 写的是「`written` 来自 `backfill_missing_military_scores`」。**错了。**
代码里有两个同名变量：

```
 687:  written = int(repository.backfill_missing_military_scores(filled))   ← 局部
 698:  return written                                                       ← 调用处丢弃
1542:  written = 0                                                          ← 扫描级
1560:      written += len(targets)          （在 persist 闭包里）
1846:  completion_message(..., written=written, suspect=written - len(kept), ...)
```

收尾那句「逐屏写入 N 条，其中末屏可疑 M 条」用的是**扫描级**那个，
而 `suspect = written - len(kept)`。

**约束不变，理由换掉**：修复写入混进 `written` 会让 `suspect` 这个差值失真，甚至为负。

### 0.3 单调性只在逐屏成立，不在整趟成立

v5 §0.2 证明了 `success_old ⟹ success_verdict`（逐屏）。
但**回放轨迹在第一次被去掉的误重置之后就分叉了** —— 历史不同 → 后续采信不同 →
再往后的成功/失败序列都不同。

所以**不能由逐屏单调推出「整趟重置更少」**。5.1 删掉「重置总数下降」这条通过线的理由
应写成**「没有鉴别力」**，而不是「必然成立」。

### 0.4 0 分被采信有多难

v5 §0.1 用 `trusted = [0, None, 0]` 说明单调性边界。**该边界成立，但可达范围极窄**：

```python
basis = anchor if anchor else (statistics.median(positive) if positive else None)
too_small = basis is not None and score * cliff_factor < basis    # 0 * 5 < basis
```

0 要被采信，得同时满足：没有曲线参照、屏内区间框不住、**且 `basis` 为空**。
而 `basis` 取本屏正值的中位数 —— **只要屏里有任何一个可读正值，0 就被「偏小 5 倍」丢掉**。

改成「非 `None` 个数」仍然是对的（定义更稳），但**不要把它写成常见路径**。

## 1. Phase 0 —— 只观测，不改行为

### 1.0 第一步：行为中性重构

首屏现在**完全走在滚动循环之外**：不打「采集一屏」日志、没有 `dry`、
没有重叠判断、**不进阀的计数**。而且 `for extra in range(1, 0 if reached_limit else ...)`
在首屏就采够时一次都不跑 —— 那一趟一条逐屏日志都没有。

Phase 0 第一步把逐屏那段抽出来给首屏复用，**行为逐字不变**：

- 首屏记为 `screen_seq=0`，走同一套日志与影子计数
- ⚠️ **阀的实际更新加一道 `screen_seq > 0` 的闸**，保持现行为（见 6.1）

### 1.1 每屏计数（六个来源分开）

| 字段 | 取自 | 区分什么 |
|---|---|---|
| `verdict_trusted` | `Judgement.trusted` 里**非 `None`** 的个数 | 判据本身成没成功（**用于影子条件**） |
| `verdict_positive` | 其中**正值**个数 | 诊断用（与上一格相等是常态，见 0.4） |
| `history_appended` | 本屏实际追加进历史的记录数 | 名次缺失会让采信值进不了历史 |
| `history_new_ranks` | 其中**不同名次**的个数 | 历史不按名次去重 |
| `bot_measured` | 过滤后 bot 行里的实读值个数 | bot / 坐标过滤吃掉了多少 |
| `fresh_valued` | 去重后新增带值目标数（阀**现在**看的那个数） | 重复观测吃掉了多少 |

⚠️ 必须由**同一次判定**交出来。`targets_from_rows` 把它已经算出的统计带出来，
**不是重判**。理由：历史追加发生在 bot / 坐标过滤**之前**。

### 1.2 影子评估 —— 记「成功」，不是「触发」

三个**成功**条件，各自维护独立影子失败计数，**连续两次失败记一次假想重置后归零**：

| 名称 | 条件 |
|---|---|
| `success_old` | `any(t.military_score is not None for t in fresh)`（现行） |
| `success_verdict` | `verdict_trusted > 0` |
| `success_history` | `history_appended > 0` |

现行阀照旧生效；三个候选都只影子运行。

⚠️ 产出只是「三种条件在**现行运行轨迹**上的比较」。换条件后轨迹会分叉（见 0.3），
**不能把影子事件当成换条件后的真实重置集合** —— 那个只有 1.5 的回放能给。

### 1.3 ~~首选候选：`success_verdict`~~ —— ⚠️ **已被 Phase 0 的数据推翻，见 §1.8**

> **这一节留着是为了记住当时的推理错在哪，它不是现在的口径。**
> 实测结论在 §1.8：改用 `success_history`（`history_appended > 0`）。

当时的理由（**结论错了，前半段的反例本身仍然成立**）：

反例：连续两屏分数正常但**名次全部缺失** → `verdict_trusted > 0` 而 `history_appended = 0`。
按 `history` 条件会清掉此前健康的历史，**却修不了名次缺失**；
而重复名次又能持续追加，`history_appended > 0` 也不代表曲线在有效推进。

⚠️ **漏掉的那一半**：`Judgement.trusted` 把采信的 **0 分**也算进去，
于是 `verdict_trusted > 0` 也会把「这一屏采信了一堆 0」判成成功。
第 2 趟实测 13 屏里有 **11 屏**正是这样（真人段的分数读出来是 `0.0`）。
上面那个反例是真的，但它比不上这一个常见 —— 而两趟数据里
`history_appended` 与 `verdict_positive` **一个数都不差**，说明「名次全缺」
这个反例在这条链路上还没出现过。

**保证范围**：这道阀保护「**连续两屏没有任何值被采信**」这一类故障。
**不保证**解决局部污染，**不保证**解决历史停滞。

### 1.4 每次重置的上下文

每次重置记：屏序、重置前历史点数、当时 `unread` 规模、
**连续那两屏各自的 1.1 六个计数**。

每趟收尾另记：**最后一次重置在第几屏、收尾时历史多少点、补数三个数**。

### 1.5 逐屏原始输入采样

**开关的传递通路**（命令行方案在调度器一侧不可行）：

```
2835:  command = ranking_command(...)               ← 命令在这里就建好了
2879:  run_id = uuid4()                             ← run_id 之后才生成
2880:  with child_environment(run_id=run_id, ...)   ← 运行器靠环境变量认领
```

**两条入口，在扫描器内部汇成同一个变量**：

- **调度器** → 环境变量（`child_environment` 那条通路）
- **手工直跑** → 扫描入口的命令行参数（本机是备份挂机机，必须能开）

**请求的存放与消费**（答 v5 §7.1）：

- 存成**一张小表**，记请求时刻和消费它的 `run_id`；
  ⚠️ **不要**在任务参数里放布尔值
- 在**起子进程之前**用一条**原子语句读取并清除**
- ⚠️ **不要绑到 `begin_mission_run`** —— 它在子进程起来之后才跑
- 子进程起不来时请求被白白消费掉，用户再点一次即可。
  这个失败方向比「多采一趟」便宜，且没有崩溃窗口
- 附带好处：完整性检查里的「生效配置」能直接对出这批语料是哪次请求采的

**内容**：开启时在「采集一屏」的 payload 里附带本屏**原始行数组**（名次、坐标、分数、空值，保留行序）。

**初始状态就地记录**（取代整体快照）：
在每屏落库**之前**，把本屏**首次出现**的坐标当时的库内状态记进同一条日志：
有没有行、军力值、估算标记、拉黑时刻。

> 为什么不用整体快照：拉黑判断走的是**按坐标查单行** ——
> 一个坐标没被本趟观测到，它拉不拉黑对回放没有任何影响。
> 就地记录还让语料自带初始状态，回放能验到「已有值 / 不可更新」那几档。

⚠️ **这不是零成本**（v5 说「成本不变」不准确）：逐屏落库那个闭包现在**不返回任何东西**
（`persist` 只做 `save_ranking_targets` 然后 `written += len(targets)`）。
要拿到落库前的状态，得让它返回逐坐标先前状态，或者在落库前多读一次。
**都很便宜、且只在开关打开时执行，但这是一处契约改动。**

**完整性检查**（缺任何一项 → 该批语料标为不完整，不得用于验收）：

1. **首屏记为 `screen_seq=0`**；其后屏序连续、不重复；**空屏也必须记录**
2. **离页那一屏**（现在是 `break` 在算日志之前）必须补一条带**结束原因**的记录
3. 原始行数组长度与 `rows_read` 一致，行序与空值原样保留
4. 同一 `run_id` 下有开始记录、生效配置（含请求来源）、**版本标识**、结束记录；
   结束记录说明：正常完成 / 达到上限 / 取消 / 异常 / 离页，以及**是否执行了收尾补数**
5. 收尾记录的总屏数、总行数与实际收到的语料一致；**缺结束记录的批次标为不完整**
6. **先用原版本回放**，复现采信统计、重置位置、收尾结果，再比较候选版本

⚠️ **版本标识**：运行机上不一定拿得到 git sha，**至少记 `SCORE_RULE_VERSION` 与包版本**。

**采样覆盖**：首批 4–5 趟，必须覆盖 —— 正常趟、含重置的趟、含重复观测修复机会的趟。
未覆盖的情形用**构造用例**补，**不得声称「生产已验证」**。

⚠️⚠️ **手工跑拿不到 run_id，而且不许自己编一个。**
`system_log.run_id` 有指向 `mission_runs` 的外键：`EVO_HELPER_LOG_RUN_ID` 设成一个
不存在的 UUID，落库时**整趟的日志会被外键全部拒掉**（只在 stdout 留一句

所以手工跑只有两条路：

1. 不设那个变量，落库 `run_id = NULL`，**按时间窗**捞语料
   （`ranking_replay <run_id>` 走不通，得另写取数）；
2. 走调度器，让它自己开 `mission_runs` 行并领取采样请求
   （`ranking_capture_requests`）—— 这才是 `ranking_replay` 设计时的正路。

⚠️ 另外：**后台跑不要把 stdout 接进 `tail`。** 管道会缓冲到进程结束，
中途一个字看不到，而进程被别的原因掐掉时那一段就彻底没了。

### 1.8 ⚠️⚠️ Phase 0 推翻了 §1.3 的首选：`success_verdict` 不能用

第 2 趟（2026-09-06 22:12–22:14）盲滚校准漂了（每格实测 0.724 行 vs 标定 1.08，
补拨 4 轮），停在第 693 名就宣布「到达 bot 区」，于是 13 屏全在**真人段**、
`bot_measured` 全 0、一行都没写库。这一趟对补数问题没有价值，
**但它把两个候选条件分开了** —— 第 1 趟做不到这件事。

| | 第 1 趟（bot 区，215 屏） | 第 2 趟（真人段，13 屏） |
|---|---|---|
| `verdict_trusted` > 0 的屏 | 212 / 215（合计 2071） | **13 / 13**（合计 41） |
| `verdict_positive` > 0 的屏 | 212 / 215（合计 2071） | **2 / 13**（合计 2） |
| `history_appended` > 0 的屏 | 212 / 215（合计 2071） | 2 / 13（合计 2） |
| 「采信了值但一个正数都没有」的屏 | 0 屏 | **11 屏** |

真人段那些行的分数读出来是 **`0.0`**（`Athena47 → 0.0`、`Isi02 → 0.0`……），
而 `Judgement.trusted` 把采信的 0 也算进去。于是：

> **`success_verdict`（`verdict_trusted > 0`）会把「这一屏采信了一堆 0」判成成功。**

那不是「判据在正常工作」，那是判据接受了一批没有用的读数。
第 1 趟看不出这件事，因为在 bot 区 0 分几乎不会被采信（`verdict_trusted` 与
`verdict_positive` 在 215 屏上**一个数都不差**，都是 2071）。

#### 结论：改用 `success_history`（`history_appended > 0`）

两趟数据上 `history_appended` 与 `verdict_positive` **完全相等** ——
说明现行代码里「进曲线历史」的条件本来就是「采信且为正」。两者今天等价，
而 `history_appended` 和阀要回答的问题对得更死：

> 自愈阀存在的理由是「历史被毒了、判据在拿错参照丢整屏」时能自己脱身。
> 那么「还在不在往历史里进真点」就是最直接的健康信号。

⚠️ **`verdict_positive > 0` 是同样正确的写法**，只是绕一层。选 `history_appended`
是因为它就是那个量本身；如果日后「进历史」的条件变了（比如加名次合理性闸，
见 §7.3），这个条件会跟着一起变 —— 那正是想要的。

⚠️ **别把这条读成「0 分该被判据拦下」。** 那是 §7.1 单独记过的另一件事，
不在本方案范围内。这里只是不许拿「采信过东西」当健康信号。

### 1.9 配对回放的结果 —— 第 1 趟

| 条件 | 重置 | 收尾历史 | 待补的洞 | 重置位置 |

## 3. ~~Phase 1b —— 重复观测补回目标~~ —— ⚠️ **Phase 0 之后不做了**

> **撤掉的理由（§1.7 交付物 3）**：第 1 趟 78 个洞里，重复观测修得上 38 个，
> 但其中 **30 个曲线补数本来就补得上** —— 1b 的**净增量只有 8 个洞**，
> 占那一趟 1506 行的 **0.5%**。而它要新建一整套仓储契约（§3.3）：
> 只更新现存、未拉黑、仍为空的目标，写实测值而非估算值，返回逐坐标结果，
> 修复写入还不许计入 `written`。收益和风险完全不成比例。
>
> ⚠️ **重复观测这条线索本身没有白挖** —— 它挖出了 §7.3
> （曲线补数给「名次读错」的行补错值），那件事便宜得多也值钱得多。
>
> 下面整节留着不删：万一日后洞的构成变了（比如 §7.3 修完之后曲线补得上的
> 比例下降），这一节的状态规则和约束**照样成立**，不用重新想一遍。


### 3.1 状态规则（本趟内，按坐标）

| 观测序列 | 应有结果 |
|---|---|
| 空 → 空 → 实读 A | 补入 A |
| 空 → 估算 → 实读 A | 估算不更新；随后补入 A |
| 空 → 实读 A → 实读 B → 空 | 保留 A；后续不覆盖、不重新进入 `unread` |
| 首次已有实读或估算 | 保持原值（本次只补空） |

⚠️ 第三行的最后一步**现有去重已经保证**（`unread` 只从 `picked` 来，
而已见坐标进不了 `picked`）——**不需要额外代码，但要有用例锁住**。

### 3.2 约束

1. **潜在收益按不同坐标计数。** 「空→实读A→实读B」只算**一个**可修复目标。
2. **修复更新不许混进 `fresh`。** 否则会改变新增计数、连续空屏数和停扫行为。
3. **达到 `bot_limit` 后**：可处理**本屏已读到的**修复机会，不新增目标、不额外滚屏。
4. **修复写入不许计入 `written`。** `written` 是**逐屏落库**的计数（`persist` 里累加），
   而收尾那句用 `suspect = written - len(kept)` 算「末屏可疑几条」——
   混进去会让这个差值失真甚至为负。
5. **名次照现有补数的做法**：只在原来为空时补，不覆盖。

### 3.3 新的仓储契约

现有两个都不能用：`backfill_missing_military_scores()` 写死 `military_score_estimated = True`；
`save_ranking_targets()` 无条件覆盖。

> **只更新现存、未拉黑、且更新时仍为空的目标；不创建新行；
> 写入实测值（非估算）、用本次观测时间；返回逐坐标处理结果。**

| 逐坐标结果 | `unread` 的处置 |
|---|---|
| 写入成功 | 移出 |
| 已有值 | 移出 |
| 不可更新（**已拉黑**；「不存在」见下） | 移出，且**不得再进入曲线补数** |
| 失败 | **保留**，不得当作成功 |

⚠️ **「不存在」这一档实际不可达**：逐屏落库会为所有非拉黑坐标建行，
而拉黑行必然已存在。**保留为防御性分支即可**，不必为它设计流程。

## 5. 验收条件

**基线口径**：所有「不降 / 改善」都必须与**旧版本在同一份语料、同一共同集上**的结果比。
⚠️ 不得拿历史总体数（如 73%）当共同集基线。

### 5.1 Phase 1a

| 项 | 通过线 |
|---|---|
| 连续失败保护 | 独立计数（不用会被重置归零的那个）；**用构造序列验证能恢复** |
| 最后一次重置位置 | **不前移** |
| 收尾历史规模 | **不下降**，且**至少在一趟含误重置的语料上上升** |
| 补数 | 分三个数报：曲线推得出 / 真正写入 / 最终仍为空 |

⚠️ **「位置后移」不能当硬线**：若最后一次重置在两个版本里都是**真实触发**，
位置不变才是正确结果，写成「后移」会把正确结果判成不通过。

⚠️ **删掉「重置总数下降」的理由是「没有鉴别力」，不是「必然成立」** ——
轨迹在第一次被去掉的误重置之后就分叉了（见 0.3）。

### 5.2 Phase 1b

⚠️ **不要求「最终缺值必须下降」** —— 旧流程估算 9500、新流程实读补 9800 时缺值都是 0，
但 1b 确实做了有效修复。

| 项 | 通过线 |
|---|---|
| 最终缺值 | **不增加** |
| 实读修复数 | 有合格机会时**必须增加**；**单列**，不并入曲线补数率 |
| 状态表符合性 | 数值、估算标记、时间戳、不覆盖行为逐条符合 3.1 |
| 仓储结果 | 四种结果与 `unread` 的处置逐条符合 3.3 |
| `written` / `suspect` | `written` 不含修复写入；`suspect` 仍等于「末屏可疑数」 |

### 5.3 估算质量（1a / 1b / 2 通用）

| 项 | 通过线 |
|---|---|
| 共同可补集准确率 | 相对**同一共同集上的旧版结果**下降 ≤ 2 个百分点 |
| 新增可补集准确率 | ≥ 共同集旧版结果 − 5 个百分点 |
| 严重高估 | 定义：估算值 > 真值 × 1.5。新增集里占比 ≤ 2%，且绝对条数不增加 |
| 误差尾部 | P99 用绝对相对误差；**另报高估方向的尾部**；样本量与无法配对比例同报 |
| 配对方式 | 按**坐标**配对，报配对成功率与时间间隔 |
| **配对排除** | 剔除**跨周一 UTC+0** 的配对（bot 军力每周一刷新）、剔除**两次观测之间有攻击记录**的配对（平局会削弱军力）；**报剔除比例** |

### 5.4 选靶影响

不只报「前列变了没有」—— **新进入前列的目标必须逐个检查有没有被严重高估**。

### 5.5 回放与单测的分工（答 v5 §7.2）

- **回放用的假仓储确定性地成功**，用途是复现生产轨迹
- **「失败必须保留」那一档用单测注入失败来验**，不靠回放 ——
  生产语料里本来也不会有写入失败的样本

### 5.6 诊断指标（不设上下界）

丢弃率、各理由占比、曲线覆盖行数、`verdict_positive` 与 `verdict_trusted` 的差。

## 7. 记一笔：本方案范围之外的几件事

### 7.1 名次 821 的 0 分不是该修的问题（答 v5 §7.3）

榜单按军力降序，**821 名夹在九千多的行中间读出 0，不可能是真值** ——
是 OCR 或渲染层的产物。判据把它丢掉是**正确行为**，
`is_bot_entry`（要求军力不等于 0）也不会让它成为目标。记一笔即可。

### 7.2 ⚠️ 已有缺陷：收尾补数缺拉黑保护

逐屏落库跳过拉黑行（`save_ranking_targets` 里 `if target.blacklisted_at_utc is not None: continue`），
但**收尾曲线补数没有这道检查**：

```python
target = _bot_target_for(session, record.coordinate)
if target is None or target.military_score is not None:
    continue                      # ← 只查了「存在」和「已有值」
target.military_score = record.military_score
target.military_score_estimated = True
```

所以拉黑坐标照样会进 `unread`，**拉黑时军力为空的行会被写进一个估算值**。

与本方案无关，**单独处理**。但实施 1b 时，把拉黑保护做成**两个入口共用的判断**更稳。

### 7.3 ⚠️⚠️ 新发现的缺陷：收尾补数会给「名次读错」的行补出一个看起来合理的错值

拿第 1 趟里 30 个「重复观测和曲线都补得上」的洞，把实测的重复读数当真值去核曲线估算：

- |误差| 中位 **0.07%**、90 分位 10.67%、最大 17.55%
- |误差| > 3%（判据容差）的只有 **4 个**
- **那 4 个全部是名次本身读错的行**：

| 坐标 | 成洞那屏读到的名次 | 曲线估算 | 采信那屏的名次 | 实测 | 误差 |
|---|---|---|---|---|---|
| 5:457:13 | **12** | 3632 | 1812 | 3090 | +17.55% |
| 8:420:19 | **27** | 5292 | 1127 | 4780 | +10.72% |
| 8:437:14 | **28** | 5290 | 1128 | 4780 | +10.67% |
| 3:132:20 | **29** | 5290 | 1129 | 4780 | +10.67% |

全是**丢掉了前面的数字**（1812→12、1127→27、1128→28、1129→29）。
反过来说：|误差| ≤ 3% 的 26 个里曲线估算**极准**（中位 0.07%），
所以问题不在曲线，在**喂给曲线的名次**。

#### 为什么补数没拦住

两条凑在一起：

1. **历史里就有读错的名次。** 这一趟历史点的名次范围是 **-4 .. 2536** ——
   连负名次都被判据采信进了曲线历史（读到的名次原始范围是 0 .. 18339）。
   于是名次 12 / 27 / 28 / 29 的 ±60 内也凑得够 4 个点。
2. **补数那一步的密度闸是刻意关着的**（`_backfill_from_the_curve` 里那句
   「`CURVE_MAX_GAP` 在这一步先不加 —— 待定的取舍，不是忘了」）。

结果就是补出一个看起来完全合理、实际错 10–17% 的估算值，写进库、进选靶。

#### 根因

**判据只管军力值可不可信，从来没有人管名次可不可信。**
`renderable_score` / `curve_reference` / 区间 / 降序全是对**分数**的检查；
名次是 OCR 读出来就直接用的。

#### 为什么它该排在 1b 前面

1b 净补 8 个洞（占全趟 0.5%）、要新建一套仓储契约；
这一个拦住 4 个错值**并且**挡住那些名次进曲线历史（那才是 §1.7 里
「曲线参照算错→整屏丢掉」的一部分燃料）。收益大、改动小。

#### 候选做法（未定）

1. **补数这一步给 `military_rank` 加合理性闸** —— 名次要落在这一趟读到的名次区间内、
   且和同屏邻行连续。改动最小，只影响补数，不动判据行为。
2. **`judge_scores` 追点进历史前先查名次合理性** —— 治根，但会改判据行为，
   要单独一趟观测，不许和 1a 同时改。

⚠️ **先别实现。** 等第 2、3 趟确认这类行的比例；只有一趟数据不足以定闸的口径。
