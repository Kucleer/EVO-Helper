# 军力榜补数问题 —— 方案与历稿

## 一句话背景

`#276` 给军力榜的自愈阀加了 `score_history.clear()`，止住了「曲线历史被毒 → 整屏全丢 →
新点进不来」的吸收态，**但同时把收尾补数的证据也销毁了**：

```
curve/1 时代   544 个洞补上 544 个（100%），每趟 0 行最后没值
2026-09-05     1050 个洞补上 260 个（25%），平均每趟 53 行最后没值
```

这一组文档是修这件事的方案，以及**五次外部 review 之间的历稿**。

## ⚠️ 历稿为什么留着

**每一稿都是被证据推翻的，而推翻它的理由本身就是这条链路的知识。**
只看当前那一版会以为方案一直是这样，从而重犯同样的错：

| 稿 | 提议 | 被什么推翻 |
|---|---|---|
| v1 | 把 `score_history.clear()` 换成「切掉最近 60 名的历史」 | 切点取不到可信位置（名次列本身有高位噪声，`repair_ranks` 共识不足时原样返回错名次）；空历史时 `max()` 崩；裁剪会留下跨度 > 60 的**结构性死带**，那一段永远补不了 |
| v2 | 从 `targets_from_rows()` 返回值统计「判据采信了多少」 | 历史追加发生在 **bot / 坐标过滤之前**，返回值取不到完整判据结果 |
| v3 | 影子条件命名为 `trigger_*` | 命名把语义写反了：`verdict_trusted > 0` 是**清零失败计数**，与「触发」相反 |
| v4 | 诊断开关走命令行参数、沿用调度器生成 `run_id` 的位置 | `command` 在 `run_id` **之前**就构建完了，而运行器靠**环境变量**认领 run_id —— 两句话在代码里对不上 |
| v5 | 「修复写入不许计入 `written`」的理由说成「`written` 来自曲线补数」 | 代码里有**两个同名 `written`**：补数那个的返回值在调用处被丢弃，收尾用的是**逐屏落库**的计数，且 `suspect = written - len(kept)` |

另外两条一直没变、也一直成立的判断：

- **判定与补数共用一份历史**，暂时保留。若修完误触发后**真实重置**仍主导历史损失，再评估分离
- `screen_consensus`（用屏内共识否决曲线参照）**已撤回** —— 独立验证只有 58% 正确率（n=19），
  低于当时的现状 73%
