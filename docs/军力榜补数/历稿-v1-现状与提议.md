# 军力榜补数被自愈阀打残 —— 现状与修复方案（求 review）

## 0. 系统背景

一个浏览器游戏的自动化机器人。其中一条链路是**扫描军事排行榜**：

- 每小时跑一趟，滚动约 100 屏，每屏读 11–14 行，一趟读出约 1,250 行
- 每行包含：名次、玩家名（可反解出星球坐标）、军力值
- 榜单按军力**降序**排列，覆盖名次 0–1650
- **相邻名次的军力只差 0.08%–0.28%**（挤得极紧）
- 军力值用于选攻击目标（排序判据 = 军力 ÷ 往返飞行小时）

读数来自 OCR，游戏把军力渲染成 `10.81K` / `9.5K`（最多两位小数，末尾 0 省略），
所以 **1000 以上的值必然是 10 的整数倍**。

**观测到的三类误读**（生产实测）：

| 形态 | 例子 | 倍率 |
|---|---|---|
| 首位被换成小数字 | `9.83K` → `3.81K` / `5.81K` | ×0.3–0.6 |
| 多插一位 | `9.78K` → `93.78K` | ×10 |
| 丢小数点 | `7.19K` → `716.00K` | ×100 |

误读是**发作式**的：某一段连着 20 屏里约 30–50% 的行被读错，然后又连着 20 屏干净。
同一个名次每次读出来的错值都不一样（15 趟里某个名次读出过 15 个不同的值），
所以不是「某些行天生读不出」。

---

## 1. 当前判据（`domain/ranking.py`）

对每一屏的读数逐行判定，交出「可信 / 不可信 + 理由」。判定是**严格的前向单程**：
一屏判完才把采信的值追加进历史。

```
对每一行：
  1. renderable_score 预筛：≥1000 且不是 10 的整数倍 → 直接丢（游戏渲染不出）
  2. 曲线参照 curve_reference(history, rank)：
       - 取名次最近的 4 个历史点（span 60 以内，允许单侧）
       - 窗口内最大空洞 > 4 → 不表态
       - Theil–Sen：两两斜率取中位数，据此反推截距再取中位数
       - 参照必须 > 0，且与窗口自身水平相差不超过 5 倍，否则不表态
  3. 有参照 → |读数/参照 - 1| > 3% 就丢
     没参照 → 落回三条兜底：
         屏内首尾区间（首尾能框住这一屏时用它）
         逐行降序（比屏内上一个可信值大就丢）
         断崖：与基准（上一屏最后一个可信值）相差 5 倍以上就丢
```

常量：`CURVE_TOLERANCE=0.03`、`CURVE_FIT_POINTS=4`、`CURVE_RANK_SPAN=60`、
`CURVE_MAX_GAP=4`、`SCORE_CLIFF_FACTOR=5.0`。

**`score_history`** 是一个 `list[tuple[名次, 军力]]`，只有被采信的读数才追加进去。

---

## 2. `score_history` 有两个消费者

**消费者 A —— 边扫边判**（上面第 2 步）。需要它**不被毒**：
一个错读进了历史，Theil–Sen 的窗口只有 4 个点，坏 2 个就到一半，斜率中位数当场跑飞。

**消费者 B —— 整趟收尾的补数**（`_backfill_from_the_curve`）。
这一趟读到名次却没读出军力值的行，用同一条曲线推算填上（标记为估算值）。
它要求**两侧各有点**（防止往扫描末端外推），需要历史**尽量完整**。

```python
# 收尾时
_backfill_from_the_curve(repository, unread, history=score_history)
```

---

## 3. 自愈阀，以及它造成的问题

### 阀的由来

曾经出现过**吸收态**：历史被毒 → 参照错 → 整屏全丢 → 一个新点也进不了历史 →
下一屏还是同一批坏点。生产实测连着 10 屏，参照一路跑到 **-48,203**，
那一趟 302 个被丢行里 101 行（33%）出自这一段。

于是加了这道阀（`tools/ranking_scan.py`）：

```python
if any(target.military_score is not None for target in fresh):
    blind_score_screens = 0
else:
    blind_score_screens += 1
    if blind_score_screens >= SCORE_ANCHOR_RESET_SCREENS:   # = 2
        say(f"⚠️ 连着 {blind_score_screens} 屏一个军力值都没采信…锚点和历史一起撤掉重新起头")
        score_anchor = None
        score_history.clear()          # ← 问题在这一行
        blind_score_screens = 0
```

阀确实止住了吸收态：连续整屏全丢从「10 屏」降到「最长 2 屏」。

### 代价

`score_history.clear()` 把**消费者 B 的证据也销毁了**。生产数据（2026-09-05，14 趟）：

```
时刻     洞    补上   推不出   收尾时的历史点数
01:07    63    19     44      850
02:07    79    38     41      913
03:15    97     0     97       24     ← 收尾前刚清过
05:37    53    32     21      858
10:43   105    10     95      373
13:53    71     4     67      263
14:53    80     5     75      293
16:59    73     9     64      494

今天合计 1050 个洞，补上 260（25%），平均每趟 53 行最后没值
```

**历史 850+ 的趟补上率 30–60%，历史 <500 的趟基本补不上。**

对照阀存在之前（`curve/1` 时代，15 趟）：**544 个洞补上 544 个（100%），每趟 0 行没值**。

### 其他指标（供判断这个改动值不值）

```
丢弃率        今天中位 12.0%（9.8–14.4%），与 curve/1 的 11.5% 基本持平
被丢的理由     偏离曲线 80%、渲染不出 8.9%、兜底判据合计 7.5%
补数估算准不准  和下一趟的实测值比：73% 落在 ±3% 内，中位偏 1.62%
噪声底        同两趟之间 实测 vs 实测：92% 落在 ±3% 内，中位偏 1.37%
```

## 4. 提议的修改

**观察：毒是局部的。** 它是发作那几屏采信进去的点，名次都挨着当前扫描位置。
而 `curve_reference` 取的是**按名次最近的 4 个点**——所以只要有一屏新点进来，
它们名次更近，会自动把毒点挤出窗口。**历史会自己变干净，不需要销毁。**

所以阀不该「全忘」，只需要「忘掉曲线现在看得见的那一段」：

```python
# 现在
score_history.clear()

# 提议
cut = max(r for r, _ in score_history) - CURVE_RANK_SPAN
score_history[:] = [p for p in score_history if p[0] < cut]
```

**为什么这样能断环**：切完之后，下一屏要判的名次在 `span` 60 以内一个历史点都没有
→ `curve_reference` 交 `None` → 落回区间/锚点判据 → 采信出新点 → 环断了。
效果与全清一致。

**为什么代价小得多**：只丢掉末尾约 60 个名次范围内的点，名次更低的那 800 多个点
全部留着，消费者 B 的证据不再被销毁。

不加参数、不加常量、不加判据，一行改动。

## 5. 考虑过并否决的方案

### 方案甲：拆成两个 list（判定用的会被清 / 只追加的给补数用）

**否决理由**：只追加的那份会保留全部毒点，而**洞最密的地方正是中毒最重的那一段**。
补数覆盖率会上去，准确率会下来——用一个在测的数换一个没在测的数。

### 方案乙：阀触发后「跳过曲线一屏」，不动历史

**否决理由**：实现上是给那一屏传 `history=None`，而**追加也在同一个判断里**
（`if history is not None: history.append(...)`）。于是那一屏的新点也进不了历史，
环没断，只是换了个形状。要做得给判据加一个 `use_curve` 参数——比切一刀更大。

## 6. 已知风险与不确定的地方

**风险 1（我认为是这个方案最大的问题）：`max(r for r, _ in score_history)` 会被错读的名次污染。**

名次本身也会被读错（生产上见过深处的行被读成名次 5、也见过 11,200 这种）。
如果一个错到离谱的名次进了历史，`max()` 就被它顶到天上，`cut` 跟着飞，
**这一刀会把几乎整个历史切掉**——退化成现在的全清，甚至更糟（静默地）。

可选的更稳形式：

- (a) 用**当前这一屏修过的首个名次**（`repair_ranks(...)[0]`）而不是历史里的 max。
  调用处拿得到 `rows`，但要多几行代码。
- (b) 用历史里名次的**高分位数**（如 P95）而不是 max。
- (c) 保留 max，但对 `cut` 加一个下界（例如不许切掉超过一半的历史点）。

我倾向 (a)，因为它用的是「当前扫到哪儿」这个事实，而不是从可能被污染的数据里推。
但我没有强证据，这是想请 review 的第一个点。

**风险 2：保留下来的历史里可能仍有更早发作留下的毒点。**
补数的覆盖率一定上升，**准确率会怎样我不知道**。现在是 73%（±3% 内），可能升可能降。

**风险 3：切掉的 60 个名次范围里也有好点。**
它们本来能给补数用。这是断环必须付的代价，但没有量过具体损失多少。

## 7. 上线前的停止条件（先定，达不到就不上）

| 指标 | 现在 | 要求 |
|---|---|---|
| 补数补上率 | 25% | **≥50%** |
| 估算准确率（与下一趟实测比，±3% 内） | 73% | **≥70%，不许降** |
| 连续整屏全丢的最长长度 | 2 屏 | **不许出现 ≥4 屏** |
| 丢弃率 | 9.8–14.4% | **不许超出这个区间** |

**第 2 条不达标就不上线，不管第 1 条多好看。**

目前**测不了第 2 条**：数据表每个坐标只保留最新值，跨趟对比需要快照。
计划是先在本地按趟存快照（不碰生产），攒 4–5 趟拿到精确基线，
再实现改动、用快照做离线回放，回放通过才提 PR。

这次提议的改动同样落在耦合处，所以最想请 review 的是**它还耦合着什么我没看见的**。
