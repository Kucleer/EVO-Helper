## 2. 第 ① 件：切出发星球「拖回顶部」换滚轮

### 2.1 调研数据

一次切换 **46.0s**（88 次实测，中位 47.5s，最大 60.9s）：

| 子步骤 | 均 | 中位 | 是什么 |
|---|---|---|---|
| 起点 → 拖到顶 | **22.1s** | 19.5s | 拖 2.4 次，每次 ≈ 9s |
| 拖到顶 → 找到并点 | 5.6s | 5.5s | 一次面板 OCR + 算点位 + 点击 |
| 找到并点 → 起点回读 | 10.7s | 10.7s | 等游戏切星球 + 读回当前星球 |
| 起点回读 → 导航栏回读 | 7.6s | 7.6s | 从导航栏再确认一遍坐标 |

拖动次数 **{1 次: 38 趟, 2 次: 12 趟, 4 次: 39 趟}**，上界
`PLANET_LIST_TO_TOP_MAX_DRAGS = 6` 一次没走满 —— 那 4 次是真需要。

### 2.2 三条「不能这么省」

**a. 整段省不掉。** 233 次切换里只有 19 次（8.2%）与上一趟同颗。7 颗出发星球
（`8:117:6` 45 / `5:261:8` 43 / `1:55:6` 42 / `2:391:16` 30 / `7:228:15` 29 /
`4:277:15` 29 / `9:250:8` 15）轮着用，**92% 是真换**。

**b. 两次回读都不该删。** `起点回读` 是点击有没有落空的唯一凭据（点位按
「这一屏在 y=650 读到 X」算出来，会偏）；`导航栏回读` 有第二个用途 —— 日志原话
「同银河的下一个目标少设 1–2 个字段」，它缓存导航栏状态，后面每个同银河目标的
`goto` 都因此更快。

**c. 「先读当前屏、命中就不拖」不做。** 目标落在「到顶那一屏」上的命中率只有
**37.1%**（86/232），只能覆盖约 1/3 的趟，而要新写一条分支。滚轮方案覆盖同一块开销。

### 2.3 为什么滚轮在这一处成立

`game/human_input.py` 的 `drag()` 上有 2026-08-22 的实测（原始数据在
`docs/军力榜翻页-滚轮实测.md`）：

    滚轮（单格 dwData=±120、16ms 间隔连拨）：19–23 行/秒
    慢拖：                                1.73 行/秒        ≈ 11 倍

同一段注释写着**为什么默认仍然是拖**：

> 滚轮有速度惯性，会把列表停在**非整行位置**（实测偏离标定网格约 12px），
> 而 `vision` 那边是逐行裁剪的——偏了就横跨两行，名字全糊。

**「拖回顶部」恰好是这条约束不成立的那一处，两条理由都要成立：**

1. **过冲无害。** 军力榜滚过头的代价是静默漏采；而往上滚过头**物理上不可能** ——
   列表到顶被夹住。
2. **到顶就是网格原点。** 「非整行位置」的根源是停在任意偏移上；被夹在顶部时
   偏移为 0，也就是标定网格的原点，所以到顶那一屏照样读得清。

⚠️ **第 2 条是推理，不是实测** —— 见 §2.6，它是这次改动唯一必须上实机量一次的东西。

### 2.4 回应 review ①：方向与落点（v1 在这里是错的）

v1 说「`LiveDriver.wheel_notch()` 已经有了，不用动」。**核实后：错。**

    src/evo_helper/tools/scan_coordinates.py:865
        pyautogui.scroll(-WHEEL_DELTA)      # 写死向下

照 v1 复用会**往下滚到底**，而底部同样会被夹住 → 两屏坐标相同 →
`reached_top` 误判「到顶」→ 之后 `_locate` 在列表末尾找上方的目标，**找不到**。
这一条 review 说得完全对。

而且 `wheel_notch()` **不移动鼠标**。滚轮事件落在指针当下所在的窗口/控件上，
所以拨之前必须先把指针放进列表面板 —— 落点原语是现成的
`LiveDriver.hover(x, y)`（`scan_coordinates.py:800`），军力榜盲滚也是这么落点的
（`ranking_nav` 那条协议上写着「盲滚之前用它落点」）。

**改法**：`wheel_notch()` 加方向。两种形状选一个：

- `wheel_notch(*, up: bool = False)` —— 一个方法带方向
- 另加 `wheel_notch_up()` —— 两个方法

⚠️ 倾向**前者**：`WHEEL_DELTA` 的符号只有一处，写两个方法就有两处会各自漂。
但**协议上仍然只暴露「一格」这一种粒度** —— `ranking_nav.wheel_notch` 的注释里
写着理由：允许传格数的话，实现里迟早把 N 格合成一个大事件发出去，而那会被游戏
静默封顶（实测 800 格只走 14px）。**这条约束不许因为加方向而松掉。**

⚠️ 还有一处不许碰：`wheel_notch` 里那段 `pyautogui.PAUSE` 的存档/恢复
（2026-08-22 生产事故：裸的全局赋值让同进程后面所有 pyautogui 调用都没了停顿）。
加方向时连着这段一起保留。

### 2.5 方案

**把 `_scroll_to_top()` 的单次动作从慢拖换成「先 hover 进列表，再向上连拨 K 格」。
判据和上界都不动。**

    现在：for drag in range(6):   读一屏 → reached_top? → _drag_back_once()
    改后：for round in range(6):  读一屏 → reached_top? → hover + 向上连拨 K 格

- 判据仍是 `domain.planet_switch.reached_top`（这一屏的坐标序列和上一屏一样）——
  **一个字不改**：它比的是读出来的内容，与用什么手段滚动无关。
- 上界仍保留，走满仍**不许说「已经在顶部」**（`_say_scroll_to_top_gave_up` 的口径不动）。
- `K` 是新标定常量，取值让「一轮 ≈ 一屏多一点」。拨太多不会出错（到顶被夹住，
  两屏都读到顶、判据照样成立），所以**宁可偏大**。

| 文件 | 改什么 |
|---|---|
| `tools/scan_coordinates.py` | `LiveDriver.wheel_notch` 加方向（保留 `PAUSE` 存恢复） |
| `game/planet_list.py` | `PlanetListDriver` 协议加 `wheel_notch` + `hover` |
| `game/planet_list.py` | `_scroll_to_top` 里 `_drag_back_once` → hover + 向上连拨 |
| `game/pirate_ui.py` | 新常量：每轮格数 K、格间隔、拨完的沉降等待、hover 落点 |

⚠️ **只改「往回拖到顶」这一处。** `_locate` 里的 `_drag_once`（往下找目标）
**一个字不动** —— 那一段每拖一次都要读屏定位，正是落点精度会咬人的地方。
这是本方案与「把慢拖全换成滚轮」的分界线。

### 2.6 未知项（必须先上实机量的）

1. **到顶之后列表停在网格上没有？** —— §2.3 第 2 条的实测。做法：连拨到顶、读一屏、
   看名字有没有横跨两行。**这一条不成立，整个方案退回慢拖。**
2. **行星列表面板吃不吃滚轮？** 军力榜面板吃（实测过），这是另一个面板。
3. **一屏几行、一格走几行？** 军力榜是 `ROWS_PER_NOTCH = 1.08`，行星列表行高不同，
   不能照抄，K 要现场标一次。

### 2.7 预估收益

一轮滚轮拨完一屏的距离约 0.5s（按 20 行/秒、一屏 3 行），加沉降等待与一次面板
OCR，一轮 ≈ 5s（现在一次慢拖 ≈ 9s）。轮数与现在同阶（判据没变）：

    22.1s → 约 12s   省 10s / 趟   按 09-07 的 90 趟 ≈ 15 分/天，保守打七折 ≈ 12 分/天

⚠️ **是估算。** 那一轮的面板 OCR 是常数项，如果它占大头，能省的比例就比这个小。
**不设通过线**，先量。

## 3. 第 ② 件：邮件重复开封（**结论从 v2 大幅收窄**）

### 3.1 调研数据

09-07 白开了 **90 封**，单封 ≈ 20s（开封 4.1s + 解析入库 7.4s + 查重 8.5s），
约 **30 分/天**。这一条不变。

### 3.2 回应 review ①：钩子根本不在调度器跑的那条路上

v2 §3.5 用「库里有 N 发到点还没战报」当「走了 `backfill_reports`」的证据。**错了。**
那句话和「开工：读回攻击战报」**两句都在 `reconcile_today` 里**
（`pirate_loop.py` 3428 附近），而它接着调的是：

    reconcile_today()  ->  _scan_for_reconcile(day_start, now=now)   ← 不传 should_open

真实的入口归属：

| 入口 | 传 `should_open` | 谁调它 |
|---|---|---|
| `collect_scout_reports` | ❌ | 侦察那条链路 |
| `backfill_scout_reports` | ❌ | 侦察补录 |
| `backfill_reports` | ✅（且仅 `due_before` 非空时） | **只有 `tools/backfill_reports.py`（手工工具）** |
| `_scan_for_reconcile` | ❌ | `reconcile_today()` ← `_reconcile_if_due()` ← `PirateLoop.run()` |

`domain/reconcile_cooldown.py` 开头就写着这条链：
`PirateLoop.run()` → `reconcile_today()` → `_scan_mail_rows()` → `_ingest_report_row()`。

**所以调度器每一趟走的都是没有钩子的那条路，那 90 封的覆盖率是 0%，不是 100%。**

改动位置跟着变：**要装在 `_scan_for_reconcile` 那条路上**，而不是往现有
`should_open` 里加条件。两种形状：

- 在 `_scan_for_reconcile` 里也传一个 `should_open`
- 或者把这道闸做进 `_scan_mail_rows` 本身，四个入口共用

⚠️ 倾向**后者**：`_ingest_non_report_mail` 的注释里写着同一个教训 ——
「三条翻信箱的路都要做同一件分流，各写一份的话，新增一种邮件时漏掉其中一条
**不会报错**」。同一句话对这道闸成立。

⚠️ 但做进共用层就必须把 `exhaustive`（补录那一档）排除在外 —— 见 §3.4。

### 3.3 回应 review ②：早停的真条件

v2 写成「遇到已入库的就别往下翻了」。**真实条件是** `_stop_after_known()`：

    outstanding = self._due_dispatches(datetime.now(UTC))     # 每封重查
    if outstanding:  say("…还有 N 发到点没战报；接着往下开");  return False
    say("  往下都是更旧的报告，不再开封");                      return True

也就是**清单空了才停**。而且 `_ingest_report_row` 的注释记着为什么必须这样：

> 报告确实在库里，**却没接到该接的那一发派遣上**（`rematch_report_at` 记着
> 2026-08-11 那四发的全过程）。那时早停会把这几发永久钉在「待战报」——
> 每一趟都在第一封就收工，而要找的那几封就躺在它下面。

三条约束，新跳过路径必须逐条满足：

1. **不许改写这个条件，要复用 `_stop_after_known()` 本身**（它已经是单独一个方法，
   注释里写着「判据只有这一份，不许在补录那边另写一条」）。
2. **`exhaustive=True` 不走早停**，所以跳过也不许在那一档生效 ——
   补录入口存在的理由正是要够到被这些闸筛掉的那些封。
3. **数数要继续。** `observe(row)`（日均份数）在 `_scan_mail_rows` 里排在
   `should_open` **之前**，所以跳过不影响它 —— 这一条已经成立，但要有用例锁住。

日志实证：那 172 次「库里已有」后面跟的全是「还有 N 发到点没战报；接着往下开」——
**早停几乎从不触发**。所以跳过在早停上的净影响接近 0，但它是三条里最容易写错的一条。

### 3.4 补认领：从「未知项」升级成「方案的前置条件」

review 说得对，`rematch_report_at`（`repository.py:886`）只查库、不读页面。
但它的两个参数 `(target, reported_at_utc)` 在现有链路上**来自刚开封的那一页**
（唯一调用点 `pirate_loop.py:4702`）。所以直接跳过 = 那一封永远不补认领。

**而这件事根本不需要信箱**：未认领的报告在库里**自带 target 和时刻**。

    battle_reports 共 2969 份
      dispatch_id 为空（未认领）：54 份（1.8%），其中近 7 天 8 份
      match_status = UNMATCHED：54 份

所以方案改成：**先加一趟纯库内的补认领扫**，遍历 `dispatch_id IS NULL` 的报告，
拿它自己的 target + 时刻走现有的认领逻辑。这比今天更全 ——
今天只有「那一封恰好还在扫描窗口内」才补得上，库内扫覆盖全部 54 份。

⚠️ **这一趟是跳过的前置条件，不是附赠品。** 没有它，跳过就是 2026-08-11 那个
「报告在库里、派遣永远待战报」的坑原样复发。**顺序不许颠倒。**

### 3.5 同秒撞车（第一轮 review ② 的收敛，本轮不变）

历史上同秒战报只有 1 对（2969 份 / 32 天 → **0.034%**，约 32 天一遇）：

    2026-08-25 20:18:44   2:490:16 + 1:439:11
    08-26 05:06:07  入库 2:490:16     05:06:32  入库 1:439:11    ← 同一趟，隔 25 秒

比对**信箱这一屏同秒有几行**，而不是待补派遣数：

    库里该秒已有份数 >= 这一屏该秒的行数   ->  跳过
    否则                                ->  照开

08-26 那次：列表 2 行、库里 1 份 → `1 < 2` → 照开，不丢。
计数用的 `rows` 就在手上，没有新查询、新状态、新配置。

⚠️ **残余缺口**：同秒两行被**翻页切开**时，两屏各看到 1 行、库里 1 份，第二行仍会被跳。
0.034% 再乘一个翻页概率。要不要接受由 review 拍。

### 3.6 类型闸（第一轮 review ③ 的收敛，本轮不变）

| | 历史数据 |
|---|---|
| `planet_scout_alerts`（安全告警） | **0 行** |
| 「撞保护期」邮件被处理 | **0 次**（这四个字在全部 `system_log` 里没出现过） |
| 264 个 `protection_seen_at_utc` 与已入库战报同秒的 | **0 个** |

保护期是派遣当场从弹窗学的（「派遣时弹『没有可执行的任务』」223 次）。
→ 不做分流，只加 `and row.kind is RECONCILE_KIND`，未知类型落在「照开」那一侧。

### 3.7 收敛后的方案

**分三步，顺序不许颠倒：**

    第 1 步  battle_reports.reported_at_utc 加索引     （无行为改动）
    第 2 步  纯库内补认领扫                            （修一个现存缺陷，独立有价值）
    第 3 步  开封前跳过                                （依赖前两步）

第 3 步的跳过，五个前提缺一不可：

1. `row.kind is RECONCILE_KIND`（其余类型照开）
2. `row.reported_at_utc` 读得出（读不出照开 —— 这条分支已经在了）
3. 库里该秒已有份数 `>=` 这一屏该秒的行数
4. **不在 `exhaustive` 那一档**
5. 早停仍然走 `_stop_after_known()` 本身，不改写条件

外加：跳过次数进日志与收尾汇总；`observe(row)` 仍然先跑（要有用例锁）。

### 3.8 预估收益（下调）

90 封 × 20s ≈ 30 分/天 是**上限**，不是预期值。要打折的地方：

- 第 3 步只在 `_scan_for_reconcile` 那一档生效（补录那一档排除）
- 早停行为一旦变化会改变翻页次数，那一块要单独量

**这一件不再声称「加一个判断」。** 它是三个提交、一条迁移、一趟新的库内扫，
外加五个前提。收益仍然值得做，但排在滚轮后面。

- 无行为改动，**不设行为指标**

### 5.2 纯库内补认领扫（第 2 步）

- `dispatch_id IS NULL` 的报告数应当从 54 下降
- ⚠️ **反面指标**：`dispatch_id` 被认领到**错的**派遣上 —— 用 `match_confidence`
  的分布看，低置信度认领数不许上涨
- 待补派遣（`due_after`）应当下降或不变，**不许上涨**

### 5.3 滚轮回顶（第 3 步）

- 「起点 → 拖到顶」中位数下降（现在 19.5s）

- ⚠️ **反面指标三**：`match_status = UNMATCHED` 不许上涨

## 7. 记一笔：调研中发现的、本方案范围之外的

1. **⚠️ 邮件回顶有 20.9% 判不出到顶**（近 14 天 142 / 681）。09-07 那两次各 245s

2. **撞保护期作废 147 次 / 8.4 分（2.2%）** —— 导航、开面板、翻预设条全做完，
   才在派遣那一刻弹「没有可执行的任务」。223 次「派遣时被弹」说明选靶侧的
   保护期排除窗口和游戏侧实际保护期对不齐。
3. **54 份未认领战报（1.8%）** —— 已经收进本方案第 2 步，这里只记它的出处。
4. **`backfill_reports` 上那道时间闸从没在调度器路径上跑过。** 撤回 v2 的
   「它空转」那句 —— 它没上场，谈不上空转。要不要把它移到共用层是 §3.2 的取舍，
   而它自身的有效性**没有任何生产数据可以支持或否定**。
5. **军力榜的名次读错** —— 09-07 13:48 那趟识别率 92.67%，11 行名次落在采集区间外
