## 1. 现状

`_scroll_mail_list_to_top`（`tools/pirate_loop.py:2338`）：

    for drag in range(MAIL_SCROLL_TO_TOP_MAX_DRAGS):     # 上限 40
        rows = self._mail_list_rows()                    # 一次面板 OCR
        if mail_times_settled(previous, [row.raw_time_text ...]): return
        previous = times
        slow_drag(self._driver, PANEL_DRAG_TO_Y, PANEL_DRAG_FROM_Y)   # 往上 400px ≈ 4.6 行

判据 `mail_times_settled`：两屏之间**时间列**逐位比较，**6 行里 ≥ 4 行相同**才算没动。
读空不算到顶（分母是总行数，不是读出来的行数）。

## 2. ⚠️ 诊断：不是读不出来，而是「一直在变」

放弃那 142 次里，**122 次（86%）是「6 行时间全都读出来了」**：

    6 行 → 122 次     5 行 → 15 次     3 行 → 4 次     0 行 → 1 次

所以这**不是** 2026-08-18 那个坑（那次是比主题、主题读不稳、判据永远不成立）。
时间列读得出来，判据却始终判「还在动」。

**两个候选解释，现有日志分不开：**

| | 解释 | 如果是它 |
|---|---|---|
| (a) | 信箱确实比 40 次拖得深（40 × 4.6 ≈ 184 行） | 滚轮**直接修好**（能真到顶） |
| (b) | 已经在顶部附近，但每次读到的行窗口不同（慢拖惯性留下非整行偏移） | 滚轮**不修判据**，但过冲夹住能修 |

⚠️ **分不开的原因是中途那几屏没有落库** —— 放弃时只记最后一屏。
所以下面第 4 节先加一步观测。

⚠️ 一个指向 (b) 的线索：放弃时那句「最后一屏第 0 行是 07/09/2026 08:21:53 的邮件」，
而那一趟跑在 08:5x —— 第 0 行是半小时前的邮件，**看起来已经在顶部了**。
但这只是一条线索，不是证据：也可能信箱里还有更新的、只是没拖到。

## 3. 为什么滚轮在这里比行星列表更值得做

| | 行星列表 | 邮件列表 |
|---|---|---|
| 一次动作 | 慢拖 ≈ 9s | 慢拖 ≈ 5.8s |
| 平均次数 | 2.4 次 | **10.9 次** |
| 上限 | 6（**从没走满**，0/2369） | 40（**走满 142/823 = 17%**） |
| 走满的后果 | 不存在 | **从一个不知道在哪的位置开始往下翻** |

⚠️ **走满上限不只是慢，它是正确性问题。** 日志原话：
「到没到顶判不出来，这一趟就从这里往下翻」。也就是说
**每五次进信箱就有一次是从未知位置开始扫的** —— 上面那些更新的邮件这一趟根本不会被看到。

而距离正是滚轮的强项：40 次拖走 184 行用 232 秒；滚轮 19–23 行/秒，同样 184 行约 **9 秒**，
上千行也在一分钟内。

## 4. 方案（分两步，观测先行）

### 第 1 步：先把中途那几屏记下来（只观测，不改行为）

放弃那条路上，把每一轮的时间列（或至少第 0 行 + 读出行数）落进 `record_system_log`
的 payload。⚠️ 现在那条记录的 `payload` 是空的（实测 `payload keys: []`，
`max_drags` 也是 `None`）—— 措辞里有的信息一条都没进结构化字段。

**这一步单独发布，跑一天。** 它回答 §2 的 (a) 还是 (b)，而那个答案决定第 2 步的形状。

### 第 2 步：换滚轮 + 过冲夹住

    现在：最多 40 轮 × （读一屏 + 慢拖 400px）
    改后：① 连拨足量格数（开环，过冲到夹住）
          ② 读一屏
          ③ 再拨少量
          ④ 读一屏；两屏比 mail_times_settled
          比不上就回到 ①，上限保留

**为什么过冲是安全的**（与行星列表同一套论证）：

1. **往上过冲物理上不可能** —— 列表到顶被夹住。
2. **到顶就是网格原点** —— 「非整行位置」的根源是停在任意偏移上；被夹在顶部时
   偏移为 0，正好是标定网格原点。
3. **而且它同时修掉 (a) 和 (b)**：两次比较的都是「已经夹住」的屏，内容必然相同。

⚠️ 第 2 条仍然是**推理不是实测**，和 v3 §2.6 第 1 项是同一个未知项 ——
两条链路可以一次上机量完。

⚠️ **判据 `mail_times_settled` 一个字都不改。** 它是 2026-08-18 那次事故的产物
（比时间不比主题、严格多数、读空不算到顶），实拍上量过
（31 屏 186 行：时间读出 93.5%，主题一字不差 0%）。这次只换**滚动手段**。

## 5. 预估收益（弱，未上机）

按「一轮滚轮 ≈ 1.3s（拨 0.3s + 面板 OCR 1s）」对「一次慢拖 ≈ 5.8s」：

    成功到顶   10.9 × 1.3 ≈ 14s   （现在 ≈ 88s）
    放弃       40  × 1.3 ≈ 52s   （现在 ≈ 245s）
    期望       ≈ 22s              （现在 ≈ 121s）
    每次进信箱省 ≈ 99s

09-07 只进了 22 次信箱 → ≈ 36 分/天。而 09-05 那种 72 次的日子 → 更多。

⚠️⚠️ **这个估算里「面板 OCR ≈ 1s」和「一轮拨 ≈ 0.3s」两个数都没量过**，
而它们是分母。真正的数上机才有。**不设通过线。**

⚠️ 如果 §2 的答案是 (a)（信箱真的深），那么「放弃」这一档会**从 52s 变成到顶为止**，
次数也不再是 40 —— 收益要重算，但那时它同时修掉了 17% 的「从未知位置开始扫」，
价值比省下的时间大。

## 6. 验收（与 v3 §5 的邮件指标合并）

- 「往上拖满」次数应当从 **142/14 天** 降到接近 0
- 「列表往上拖了 N 次到顶」里的 **N 的分布**应当整体左移
- ⚠️ **反面指标一**：`往上拖满` 不许上涨（上涨就是方向或过冲量搞错了）
- ⚠️ **反面指标二**：到顶那一屏「6 行里读出时间的有 N 行」不许下降 ——
  它降了就说明夹住的那一屏没落在网格上（§4 第 2 条不成立）
- ⚠️ **反面指标三**：`battle_reports` 每天新增份数不许下降 ——
  真到顶之后看到的邮件更多，这个数**应当上升或不变**

## 7. 与 v3 的关系

- **共用一个未知项**（到顶是不是网格原点），一次上机两条链路一起量
