# 数据概览页 —— 需求（2026-08-19）

用户需求原文：

> 开一个新需求，叫数据概览吧，目的是直观的查看当前的状态，以及数据，我关心的东西是。
> 现在几条航线在跑（按星球），几个邮件未读。今天收益 and 统计（UTC+0），
> 最近一周/月/合计等等。

**这是一个新页面**，与现有的「任务中心 / 攻击配置 / 军力榜 / 星球列表 / 攻击日志 /
系统日志 / 诊断」并列。

⚠️ 仓库里已有一份 [`数据概览-方案.md`](数据概览-方案.md)（2026-08-17，需求是
「每天攻击了多少次、扫描了多少球、攻击发出率」）。**那一份是这一份的子集**，
本文档在它之上扩「实时状态」与「收益」两块，其既定口径（UTC+0 切天、统计起点
2026-08-17、不对「没打出去」做归因）**全部沿用，不重新讨论**。

## 二、能直接给的（不加表、不加列、不加迁移）

### 2.1 此刻状态

| 指标 | 来源 | 现在的实际值（2026-08-19 23:0x） |
|---|---|---|
| 各星球在飞几条 | `attack_dispatches` + `attack_intents.origin_*`，判据 `line_free_at_utc > now()` | `4:277:15` 5 条、`9:250:8` 1 条 |
| 各星球最早何时空出一条 | `min(line_free_at_utc)` | `4:277:15` 23:26:48、`9:250:8` 23:07:24 |
| **占线但时长未知的** | `line_free_at_utc IS NULL AND line_released_at_utc IS NULL` | `4:277:15` 2 条、`9:250:8` 3 条 |
| 到点还没收到战报的派遣 | `expected_report_at_utc < now()` 且无关联战报 | 11 发 |
| 军力候选池新鲜度 | `bot_targets.military_score_at_utc` | 窗口内 510 个、龄中位 0.4h |
| 调度器在跑什么 | `mission_runs` 最新一行 | |

⚠️ **「时长未知」那一档必须单独显示，不许并进「在飞」。** 它是飞行时间没读出来、
按 `UNKNOWN_LINE_HOLD`（90 分钟）占着航线的那些——把它和真的在飞混在一起，
页面就说不出「为什么明明没派几发却没航线了」。

⚠️ **在飞数可能超过该星球配置的航线数**（实测 `4:277:15` 在飞 5 条而配置是 4 条），
因为它**跨任务种类**（海盗与 bot 抢同一批航线）。页面要把这件事说出来，
否则会被当成 bug。

### 2.2 今天 / 本周 / 本月 / 合计（UTC+0 切天）

每一档都给同一组数：

| 指标 | 来源 |
|---|---|
| **稀有三样**：合金碎片 / 泰坦立方 / 收割者碎片 | `battle_report_resources` 的 slot 5 / 8 / 9 |
| 其余九种资源 | 同表 slot 0–4、6、7、10、11（名字见 `domain.battle_resources.SLOT_LABELS`） |
| 派遣发数 | `attack_dispatches`（`accepted`） |
| 战报回收数 / 回收率 | `battle_reports` ÷ 派遣数 |
| 撞保护期次数 | `bot_targets.protection_seen_at_utc` |
| 覆盖坐标数 | `count(distinct 目标坐标)` |
| 航线利用率 | 占用航线小时 ÷ 可用航线小时 |

**航线利用率**是这次新加的、也是我认为最值得放在首屏的一个数——2026-08-19 实测
它从 40.3% 涨到 99.2%，而同期实际收获涨了 3.4 倍。**它比「打了多少发」更能说明
产能有没有被浪费。**

## 三、「未读邮件」= 发出去还没回读战报的那些

用户澄清（2026-08-19）：**「我的未读邮件是指你发出攻击，但是还没有回读邮件的数量」**
—— 不是游戏顶栏那个 `✉ N` 角标（那个数含系统公告、联盟消息、别人打你的战报，
而且全仓从没读过它）。

这个数**今天就有**，而且**必须切成三档**，因为它们的善后完全不同。
实测（2026-08-19 23:0x，48 小时窗口）：

| 档 | 判据 | 现值 | 这是什么 |
|---|---|---|---|
| 还在飞 | `expected_report_at_utc > now()` | 3 发 | **正常**。战报还没产生，等着就行 |
| **★ 到点了还没读回来** | `expected_report_at_utc <= now()` | **25 发** | **这就是「未读邮件」**。战报在信箱里躺着，助手还没去读 |
| 不知到没到 | `expected_report_at_utc IS NULL` | 9 发 | 飞行时间没读出来（PR #205 之后新发不该再有），按 90 分钟兜底占着航线 |
| 合计待回读 | | 37 发 | |

按出发星球：`4:277:15` 未读 22 / 待回读 30，`9:250:8` 未读 3 / 待回读 7。

### ⚠️ 光显示一个数不够，必须同时显示「最老的等了多久」

实测最老那一发的期望战报时刻是 **2026-08-17 10:38** —— **等了两天多**。
这类多半永远读不回来了（战报被信箱窗口滑出去、或者当时的认领缺陷留下的残骸），
它们会**永久地把「未读」这个数垫高**。

所以页面上要么：

- 同时显示「最老一发已等 N 小时」，让人一眼看出这个数里有多少是陈年积压；
- 要么把统计窗口限死（例如只算 24 小时内派出的），并**把这个窗口写在页面上**。

⚠️ **别只显示一个总数。** 「25 发未读」如果其中 20 发是两天前的死账，
那它表达的是「有历史包袱」而不是「现在积压」，而这两件事的善后完全相反。

## 四、⚠️ 「最近一个月」目前只有 3 天真数据

实测（2026-08-19）：

| 窗口 | 战报 | 派遣 | 稀有三样 |
|---|---|---|---|
| 今天（UTC+0） | 2 份 | 6 发 | 8,756 |
| 最近 7 天 | 106 份 | 427 发 | 215,741 |
| 最近 30 天 | 183 份 | 927 发 | 215,741 |
| 自 2026-08-17 起 | 79 份 | 128 发 | 215,741 |

**三个窗口的稀有三样完全相同**，因为资源识别是 2026-08-18 才修好的
（PR #191/#193），更早的战报**根本没有资源明细**。

所以页面上必须做两件事，否则「本月收益」会被读成一个假的低值：

1. **每一格都标出它覆盖了几天真数据**，例如「最近 30 天（有效数据 3 天）」；
2. **资源类指标的统计起点单列**，与派遣/战报类指标的起点（2026-08-17）分开——
   它们不是同一天开始有数的。

⚠️ 现有方案文档里那条「统计起点 2026-08-17」仍然成立，但**只管派遣与战报这类计数**；
资源明细的实际起点是 **2026-08-18**。这两个日期不能合并成一个常量。

## 七、实现上的边界（写给做这件事的人）

- **不加表、不加列、不加迁移。** 上面全部指标都从现有表算得出来。
- **只读。** 这一页不许有任何写操作、不许触发游戏动作。
- **UTC+0 切天**，但页面上的时刻按 UTC+8 显示（与攻击日志一致），**并且标出来**。
- 统计起点做成常量，不许散在各处查询里（现有方案文档已有此约定）。
- 页面要能在**调度器停着**的时候照常打开——它是只读视图，不依赖 runner。

## 八、原型评审之后补的硬约束（2026-08-19）

原型第一版在这几处都算错过，每一条都是**看起来合理、实际相反**的那种，所以写死在这里。

### 8.1 ⚠️ 航线占用必须复用 `_still_holding_a_line`，不许另写

原型第一版自己写了个判据 `line_free_at_utc IS NULL AND line_released_at_utc IS NULL`，
把 10–22 小时前派出、早已超过 `UNKNOWN_LINE_HOLD` 的那些也算成「占着航线」。

调度器有现成的谓词（`storage/repository.py` 的 `_still_holding_a_line`）：

```
line_released_at_utc IS NULL
AND ( line_free_at_utc > now  OR  (line_free_at_utc IS NULL AND dispatched_at_utc > now - hold) )
```

三档缺一不可，`hold` 必填（用户在攻击配置页上改的那个值）。**页面必须调同一个谓词**——
两处各算各的正是这个仓反复出事的形状。

### 8.2 ⚠️「最早空出」要 `FILTER (WHERE line_free_at_utc > now())`

原型第一版写的是 `min(line_free_at_utc)`，取到的是一个**早就过去**的时刻
（显示「23:26:48，约 21 分钟后」，而当时已是次日 09:54）。

### 8.3 航线格子按**配置的航线数**画，不按占用数

配置几条就画几格，占用多少点亮多少。原型第一版按「在飞 + 时长未知」画格子，
于是一颗配了 4 条的星球画出了 7 格。

⚠️ 每颗星球的航线数**各不相同**（实测 `4:277:15` 5 条、`9:250:8` 4 条），
要从 `mission_task_origins.fleet_lines` 读，不许写死。

### 8.4 ⚠️ 收益只覆盖「已读回的战报」，而且过去某一天的数会一直变

材料由游戏直接入账，**读不读战报都拿到了**——读战报只是我们知道的途径。
所以资源列永远是**下界**，低多少由回收率决定。

更要紧的是它**不收敛**：战报是滞后读回来的。实测 08-18 这一天

| 看的时刻 | 已读回 | 合金碎片 |
|---|---|---|
| 08-18 23:10 | 33 份 | 67,594 |
| 08-19 10:10 | 61 份 | 166,194 |

**同一天的数，隔 11 小时涨了 2.5 倍。**

所以：

- 每一行的**「读回战报数」与「回收率」必须和资源列并排显示**，不许只给资源；
- 页面上要写明「资源列只统计已读回的战报」。

不这么做的话，用户明天再看同一天的数会以为出了 bug——而它其实一直在补。

### 8.5 未读战报要给「窗口内」和「总积压」两个数

实测：**总积压 713 发**（最老派于 08-09 18:27，等了 9 天多），而 48 小时内派出的只有 **25 发**。

只给 713 会让人以为现在出了大问题；只给 25 会把历史包袱藏掉。**两个都要有。**

### 8.6 资源图标从战报面板切，不必上实机

`battle_report_screenshots` 表里存着 520×695 的战报面板（实测 79 张），
「获得资源」那 4×3 网格上就有全部 12 个图标。抠透明底用**从四边漫水**、
容差取 10——容差放大到 16 以上会顺着图标内部的暗缝漏进去，把图标掏出洞来。

### 8.7 页面自己不许再造判据

上面这些之所以会错，共同原因是**页面自己算了一遍**。凡是领域层已有的判据
（航线占用、候选池筛选、回收率、保护期排除），页面一律**调现成的**，
不许为了「一条 SQL 更快」另写一份。

## 九、拍板结论（2026-08-19，用户定）

第六节那几个待定项已经定了，**不再讨论**：

| 项 | 结论 |
|---|---|
| **统计时区** | **UTC+0**。用户口径：「使用 UTC+0 作为统计口径」 |
| **未读战报** | **只统计当天，不统计历史积压** |
| 说明文字 | **不留小字**。用户口径：「不留小字」 |
| 收益首屏 | 稀有三样（合金碎片 / 泰坦立方 / 收割者碎片），其余九种折叠 |
| 周期统计 | 按天最多 7 行，可切换 按天 / 按周 / 按月 / 总计 |
| 菜单位置 | 「数据概览」放侧边栏**最上面** |
| 调度器状态 | 放「此刻」**第一位** |

### ⚠️ 时区这一条会让页面上的数和用户手查的对不上，这是预期的

用户平时用 `AT TIME ZONE 'Asia/Shanghai'` 分组手查。同一批数据两种切法：

| 日期 | UTC+8 合金碎片 | UTC+0 合金碎片 |
|---|---|---|
| 08-19 | 117,600（33 份） | 27,500（8 份） |
| 08-18 | 86,728（49 份） | 166,194（61 份） |
| 08-17 | 20,200（3 份） | 30,834（16 份） |
| **合计** | **224,528（85 份）** | **224,528（85 份）** |

**合计完全一样，只有日切位置不同。** 页面按 UTC+0，所以某一天的数会和用户按
UTC+8 手查的对不上——**这不是 bug**。页面头部已经写明「统计按 UTC+0 切天」，
不再额外解释。

（这一条曾经让人以为出了 10 倍的资源计算错误，查了一轮才发现只是日切口径不同。
写在这里是为了下次不用再查一遍。）

### 未读战报「只算当天」的实现口径

```
当天（UTC+0）派出的 accepted 攻击中，
  expected_report_at_utc <= now() 且还没有关联战报的
```

⚠️ **不要**把历史积压（实测 713 发、最老派于 08-09）混进来。按当天算出来的数

## 十、追加需求：今日收益里加「航线平均时间」（2026-08-19）

用户口径（2026-08-19）：

> 首页今日收益中增加，航线平均时间。**前置是飞行时间 ocr 修复**。

### 口径

**每发平均占用航线多久（往返）** = `flight_seconds × 2`，取**中位**与**均值**都给。

放在「航线利用率」旁边。两个是一对：**利用率答「航线闲不闲」，平均往返答「一发要占多久」**，
两个一起才分得出「是发得少，还是飞得久」。

⚠️ **不要做成「每条航线今天平均被占了多久」**（占用小时 ÷ 航线数）——那个数等价于
`利用率 × 已过小时数`，信息与利用率重复。

### ⚠️ 为什么必须等 OCR 修好：这个数现在是**系统性偏低**的，不是「样本少一点」

实测 2026-08-19（UTC+0 当天，派出 18 发）：

| | |
|---|---|
| 读到 `flight_seconds` 的 | 12 发 |
| 读不到的 | **6 发，全部来自 `9:250:8`，一发都不在 `4:277:15`** |
| 口径 A 算出来 | 中位 125.0 分、均值 108.5 分 |

缺的那 6 发**全是跨银河长途**。也就是说这个平均值**丢掉的恰好是最长的那一批**，
而且丢得有规律（按出发星球），不是随机缺失。

成因（记在 `domain/flight_estimate` 那条线上）：飞行时间 OCR 会截断
（`'IBY 2分 6秒'` ← 真值 62 分 6 秒），三来源里本该由公式裁掉它，
但公式的适用域闸是**速度字符串相等**（标定值 `14.520`），而 `9:250:8` 的速度是 `14.720`
—— 公式弃权 → 「两个读数打架、裁不出来」→ 两个都不采信。

`4:277:15` 正好是标定那颗星球，公式能裁，所以它一发都没丢。

**修法（另一条线）**：系数改成按出发星球从历史实测学。实测 256 发反解，
跨银河那一档每颗星球自己的 k 预测误差**最大 0.03%**（`4:277:15` k=26.5165、
`9:250:8` k=26.3327）。同银河那一档仍然弃权（p90 误差 32–50%）。

### 页面上要标什么

沿用第 8.4 节那条既有规矩：**资源列旁边并排显示「读回战报数」与「回收率」**。
这一项同理——**平均往返旁边要显示「基于几发」**，因为读不出飞行时间的那些不进分母。

不这么做的话，OCR 出问题时这个数会静默变小，而页面上看不出任何异常。
