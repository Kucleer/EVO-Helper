# 军力数据超期就不打 —— 方案（方案 A）

用户口径（2026-08-17）：「我配置了超过 1 小时要扫描军力，但是仍然获取了旧数据进行攻击」，选定**方案 A：选目标时跳过超期的**。

## 一、现状与它错在哪

判据在 `application/mission_scheduler.py:1380`：

```python
scanned_at = [item.military_score_at_utc for item in pool if item.military_score_at_utc]
stale_at = min(scanned_at, default=None)          # 整池最旧的那一条
if stale_at is not None and now - stale_at >= stale_after:
    # 只记录，不阻塞派遣、更不能从这里启动 RANKING：两条链路会争同一只鼠标。
    _LOGGER.info("军力候选池数据已过期（最旧读数 %s）；继续派遣，等待调度器空隙扫描", stale_at)
```

实机对照（2026-08-17）：`4:293:6` 的读数是 01:50 UTC，攻击发生在 05:28 UTC，**已经 3.6 小时**，而用户设的是 1 小时——确实拿超期数据打了。

两处要改：

1. **「不能从这里启动扫描」≠「必须拿旧数据去打」。** 注释里那个理由（两条链路争一只鼠标）只能解释「不立刻发起重扫」，不能解释「继续用旧值派遣」。跳过超期目标一只鼠标都不多占。
2. **判据是 `min(整池)`，不是逐目标。** 日志里那句「最旧读数 2026-08-14 21:58」说的是三天前的某一条，而不是它正要打的那个。500 个候选里一条陈旧就让整池被判过期，于是这条警告永远在响，而响的时候你并不知道正要打的那个新不新。

## 二、⚠️ 最重要的一条：「没有新鲜目标」绝不能走 `MissionParamError`

`domain/missions.py` 里那些 `MissionParamError` 会一路走到 `repository.disable_mission_task`，**把任务自动停用、挂上 `disabled_reason`、要用户手动点「恢复」才能回来**（`mission_scheduler.py:1553` 的判据是 `enabled and disabled_reason is None`）。

PR #161 只让「空闲航线不足」那一类自动恢复，其余仍需人工。

**所以「这一轮没有读数新鲜的目标」如果按参数错误抛出去，后果是：任务被停用 → 你不点恢复它就永远不跑。** 那比现在拿旧数据打糟得多。

**正确做法**：它是一个**正常的「暂时没活干」**状态，不是错误。

- 优先在**调度判据**里表达（`domain/scheduler.py` 的 `has_work`）——没有新鲜目标就当这条链路此刻没活干，调度器自然会去跑填空隙的任务（正好就是军力榜扫描），把池子刷新。
- 退一步，也要保证 runner 干净退出（`exit 0`），**不要**让它进连续失败计数——那会和刚修好的 #157（环境条件按 75 收场）、#161 打架。

这一条要有专门的用例钉住：**池子全超期时，任务不被停用、`consecutive_failures` 不增长**。

## 三、改法

### 1. 过滤放在取 top-N **之前**

现在的算法是「按军力取前 N，再按距离排序」。**先滤掉超期的，再取前 N**——反过来的话，前 N 里若大半超期，实际可打的就寥寥无几，而「候选 500 名」这个设置就形同虚设。

### 2. 判据逐目标

```
可打 = 读数存在 且 now − military_score_at_utc < 有效期
```

⚠️ **`military_score_at_utc IS NULL` 一律算超期**（从来没读过，不知道多旧），不要当成「刚读的」。

### 3. 日志说实话

现在那句「最旧读数 …；继续派遣」要换掉，改成能回答「这一轮到底还剩多少能打」：

```
军力候选池：500 个候选中 37 个读数在 1 小时内，463 个超期已跳过（最旧 2026-08-14 21:58）
```

超期数为 0 时不必每轮都打。

### 4. 字段改名

界面上现在叫「**小时提示重扫**」——那时它确实只是提示。改成方案 A 之后它是硬判据，名字要跟着改，例如「军力数据有效期（小时）」。⚠️ 不改名的话，语义又一次和文案对不上，而今天已经因为「日志说的不是实话」栽过一次。

## 四、和今天其它改动的相互作用

- **PR #153（军力扫描数量范围）让这个方案可行。** 用户口径：「因为今天的修改有军力扫描范围，不会出现长扫描轮询占用」——扫描可以配成小批量、跑得勤，池子刷新周期短，所以「超期就不打」不会把攻击饿死。
- ⚠️ **但两个设置有个必须成立的关系**：军力榜扫完一轮的时间**必须短于有效期**，否则池子永远追不上，攻击会长期停摆。这条建议在界面上提示，或在日志里明确报出来（例如连续 N 轮没有新鲜目标时给一条 WARNING）。
- **PR #162（盲拖自动标定）** 会让每趟扫描更快，同向利好。

## 五、不做的

- **不从攻击链路里发起军力扫描**。原注释那个理由仍然成立：两条链路会争同一只鼠标。刷新交给调度器的填空隙机制。
- **不改 24 小时不重复打同一坐标**那条判据，两者独立。
