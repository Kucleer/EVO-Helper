## 2. ⚠️ 没验到的两条 —— **别当成验过了**

### 2.1 截止时刻那条分支

三趟空闲回读的 `earliest_line_free_at_utc` **全是 `null`**，走的都是
「算不出就不设截止」那一侧。原因是那几个时刻库里没有带航线钟的在飞派遣
（上一批 BOT 轮停在 08:49）。

⇒ **`deadline` 真正生效的那条路（每次开封前问、到点收工）实机一次都没跑过。**
单元用例覆盖了判据本身，但「实机上它会不会在对的时刻停下来」没有证据。

要验到它，需要：调度器派出攻击（于是有航线钟）→ 信箱回读恰好在那段窗口里起来 →
且那条线会在一趟信箱的时长内空出来。观察期看 `stopped_by=deadline` 的趟数。

### 2.2 抢占

方案 §9 自己写着：军力榜从未被抢占过（全时段 0 次），而空闲回读依赖**同一条**
抢占路径（`decide()` 的 PREEMPT 档 + `_act()` 的 `stop(PREEMPTED)`）。

本次改动把执行层三处写死的 `is not MissionKind.SCAN` 换成了 `PREEMPTIBLE` 集合，
**用例覆盖了两层各自的判据，但整条链在实机上没跑过**。

⇒ 观察期**至少要见到一次 `mission_runs.stopped_by = PREEMPTED`**，否则这条路
仍然算没验过 —— 而它正是「攻击不会被信箱拖着」的最后一道保证。

## 3. 实机打回来的那一个真问题

`run_mail_only` 漏了 `run()` 开工四步里的第四步 `_require_system_view`：

```
15:13:50  列表往上拨了 1 轮到顶
15:13:52  6 行按主题全拒
15:13:58  第 2 屏拖不动了（到底）
15:14:27  读完邮件切不回恒星系视图   ← 栽在收尾
```

信箱**翻得好好的**，栽在收尾 —— 而关窗重开又撞上网络波动，一趟白跑。

⚠️ **今天第二次犯同一个错**（`#331` 星门那次漏的是 `_ensure_session`）。两次都是
「抄了一部分」，而缺哪一步的失败都发生在**后面很远的地方**，从症状反推不到这里。
所以加了 `tests/unit/tools/test_entry_sequences.py` 直接钉序列本身，并反向钉住
「`run()` 多一步时那张清单要跟上」。

## 4. 顺带修的 `#331` 漏

`missions.html` 里 `FILLS_GAPS` 是手写 JS 字面量，与 `domain.scheduler.GAP_FILLERS`
**没有任何同步机制**。加星门时漏改了 —— 那张卡因此是可拖的，而带 `priority` 的
PATCH 打到填空隙任务身上一律 400，**用户拖完了才发现**。

那段注释里本来就记着同一个坑发生过一次（军力榜）。补上清单，并加
`tests/unit/web/test_fills_gaps_sync.py` 比对两份清单。
