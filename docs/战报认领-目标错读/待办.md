# 战报的目标坐标读错 → 派遣永远认不上（待办，2026-09-08 调研完，未开工）

**状态：验证做完了，代码一行没动。** 用户口径（2026-09-08）：「记录待办，先不开工」。

---

## 1. 现象

`battle_reports` 里有一批战报 `dispatch_id IS NULL`（`match_status = UNMATCHED`）。
后果不是「少一条账」：

> 库里那一份至今没认领任何派遣（UNMATCHED），**它的战果不会出现在攻击日志上**
> —— 日志原话

近 12 天 **17 份**。而它对应的那一发派遣永远停在「到点还没战报」，
每趟对账都会把它列进「单子上还有 N 发」，也就永远拖着早停不放。

---

## 2. 调研：只有一个成因，不是两个

一开始看着像两组（位号 ≤4 的 / 位号 ≥5 的），查完是同一件事：
**战报的目标坐标被 OCR 读错一位。**

### 2.1 位号被吞掉末位

```
09-08 01:40  已发动攻击 → 9:240:11（预设 BBB）
09-08 01:57  战报入库，目标记成 9:240:1     ← 11 → 1
```

同形态 4 例（`9:240:11`、`8:70:11`、`2:420:11`、`2:307:11`），
时间差 17–27 分钟正好一个飞行时长。

⚠️ **`位号 ≤4` 是一个零误报的检测器**：`domain/scan_bounds.py` 写着
「**1–4 号位恒为海盗**，扫了不会有 bot」，而派遣侧 14 天 2493 发**一发都没往那儿打**。
所以战报里出现位号 ≤4 就是定义上不可能的读数。

⚠️ 但**不是 ROI 裁窄**：位号 ≥10 的战报 1544 份 / 派遣 1645 发，读得好。
位号 ≤4 只有 8 份（0.34%），是偶发。

### 2.2 `9` 被读成 `3`

```
战报 3:188:8  ← 真的打的是 9:188:8（报告前 24 分，未认领）
战报 1:30:7   ← 真的打的是 1:90:7 （报告前 21 分，未认领，08-28/09-04/09-07 三次）
```

这正是 2026-08-18 记过的那条：`[` 与 `9` 在 7× LANCZOS 下糊成 `3`
（当时的表现是出发点 `9:250:8` → `3:250:8`）。**同一个字形问题，这次落在目标上。**

### 2.3 丢一位

```
战报 3:103:18 ← 3:109:18（报告前 63 分）
战报 2:30:20  ← 2:311:20（报告前 27 分，编辑距离 2）
```

---

## 3. ⚠️ 为什么现有三档一档都救不了

`_link_dispatch` 的候选池是**先按目标精确筛**出来的：

```python
close = _unmatched_dispatch_candidates(session, target=target, ...)   # ← 目标一错，这里就是 0
same_origin = [c for c in close if c.origin == origin]                # 出发点只在这一步收窄
```

目标错 ⇒ `close` 为空 ⇒ 出发点那三档**压根轮不到**。

这也解释了那句注释「**没有一例是靠出发点才分开的**」：不是出发点没用，
是它在现有流程里永远没机会上场。

---

## 4. 用户口径：一个星系只有一个出发点

用户口径（2026-09-08）：**「已知我方一个星系只有一个出发点」**。库里核实成立：

```
attack_planets：4:277:15  9:250:8  5:261:8  7:228:15  1:55:6  8:117:6  2:391:16
                7 个出发点，7 个不同星系，每星系恰好 1 个
```

**所以出发点是强约束** —— 目标模糊之后，它是把候选池收窄到 1 的那把刀。

---

## 5. 方案：加第 4 档「目标近似」

只在**前三档一发都没认到**时启用：

```
候选 = MATCH_TIME_TOLERANCE(12h) 窗内的未认领派遣
     ∩ 出发点精确相等
     ∩ 目标编辑距离 <= 1
     ∩ 落在 expected_report_at_utc 的 −60s / +300s 窄窗内
唯一存活 → 认领，新置信度档（拟 0.5，低于现有最低的 0.6）
          并把「读成什么 / 实际是什么」落 system_log
多于一个 → 一发都不认（AMBIGUOUS），照现有口径
```

### 三条边界（要写进注释）

1. **要求 `expected_report_at_utc` 非空** —— 读不到飞行时长的那 13% 派遣没有窄窗，
   宁可留 UNMATCHED。与现有第 3 档同一条口径。
2. **同时把错读的目标坐标纠正过来** —— 否则库里留着 `9:240:1` 这种我们从没打过的
   坐标，而它还可能撞上一个真实存在的别的目标（`2:420:1` / `2:307:1`
   在 `bot_targets` 里真的有行）。**把战果挂到没打过的坐标上比认不上更糟。**
3. **位号 ≤4 单独报一条 WARNING** —— 那是定义上不可能的读数，值得独立可查，
   不该混在「认不上」里。

## 6. 验证（2026-09-08，只读库，没起游戏）

复现脚本的逻辑：候选池 = 12 小时窗内未认领派遣，按「出发点精确 + 目标编辑距离
+ 窄窗」筛，数存活个数。

### 实验 B（决定性）：拿 200 份已 1.0 认领的战报，人为错读一位（375 次）

| 配置 | 还原对了 | **认错人** | 歧义不认 |
|---|---|---|---|
| 距≤1，不用窄窗 | 370（98.7%） | **0** | 5 |
| **距≤1 + 窄窗** | **375（100%）** | **0** | 0 |
| 距≤2，不用窄窗 | 292（77.9%） | **0** | 83 |

四种错读形态：末位吞掉、星系 `9→3`、系统 `9→3`、系统丢中间位。

### 对照：把正确答案从候选池里抽掉

⚠️ 这一档是我第一版脚本的 **bug**（池子过滤了「已认领」，而 hold-out 的真身正被
那份战报认领着），但它恰好量出了纯误判率：

| 配置 | 正确答案缺席时乱认几次 |
|---|---|
| 距≤1，不用窄窗 | 4 |
| **距≤1 + 窄窗** | **0** |
| 距≤2 | 62 |

**窄窗是决定性的那个约束**：有它，答案在就 100% 找对、答案不在就 100% 不认；
没它两头各漏一点。不奇怪 —— `expected_report_at_utc` 从飞行时长算出来，
±60/300 秒比坐标本身更能定死是哪一发。

### 实验 A：真实的 17 份

**距≤1 + 窄窗：13 份唯一定下来、0 歧义、4 份无候选。**

```
2:420:1  → 2:420:11        1:30:7   → 1:90:7（×3）
2:307:1  → 2:307:11        3:188:8  → 9:188:8
8:70:1   → 8:70:11（×2）    3:103:18 → 3:109:18
9:240:1  → 9:240:11        1:87:1   → 1:87:11
```

剩 4 份无候选（含 `5:227:20`，最近的派遣差 578 分钟）—— **无候选就留 UNMATCHED，
这正是想要的行为。**

## 7. 未决

1. **那 4 份无候选的到底是什么** —— 还没定性。可能是更旧的派遣（超出 12 小时窗）、
   也可能是别的读错形态。**不该为了它们放宽任何一条筛**：实验 B 说得很清楚，
   放到距≤2 就开始乱认。
2. **根因在 OCR 那一层** —— 第 4 档是补救，不是修根。`9→3` 那个字形问题
   2026-08-18 记过一次（出发点），这次换到目标上；末位被吞是另一种。
   要修根得看那个 ROI 与二值化，而那要实拍图。
3. **`5:227:20` 那份编辑距离 0** —— 池子里真有一发未认领的 `5:227:20`，
   却没被严格判据认上。说明它落在 `MATCH_TIME_TOLERANCE` 之外或者 origin 不同，
   值得单独看一眼：**那可能是现有第 1 档的一个漏**，和本方案无关。

---

## 8. 排在哪

它和「任务耗时优化」那六件无关，独立可发。规模小（一处判据 + 一档置信度 +
一条日志），但**动的是战报入库那条路**，而那条路上有记录在案的雷
（2026-08-11 那四发：报告在库里、派遣永远停在待战报）。所以：

- 用例要覆盖「唯一 / 歧义 / 无候选」三条，以及「已认领的不许被重挂」
- 变异验证至少两条：去掉窄窗那道筛、把编辑距离放到 2
- 上线后看 `UNMATCHED` 的日增量，和新那一档的置信度分布
