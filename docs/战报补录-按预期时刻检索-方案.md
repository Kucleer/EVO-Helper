# 战报补录：从顺序翻页改成按预期时刻检索 —— 方案（2026-08-21）

用户口径（2026-08-21）：

> 关于战报补录功能，目前的方案是顺序补录。我需要更新成，根据已经派遣缺失的邮件所
> 预期的战报时间，去邮件列表寻找，并且给与一定的秒数误差（±5 秒）。

---

## 一、先说结论：方向对，但 ±5 秒要改成**非对称、分档**

拿生产库实测了 **299 发**（近 4 天、有飞行时间、有战报）：

```
实际战报时刻 − (派出时刻 + 飞行秒数)

中位 −0.9 秒     p10 −2.3     p90 +0.9      ← 绝大多数落在 [−3, +1]
最小 −3.8        最大 +51.7

±5 秒覆盖 292/299 = 97.7%     ⇒ 会漏掉 7 发
±60 秒覆盖 299/299 = 100%
```

**⚠️ 那 7 个不是噪声，是一族，而且成因查清了。**

| 分组 | n | 误差中位 | 范围 | 超出 ±5s 的 |
|---|---|---|---|---|
| **飞行秒数是整分钟**（OCR 把秒丢了） | 6 | **+50.4s** | [−1.3, +51.7] | **4 个** |
| 飞行秒数带小数（读全了） | 295 | −1.0s | [−4.0, +218.9] | 4 个 |

整分钟那一族**全部偏正**，因为 `62分06秒` 只读到 `62分` 时，我们算出来的到达时刻
比真实的早 0–59 秒。⇒ **误差方向是可预测的，不该用对称窗口。**

### ⇒ 建议的容差

```
飞行秒数带小数（读全了，占 98%）      [−10 秒, +10 秒]
飞行秒数是整分钟（秒被丢了，占 2%）    [−10 秒, +70 秒]
飞行秒数为 NULL（读不出）             ⚠️ 没有预期时刻，不能按时间找，走兜底
```

⚠️ **不建议用 ±5**：它只覆盖 97.7%，而漏掉的代价是**永久判成「不在信箱里」**——
补录本来就是最后一道网。±10 把带小数那一族的覆盖推到 99%+，而代价只是偶尔多开一封。

⚠️ **带小数那组的最大值 +218.9 秒没有解释。** 只有 1 例。**不要为它放宽窗口**
（放到 ±220 等于退回顺序翻页），但**要在日志里把「按时间找不到」记下来**，攒够几例
再回来看是不是另一族。

## 二、这个改动省的是什么

⚠️ **省的不是「翻页」，是「开信」。**

`pirate_loop.MailRow` 已经从列表行里解析出 `reported_at_utc` 了，而现在的
`may_be()` **只按主题过滤**，注释里写明它刻意往「开」的一侧倒：

> 漏开一封 = 这一轮少一份报告（侦察白飞、探路白派），多开一封 = 多花八秒。

补录一趟的预算是 **12 屏 / 60 封**。按 8 秒一封算，全开满是 **8 分钟**。
而一趟补录真正缺的通常只有 **3–5 发**。

**⇒ 按预期时刻筛掉不相干的行，一趟从 ~8 分钟压到 ~1 分钟。**

## 三、判据怎么写

### 3.1 新增一道时间闸门，**放在主题闸门之后**

```
这一行值不值得打开 =
      may_be(想要的类型)                    ← 现有判据，不动
  且   matches_any_expected(这一行的时刻)    ← 新增
```

⚠️ **两道闸门都是「往开的一侧倒」，新的这道必须保持同样的倾向：**

- **列表行时间读不出来（实测 6.2%）→ 一律开。** 读不出就没法筛，而不开的代价是永久漏掉。
- **候选集为空（没有缺失的派遣）→ 退回原行为**，不要因为「没有期望时刻」就一封不开。
- **飞行秒数为 NULL 的那些派遣**，没有预期时刻 ⇒ 它们让整个时间闸门失效吗？
  **不。** 让它们**单独走兜底**：只要还有这类缺口，就保留一条「按顺序翻」的通道，
  但**只在时间闸门筛完之后**用剩余预算跑。

### 3.2 候选集怎么建

对每一发「已派遣、无战报」的记录算一个**预期区间**：

```
expected = dispatched_at_utc + flight_seconds
window   = [expected − 10s, expected + (70s 若整分钟 else 10s)]
```

⚠️ **优先用 `attack_dispatches.expected_report_at_utc`**（库里已有这一列，
实测与 `派出+飞行` 的误差分布几乎一样：中位 −1.5s vs −0.9s）。
两者只在极少数行上不同，**取现成的那一列，别自己再算一遍**——那是第二份真相。

### 3.3 ⚠️ 撞车：同一时刻有多发

多条线可能在同一秒前后到达。所以**时间只用来决定「开不开」，不用来决定「这封属于谁」**。

**归属判定一个字都不许改**——仍然走打开之后 VS 块里的坐标（`report_claim` 那套，
PR #204 已经把它放宽成「目标 + 到达窗口」）。时间闸门只是个**预筛**。

### 3.4 区间要合并

10 发缺口就是 10 个区间，很多会重叠。**先合并成不相交的区间集**再拿去比，
否则每一行要比 10 次。

---

## 四、⚠️ 不许破坏的几条

1. **补录仍然只读信箱、只写库，一发都不派。** 这是既有的安全不变量。
2. **去重口径不变**（`has_report_at`），仍与开工那一趟同源。
3. **`is_older_than` 那道早停闸门保留。** 列表按时间倒序，翻到比最早的缺口还旧
   就可以收工——⚠️ 但**早停的锚点要改成「最早的那个预期区间的下界」**，
   不是原来的扫描窗口。
4. **`exhaustive` 模式的语义不变。**

---

## 五、日志（CLAUDE.md 硬要求）

**「按时间找不到」是这个方案最需要留痕的事**，因为它静默失败的样子和
「信箱里本来就没有」一模一样：

```
补录按时刻检索：本趟 N 个缺口 → M 个区间；扫了 X 行，其中
  时间命中 A 行、时间读不出照开 B 行、被时间筛掉 C 行；
  最终认领 D 发，仍缺 E 发
payload: {gaps, windows, rows_scanned, opened_by_time, opened_blind,
          skipped_by_time, claimed, still_missing: [坐标与预期时刻]}
```

⚠️ **`still_missing` 要带上每一发的预期时刻**——那正是回来调容差时要看的数据。
⚠️ 每趟只写一条，**不要逐行写**。

## 六、怎么验

1. **离线回放**：拿库里已有的 299 发做夹具，断言「按预期时刻 + 建议容差」能命中
   ≥99%，并且**整分钟那一族用窄窗口时会漏掉**（这条要转红，证明分档是必要的）。
2. **不许用真实坐标当夹具**——仓库是公开的。
3. **实机验证要等一趟真实补录**，届时看日志里的 `skipped_by_time` 与 `still_missing`。

---

## 七、还没解决的

- **+218.9 秒那一例没有解释**，只有 1 例，本方案不为它放宽，靠日志攒样本。
- **整分钟那一族只有 6 例**，`+50.4s` 这个中位不牢靠。理论上应当均匀落在 [0, 60)，
  实测却挤在 +50 附近——**样本太少，也可能是别的成因**。上界取 70 秒是照
  「理论上不会超过 60」加一点余量，不是拟合出来的。
- **真正的根因是飞行时间 OCR 丢秒**（`62分06秒` 只读到 `62分`）。这个方案是在
  下游兜它。⚠️ **上游修好之后，整分钟那一档就该撤掉**——留着会白开信。
