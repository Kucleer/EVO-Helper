# 数据概览页 —— 方案

用户需求（2026-08-17）：「想看下每天攻击了多少次，扫描了多少球，攻击发出率（被保护或其他停止）等等」。

已定的口径：

1. **发出率同时给 B 和 C 两个**（见下）
2. **不对「没打出去」做归因分类**——只统计总数
3. **按 UTC+0 切天**
4. **统计起点 2026-08-17**

第 2 条是这个方案能轻装上阵的关键：**不加表、不加列、不加迁移**，全部指标从现有数据算得出来。

## 〇、统计起点：2026-08-17

用户口径（2026-08-17）：「数据统计从 8/17 开始计算，算是正式运行」。

**这个日期之前的数据一律不进任何统计**，包括「历史合计」——那一档的含义是「自 2026-08-17 起的合计」，不是「库里的全部」。页面上要把这句话写出来，否则「历史合计」会被当成全量读。

这条不只是划个线，08-17 之前那段确实不该算数：

- `flight_seconds` 里躺着一批垃圾读数（2 系目标记着 `1s`/`4s`/`8s`），是 08-13 收紧解析之前留下的，会把 C 的分子算歪；
- 战报从 08-15 21:40 起两天一份都没读回来，那几天的「战报回收率」是故障值不是业务值；
- 期间有多次人工干预（手动撤回舰队、手动清理航线占用、反复点开始/结束），派遣与占线数据都不干净。

**实现上把起点做成一个常量**，别散在各处查询里；将来若要改（例如再次重置），只改一处。

## 一、指标清单与数据来源

按天一行（UTC 日切），全部来自已有的表：

| 指标 | 来源 | 备注 |
|---|---|---|
| 攻击发出数 | `attack_dispatches`（`accepted IS true`），按 `dispatched_at_utc` | |
| 覆盖坐标数 | 同上 `count(distinct 目标坐标)` | 与上一行的差 = 当天重复度 |
| 攻击意图数 | `attack_intents`，按 `created_at_utc` | 见「发出率 B」 |
| 坐标扫描数 | `coordinate_scans`，按 `scanned_at_utc` | |
| 军力榜采集数 | `bot_targets`，按 `military_score_at_utc` | 同一坐标当天多次采集算多次 |
| 战报回收数 | `battle_reports`，按 `reported_at_utc` | ⚠️ 见「已知会难看的一格」 |
| 战报回收率 | 战报数 ÷ 当天攻击数 | 同上 |

近 7 天实测（2026-08-17）：意图 995 / 派出 819 / 坐标扫描 3,310 / 军力采集 2,692 / 战报 100。

## 二、两个「发出率」

### B：执行成功率 = 派出数 ÷ 意图数

**回答「白跑了多少趟」。** 一条 `attack_intents` 代表「已经决定要打这个目标」，`attack_dispatches` 代表「真的派出去了」。**有意图没派遣 = 走到目标面前但没打成**。

近 7 天：**819 / 995 = 82.3%**，即 176 趟白跑。

⚠️ **口径上的两处限制，必须写进页面注释：**

- `attack_intents` 有唯一约束 `(run_id, target, cycle_start_utc, forced_revisit)`，所以**同一轮里对同一目标的重试不会产生第二条意图**。这个比值统计的是「目标数」不是「尝试次数」，实际白跑的次数只多不少。
- 176 条里混着好几种原因（保护期、军力超标、切星球失败、会话不可用……）。**按用户口径本方案不做归因**，页面上不要暗示它们是同一回事。

### C：产能利用率 = 航线被占用的时长 ÷ 可用航线时长

**回答「资源有没有闲着」。**

#### ⚠️ 2026-08-20 换了分母：改成「周期总时长 × 航线数」

用户口径（2026-08-20）**反转了他自己 08-17 定的那一条**：「我想了一下，把分母换成一天的总时长，这样更能体现利用率。然后再增加一个挂机运行时长。」

```
可用航线时长 = 周期总时长 × 那个周期的航线数
被占用时长  = Σ 每一发的占线时长
```

旧口径（下面那一段）指出的问题**是真的**：关一晚上机器、第二天利用率腰斩，而那不是「资源闲着」，是「本来就没开工」。新口径**把这个问题交给「挂机运行时长」这个新指标去回答**（见 D）。**两个是一对，只做前一半会让页面比改之前更难读。**

用户口径（2026-08-17）：「C 的分母是**任务实际运行时间 × 航线数**」。「任务实际运行时间」= `mission_runs` 每轮 `started_at_utc` → `ended_at_utc` 之和（重叠的要并起来，否则军力榜扫描与 bot 攻击并存时分母翻倍）。

#### ⚠️ 那一天到底配着几条航线：新分母里它是唯一的乘数

旧分母里线数只是其中一个乘数；新分母里**错多少，利用率就错多少倍**。而航线数会变——用户 2026-08-20 当天就把它从 4 条加到 9 条，按 9 条去算 08-15（当时 4 条）会把那天低估到 44%。

用户选定的方案 C（2026-08-20）：

1. **`mission_runs.configured_lines`**（新列，可空）记「这一轮开始时账号一共配着几条线」。**NULL = 不知道**，既不填 0 也不回填此刻的值。
2. **那一列为空的那些天**，线数改用**当天观测到的最大并发在飞数**（占用区间复用 `domain.overview.occupancy_end`，不另写一份判据）。
3. ⚠️ **方向**：**线数取下界 ⇒ 分母偏小 ⇒ 利用率取上界**。历史天会显示得比真实**偏高**，页面上那些格子标「≤」。
4. ⚠️ **页面必须把两种天区分开**（真值 vs 下界推算）。宁可说「这个数不准」，也不能让它假装准。

**一条可以自检的性质**：用最大并发当线数时，利用率**在构造上 ≤ 100%**（任一时刻最多 M 条在忙 ⇒ 占用 ≤ M × 周期长度）。历史天算出 >100% 就是实现有 bug（最典型的写法错误是把重叠区间合并了，那会让最大并发恒等于 1）。有真值那些天**仍然可能 >100%**（配置中途改小、在飞数超过配置数），**那种不许截断**。

#### D：挂机运行时长（2026-08-20 新增）

**回答「那段时间到底开没开工」**，也就是新分母不再替用户解释的那件事。

⚠️ **这个数原本取不到**：`state_events` 全表只有 1 行、写它的路径早删了；而拿 `mission_runs` 的轮次覆盖冒充它会**说假话**——实测 2026-08-20 近 24 小时，轮次覆盖 17.7h、跨度 23.8h，大于 2 分钟的空隙 15 个合计 6.0h，其中 11:45→12:25 那 41 分钟**调度器是开着的**（扫描间隔挡住 RANKING、`waiting_for_a_line` 压住 BOT）。

所以新增 `scheduler_uptime_segments`：**心跳**，一段一行，每分钟把 `last_beat_at_utc` 往前推。⚠️ 刻意**没有「结束时刻」这一列**——进程被杀时没人会写它，而「最后一拍」天然就是右端，挂机时长因此不会在崩溃后一直涨。

⚠️ **历史补不回来**：心跳之前的那些天必须显示「—」而**不是 0**（显示 0 等于说「那天没开机」，那是假话）。

#### 每一发的占线时长从哪来

按现有判据算（`repository._still_holding_a_line` 那三档）：

- 人工放手（`line_released_at_utc`）→ 派出 → 放手时刻
- 有航线钟 → 派出 → `line_free_at_utc`
- 航线钟为 NULL → 派出 → 派出 + `UNKNOWN_LINE_HOLD`（90 分钟）

#### ⚠️ 这个比值会超过 100%，而且那是有意义的

实测（航线数按 7 算）：

| 日期 | runner 运行 | 航线被占 | C |
|---|---|---|---|
| 2026-08-15 | 185 分 | 3146 分 | **243%** |
| 2026-08-16 | 725 分 | 3797 分 | 75% |
| 2026-08-17 | 256 分 | 1434 分 | 80% |

原因是这个分母的固有特性：**舰队在天上飞的时候 runner 不一定在跑**。08-15 只开了 3 小时、派了 42 发，而那些舰队要飞到几小时后才回来。

**处理方式：照实显示，超过 100% 的格子标出来，不要截断。** 它是个真信号——「派出去的活比开机时间还多」意味着**关机太早、舰队回来时没人接**。08-15 那个 243% 正好和「战报从 08-15 21:40 起两天没读回来」对得上。截成 100% 就把这个信号抹掉了。

页面上给这一格一句悬停说明，别让人以为是算错了。

#### ⚠️ 第三档会让 C 虚高

飞行时间读不到时按 90 分钟计，而真实往返只要 40–65 分钟（实测 2026-08-17）。所以 C 里有一部分是**被白占的**，不是真的在干活。页面上要把「其中按 90 分钟兜底的有几发」单独列出来，否则这个数会把「浪费」显示成「产能」。

（这一条与 `docs/预计战报时间-估算方案.md` 是同一个根因，那边修好之后 C 会自动变准。）

## 三、聚合口径：天 / 周 / 月 / 历史合计

用户口径（2026-08-17）：「数据统计要有按天/周/月/历史合计」。

四档共用同一套指标，只换聚合粒度：

| 档 | 边界 | 默认给多少 |
|---|---|---|
| 天 | UTC 自然日 | 最近 14 天 |
| 周 | **ISO 周（周一起），按 UTC** | 最近 8 周 |
| 月 | UTC 自然月 | 最近 6 个月 |
| 历史合计 | 自 2026-08-17 起全部 | 一行 |

⚠️ **周口径要写明是「周一起」**：周一是 bot 刷新日、全服都在打，保护期跳过会大量增加。周边界压在周一，那一天的异常才不会被劈到两周里，趋势才看得出来。

⚠️ **比率列不能对天求平均**。周/月的 B、C 必须**先把分子分母各自求和再相除**，不是把每天的百分比平均一遍——那两个算法在天数不齐、量级不齐时会给出不同的数，而且后者是错的。这条要有用例钉住。

## 四、页面

新开一页「数据概览」，导航栏加入口。每行一天，倒序，默认给最近 14 天，粒度可切换。

- 时间一律标 **(UTC+0)**，并在页首写明「按游戏日切，与配额口径一致」——⚠️ 全站其它页面显示的是 UTC+8（用户口径 2026-08-17），**这一页是例外**，不写清楚会被当成同一套时区读。
- 每个指标一列，鼠标悬停给口径说明（尤其 B 和 C 的限制）。
- 全部在 SQL 里按天聚合，不要把行拉回 Python 再分组——`coordinate_scans` 一天三千多行。
- ⚠️ **按 UTC 切天在 PostgreSQL 上不能用 `func.date()`**：它按会话时区换算，服务器在 UTC+8 时日界会整体挪 8 小时。2026-08-17 切 PG 时正是在海盗配额那条链路上抓到了这个 bug（见 PR #159），那边新加的 `_utc_day` 可以复用。

## 五、已知会难看的一格

**战报回收率在 08-15 到 08-17 之间是 0%。** 那段时间战报一份都没读回来（两道默认关闭的闸门叠在一起，修复见 PR #158）。

**这不是要遮的，恰恰是这一页存在的理由**——那个故障安静地跑了两天没人发现，而这一页会让它在第一天就变成一个显眼的 0。

## 六、不做的

- **不做归因分类**（用户口径）。要做的话得先给「这一发为什么没派」建结构化记录，那是另一件事，且要动 schema。
- **不做实时刷新**。这是按天聚合的回顾页，不是监控页。
- **不做图表**。先把数字摆对，形状以后再说。
