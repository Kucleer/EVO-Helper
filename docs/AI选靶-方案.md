# 用 LLM 选攻击目标 —— 方案（2026-08-19）

用户口径（2026-08-19）：

> 代码所有可能影响决策的变量整理成 prompt 给到 LLM，然后 LLM 返回指定的格式，
> 然后控制台按 AI 返回来发出攻击。先整理一个方案，**第一期甚至可以只接入 LLM
> 看 AI 的返回对比当前的选择**。

一期就是**影子模式**：照常按现有算法派遣，同时把同一份输入喂给 LLM、把它的答案记下来，
**不据此动一根手指**。

---

## 一、⚠️ 先说天花板，免得投入之后才发现打错了地方

这一整天的实测里，**收益提升几乎全部来自「感知」和「管道」，不是「排序」**：

| 改了什么 | 提升 |
|---|---|
| 航线利用率 40.3% → 99.2%（管道） | 实际稀有产出 **×3.4** |
| 军力榜扫描加深，本地银河从 0 个新鲜读数变成 17 个（感知） | 近目标 0 → 13 个 |
| 飞行时间 OCR、战报认领、行星列表回顶（感知） | 每天挽回约 10 航线小时、713 发未认领战报 |
| **把拟合出来的系数接进排序**（排序） | **+7.0%** |

最后一行是关键：拿 45 份实测拟合出 `稀有 ≈ 1.31 × 军力^0.79 × exp(−0.115×龄)`，
**用它替换现在的 `军力^1.0 ÷ 往返`，模拟出来只提升 7%**。也就是说**现有排序已经在
拟合最优的 93% 上**。

**LLM 接在排序层，天花板就是那 7%。** 这不是反对做，而是说：

> **一期的价值不在「LLM 能不能选得更好」，而在「LLM 能不能看出池子有问题」。**

今天最值钱的几个发现都是这一类，而**公式在结构上说不出它们**：

- 「候选池里 514/518 个都是跨银河」——公式照样能排序，排出来的是矮子里拔将军；
- 「9 系 6 小时内新鲜读数 0 个」——公式看到的是「这个银河没候选」，说不出「是扫不到」；
- 「撞保护期的 11 个精确占满排名前 11」——公式没有「排名前缀」这个概念。

**一个读得懂池子摘要的 LLM 能把这些当场喊出来。** 所以一期的输出里，
「异常判断」这一项和「选哪几个」同等重要，甚至更重要。

## 二、现在的决策用到了哪些变量（完整清单）

按四步流水线（`domain/target_order.py` 的模块头）：

### 第 ① 步 排除（`application/mission_scheduler._military_candidates`）

| 变量 | 来源 | 旋钮 |
|---|---|---|
| 近 N 小时内已攻击过的坐标 | `attack_dispatches`（`accepted`） | `bot_revisit_hours`，默认 24h |
| 撞过保护期的坐标 | `bot_targets.protection_seen_at_utc` | `protection_exclusion_hours`，默认 8h |
| 本轮已走完的 | `bot_dispatch_facts_many(since=round_started_at_utc)` | — |

### 第 ② 步 有没有可用读数（`has_a_military_reading`）

| 变量 | 说明 |
|---|---|
| `military_score` 是否为空 | 从未上过军力榜的不打（实测 638 个，占 bot 总数 17%） |
| `military_score_at_utc` 是否为空 | 说不清何时读的 → 进不了窗口 |
| **读数是否早于本周期起点** | 周一 UTC+0 刷新后上周的读数全部作废（PR #212） |

### 第 ③ 步 新鲜度窗口（`within_score_window`）

| 变量 | 旋钮 |
|---|---|
| 读数龄 < `max_age` | `score_max_age_hours`，当前 6h |
| 窗口内不足 `window_floor` 就放弃窗口并告警 | `top_n`，当前 500（**同时决定军力榜一轮采多少个**） |

### 第 ④ 步 打分与分配

| 变量 | 说明 |
|---|---|
| 得分 = `军力^1.0 ÷ 往返小时` | `MILITARY_EXPONENT` 写死 1.0 |
| 往返小时 | `domain/flight_time`：`D = 跨银河 ? 20000×银河环距 : 1162 + 31.71×恒星系环距`；`单程秒 = 2 + k·√D`，**k 按出发星球标定**（PR #216） |
| 安全线 `max_score` | 当前 70000，军力高于它不进池 |
| 每星球航线预算 | `mission_task_origins.fleet_lines` − 在飞（判据 `_still_holding_a_line`） |
| 全账号航线上限 | `account_line_limit`，当前 10 |
| 出发星球轮换 | `last_dispatch_at` 最久远的那颗，**刻意不按价值**（否则弱的那颗永远饿死） |
| 预设档位 | `tiers_json`：≥60000→CCC，≥20000→BBB，≥10000→AAA，其余 fallback |

## 三、我们已经量出来、但**还没进公式**的

这些是 LLM 相对公式的真正信息优势——喂给它就能用，改公式则要改代码。

| 已知 | 出处 |
|---|---|
| `稀有 ≈ 1.31 × 军力^0.79 × exp(−0.115×快照龄)`，R²=0.728，n=45 | [`军力数据有效期-方案.md`](军力数据有效期-方案.md) |
| **衰减项完全不在现有打分里**：龄 6h 的目标产出只剩 50%，排序上却和 0.4h 的一视同仁 | 同上 |
| 近弱 vs 远强的平衡点 `军力比 = 往返比^1.27`；D2–D3 实测近的每航线小时高 **56%** | [`近弱还是远强-实测.md`](近弱还是远强-实测.md) |
| **周内相位**：D1 竞争最激烈、新鲜度最值钱；D4–D7 才轮到「近弱 vs 远强」 | [`周内相位-策略模型.md`](周内相位-策略模型.md)（**尚无数据支撑，是领域直觉**） |
| 撞保护期集中在 4 系、且精确占满排名前 11 | [`保护期撞上-调查.md`](保护期撞上-调查.md) |
| 打得更狠不会多拿稀有材料（我方单位系数 +0.03，R² 不变） | [`军力数据有效期-方案.md`](军力数据有效期-方案.md) |

⚠️ **用户口径：分析一律不考虑单位数量，我方与敌方都不考虑。** prompt 里不许出现这两个量
——违反它的直接后果记在那份文档里（军力系数会拟出 −0.557 这种荒谬值）。

## 四、一期：影子模式

### 4.1 挂在哪

**挂在控制台（`application` 层），不挂 runner。**

理由：这是「决定打谁」，而 runner 只负责「去点」。控制台本来就有库、有全部候选池账目
（`_military_pool_reading` 每轮算一次），而 runner 跑在另一台机器上、还占着鼠标。

触发点：`_military_assignments()` 算完之后、命令行组好之前。**读一份、记一份，不改返回值。**

### 4.2 ⚠️ 候选池放不进 prompt，必须先裁

实测候选池 **3784 个**（窗口内 909 个）。全塞进去既贵又没用。裁法：

1. **按现有得分取前 60 个**（覆盖了一轮最多派 10 发的所有现实选择）；
2. **另附整池的统计摘要**——这一半才是 LLM 的用武之地：
   - 按往返时长分档的个数（`≤30 / 30–60 / 60–90 / 90–120 / ≥120 分`）
   - 按银河分的个数与军力中位
   - 读数龄的分布（中位 / p90 / 最大）
   - 窗口内个数 vs 窗口门限（是否放宽了）
   - 被第 ① 步排除掉的数量与原因分布

⚠️ **裁剪本身要写进 prompt**：告诉 LLM「你看到的是按现有算法排名的前 60 个，
不是全池」，否则它会把「前 60 名都很远」误读成「全池都很远」。

### 4.3 prompt 里要给的（分四块）

```
【当前局面】
  现实时刻 / UTC+0 日期 / 本周期起点（周一）/ 今天是刷新后第几天
  各出发星球：配置航线数、在飞、时长未知、最早空出
  全账号航线上限与已占用
  这一轮最多能派几发

【候选（前 60）】
  坐标 / 军力 / 读数龄(h) / 从每个可用出发点的往返分钟 / 现有得分与排名
  / 上次被我方攻击距今(h) / 是否撞过保护期

【整池摘要】
  见 4.2 第 2 点

【已知规律】（我们量出来的，逐条给出 n 与 R²）
  收益曲线、平衡点公式、周内相位（标注「尚无数据支撑」）、
  撞保护期的分布、"不考虑单位数量"这条口径
```

### 4.4 返回格式（严格 JSON，schema 校验）

```json
{
  "picks": [
    {"target": "3:98:12", "origin": "4:277:15", "rank": 1,
     "reason": "军力 31,820、读数龄 0.3h、往返 125 分；同价位里读数最新"}
  ],
  "pool_warnings": [
    {"severity": "high",
     "finding": "前 60 名里 58 个是跨银河（往返 ≥120 分），近目标只有 2 个",
     "suggested_check": "9 系 6 小时内新鲜读数是否为 0"}
  ],
  "confidence": "high | medium | low",
  "notes": "一句话说清这一轮的主要取舍"
}
```

- `picks` 长度 = 这一轮能派的发数，**不许多给**；
- `target` / `origin` 必须来自输入里给过的集合，**校验不过就整份丢弃**并记日志；
- **`pool_warnings` 是一期的主产出**，见第一节。

### 4.5 ⚠️ 怎么评估——先说清一个绕不过去的限制

**影子模式观察不到反事实。** LLM 选了 A、我们打了 B，A 的收益**永远不知道**。
所以一期能得到的只有三样：

1. **重合率**——LLM 与现有算法选中同一批的比例。⚠️ 重合率高**不代表** LLM 好，
   只代表它没说反话；重合率低也不代表它错。**这个指标只能用来发现「它压根没在按规则做事」。**
2. **重合部分的事后表现**——两边都选中、且我们真打了的那些，收益如何。
   这能验证「LLM 给出的理由和实际结果对不对得上」。
3. **`pool_warnings` 的命中率**——它喊出来的异常，人工复核有几条是真的。
   **这一项是一期真正的验收标准。**

**要真比出高下必须 A/B**：按轮次交替用两套决策，比较各自的每航线小时产出。
那是二期，门槛见第六节。

### 4.6 记什么

新增一张表（或先落 `system_log` 的 `payload_json`，一期够用）：

```
轮次 id / 时刻 / 现有算法选中的 / LLM 选中的 / 重合数
/ LLM 的完整返回 / prompt 的 token 数 / 延迟 / 模型与版本
```

⚠️ **prompt 与返回要原样存**。模型换一个版本答案就可能变，事后复盘时
「当时喂进去的到底是什么」是唯一能对账的东西。

## 五、安全边界（一期）

- **一期绝不影响派遣。** LLM 的返回只进日志，`_military_assignments()` 的返回值一个字不动。
  这一条要有用例钉住：**注入一个返回垃圾的假 LLM，断言派遣结果与没接时逐字相同。**
- **调用失败一律静默降级**：超时、限流、JSON 校验不过 —— 记一条日志，照常按算法派。
  ⚠️ 绝不能因为 LLM 挂了让攻击停摆。
- **限流**：一轮最多一次调用；`_facts` 每 tick 都会走，**绝不能挂在那里**（页面轮询也会走）。
- **不发送敏感数据**：坐标和军力要发（否则没法选），但**账号名、玩家名一律不发**。
  ⚠️ 仓库是公开的，prompt 模板会进 git——模板里不许出现任何真实坐标当例子。
- **成本可关**：一个开关能整个停掉，默认**关**（同 `AUTO_ENABLED` 的惯例）。

## 六、成本与二期门槛

**一期成本**（按当前节奏 20–26 轮/天）：

```
prompt ≈ 4–6k token（60 个候选 + 摘要 + 规律）
输出   ≈ 0.5–1k token
每天   ≈ 25 轮 × 6k ≈ 150k token/天
```

按当前主流定价是每天几毛到几块钱的量级，**成本不是障碍**。

**进二期（真的按 LLM 的结果派）的门槛，建议定死在这里**：

1. 一期跑满 **两个完整周期（两周）**——因为周内相位是这套东西最可能出错的地方，
   而一周只产出一个 D1；
2. `pool_warnings` 的人工复核命中率 **≥ 50%**，且**至少喊对过一次我们没发现的问题**；
3. JSON 校验通过率 **≥ 99%**；
4. 二期不是「全量切换」，而是 **A/B 交替**，并且**保留一键切回**。

⚠️ **不建议跳过一期直接做 A/B。** 理由是第一节那个天花板：排序层能拿的最多 7%，
而 A/B 要跑很久才能在这个量级上做出统计显著——**先用一期确认「它到底能不能看出
公式看不出的东西」，那才是它值不值得接的真正判据。**

## 七、这个方案没解决的

- **反事实观察不到**，一期结构性地无法证明「LLM 选得更好」（4.5）。
- **周内相位那几条规律本身还没有数据支撑**（领域直觉），喂给 LLM 等于把一个未验证的
  先验写进 prompt。**必须在 prompt 里标注它的证据强度**，否则 LLM 会把它当事实用。
- **候选池的裁剪可能把 LLM 想要的信息裁掉了**——它看不到第 61 名之后的任何东西。
  一期先接受，二期可以让它主动要（"再给我 30 个往返 ≤60 分的"）。
- **决策的可复盘性会变差**。这个仓的惯例是「判据只能有一份、出事能只靠库里的日志定位」，
  而 LLM 的输出天然带随机性。**这是接入它的真实代价**，不是可以绕过去的实现细节。
