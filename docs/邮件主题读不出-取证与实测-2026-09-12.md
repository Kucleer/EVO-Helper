# 信箱列表页「主题读不出」 —— 取证与实测（2026-09-12）

**一句话**：白开是**框切的**，不是配方糊的。同一批像素、同一套 OCR 配方，只把整行
ROI 的纵向原点换成按这一行自己的时刻带对齐，主题认出的行数就从 **22/42 涨到 32/42**。

这一版**只加取证，一个判据都没改**。换不换框要等实机裁片，理由见 §5。

---

## 1. 现象（生产库，用户 2026-09-12 夜实测）

开封之后读不出东西的比例，在回收派遣上线那天翻了三倍多：

| 日期 | 开封 | 入库 | VS 读不出 | 白开率 | 当天回收派遣 |
|---|---|---|---|---|---|
| 09-08 | 505 | 204 | 16 | 3% | 0 |
| 09-09 | 503 | 203 | 28 | 6% | 0 |
| 09-10 | 371 | 199 | 35 | 9% | 0 |
| 09-11 | 314 | 100 | 92 | **29%** | 88 |
| 09-12 | 199 | 80 | 62 | **31%** | 76 |

当晚 21:22–22:37 这 65 分钟：开封 58 封 → 入库 7 封、白开 50 封，**约 8 分钟白花，
占挂机时长的 12%**。

58 封里 **55 封的主题读数连「攻击报告」「海盗」字样都没有**，读成
`'TTT     seesere'` / `'一一 band a | rt rm kar Ae'` / `'~~ ae te'`。于是：

1. 主题闸 `MailRow.may_be(wanted)` 拿不到可识别的主题，拦不住（`UNKNOWN` 一律照开）；
2. 未读必开那一条把它开了；
3. 开出来是「舰队返回」，没有 VS 块 → 白开。

⚠️ **这里有一个容易搞反的因果**：主题读不出**不是 09-11 才开始的**，变的是它的
**代价**。回收链路上线之后信箱里「舰队返回」的量大增（评估文档记的比例约 2:1），
于是同样一行读不出的主题，以前开出来多半真是一份战报，现在多半是一封舰队返回通知。
下面 §3 的实测支持这个读法：同样的失效在 09-08 的那几屏实拍上就已经在了（42 行里 20 行读不出），
而那几天的白开率只有 3–9%。

## 2. 原假说，以及它为什么不成立

当时手上的假说是**配方**：

> 生产读一行用 `ReportLayout.mail_row(index)` → `Region(700, 205, 1220, 290)`，整行
> 520×85 全框，`OCR_UPSCALE = 2`，不二值化；而 2026-09-12 采回收语料时用主题窄条
> `(820, 256+86i, 1000, 282+86i)` + `upscale=4, threshold=120`，主题读得干干净净。
> 三处差异：框宽 3 倍、放大 2× vs 4×、有无二值化。

两条都不成立：

1. **那个「同一块屏幕区域」不是同一块屏幕。** 回收语料
   （`var/fixtures/vision/recycle-mail/*.png`）是**邮件详情页**的整帧，
   `(820, 256, 1000, 282)` 读的是详情页页眉那行「主题: 回收报告」——大字、高对比、
   固定位置、每帧只有一行。列表页那六行是另一回事。
2. **配方不是主因。** 把三处差异逐个试过（见 §3.2），最好的一档也没赢过生产那一档；
   而**只换 ROI 的纵向原点**、配方一个字不动，收益立刻出来。

## 3. 实测

### 3.1 样本

主仓 `var/` 下七屏信箱**列表页**实拍，42 行，真值人眼核过（全是「攻击报告」，
`var/mail-list.png` 第 0 行是「矮星系统战报」）：

- `var/logs/sample-mail{box,unread-03,unread-04,unread-05,unread-11,-down4}-*.png`（2026-09-08）
- `var/mail-list.png`（2026-09-12 16:49）

⚠️ **实拍不进 Git**，所以这张表在仓库里复算不了。复算的入口是
`tests/integration/vision/test_mail_row_alignment_live.py`——主仓有图时跑，
worktree 里整条 skip。判据用生产那一条 `classify_report_subject`。

七屏的**离网格量**（时刻带顶 − 名义行顶）铺得很开：`10, 11, 23, 24, 25, 26, 27,
38, 39, 48, 49, 81, 82`。选它们正是因为这个自变量铺得开。

### 3.2 配方那一侧（对照组，全部失败）

| 配方 | 主题认出 |
|---|---|
| **生产：整行 520×85 / psm6 / u2 / 无阈值** | **22/42** |
| 整行 / psm6 / u4 / 无阈值 | 21/42 |
| 整行 / psm6 / u4 / t120 | 21/42 |
| 自对齐主题窄条 / psm7 / u4 / t120 | 18/42 |
| 自对齐主题窄条 / psm7 / u3 / t120 | 15/42 |
| 自对齐主题窄条 / psm7 / u4 / t150 | 5/42 |
| 自对齐主题窄条 / psm7 / u4 / 无阈值 | 3/42 |
| 自对齐主题窄条 / psm7 / u2 / 无阈值 | 1/42 |

窄条那一族输得最惨，而这正是假说押的那一档。

### 3.3 框那一侧（主因）

把**同一套生产配方**喂给一个上沿取「这一行自己的时刻带顶 − `dy`」的框：

| ROI 纵向原点 | 主题认出 | 时刻读出 |
|---|---|---|
| 名义行顶（今天生产用的） | 22/42 | 35/42 |
| 自对齐，`dy = 48` | **32/42** | **41/42** |

`dy` 不是调出来的：39 / 45 / 48 / 54 / 60 五档跑下来是 33 / 32 / 32 / 31 / 31，
差一行的抖动而已。

### 3.4 分档之后，因果一眼看得见

| 离网格量 | 行数 | 名义 ROI 认出 |
|---|---|---|
| ≥ 30 | 18 | **17**（94%） |
| < 30 | 24 | **5**（21%） |

而那 5 行还是**读到了下一行的主题**（偏移 +10 / +11 时自己的主题整条在框外），
只因为同屏主题都一样才没露馅。

## 4. 根因

一行邮件的三段文字**各自的墨迹**相对时刻带顶（42 行实测，41 行一致）：

| 段 | 相对时刻带顶 |
|---|---|
| 主题 | −30 .. −18 |
| 发件人 `System` | −18 .. +3 |
| 时刻 | 0 .. +9 |

**加起来只有 39 像素**，而名义行 ROI 高 85、行距 86。也就是说一行里有 46 像素是空的，
而**那 46 像素全在文字下方**——文字挤在行的上三分之一。

⇒ **名义 ROI 向上一个像素的余量都没有。** 列表一离网格，主题就被 ROI 上沿横着切掉。

⚠️ `_mail_time_bands` 原先的注释写着「`mail_rows()` 的 OCR 不受漂移影响，因为它的
ROI 有 85px 高、装得下这点漂移」。**这句话是错的**，这一版当场改掉了。85px 不是余量，
是「文字 39px + 下方空白 46px」。

## 5. 这一版做了什么（以及**没**做什么）

### 做了：取证

`PirateLoop._record_unreadable_subject_evidence`，接在 `_mail_list_rows` 上，
**默认开**（与未读色那条标定探针相反，理由写在方法上）。一屏有主题读不出的行就记一条
`WARNING`，`message = 信箱列表页主题读不出`，里面三样：

| 记什么 | 谁读 | 答什么 |
|---|---|---|
| `title_band_offset`（离网格量），**每一行都有** | 机器 | 框切了没有 |
| `aligned_subject` / `aligned_kind`（同一帧自对齐重读） | 机器 | 换框救不救得了这一行 |
| `mail_row_png_base64`（**原分辨率**裁片） | **人** | 这几个字本该是什么 |

名额：文字一个进程 12 屏（`MAX_MAIL_SUBJECT_EVIDENCE`）；裁片与重读**一条记录只给
两行**（`MAIL_SUBJECT_EVIDENCE_CROPS`，一行裁片 ≈69 KB，一次重读是一次真 OCR），
跨轮那一半归 `EVIDENCE_FRAME_INTERVAL_S`。名额先给未读行——白开的成本由它们付。

捞出来：

```
python -m evo_helper.tools.mail_subject_evidence --out var/fixtures/vision/mail-subject
```

它打印「被切掉 vs 框本来就对」的分档，以及自对齐重读的战绩，并把裁片落成 PNG。

### 没做：换框

`mail_rows()` 与 `ReportLayout.mail_row` **一个字都没动**，`may_be` 的取舍也没动
（主题读不出仍旧 `UNKNOWN`、仍旧照开）。

⚠️ **主题读不出绝不能倒向「不开」。** 那样一封主题被糊掉的**真战报永远不会被开**，
代价是丢战报，比白开八秒严重得多。正确方向是把主题读准。

## 6. 还没验的，写明不藏

1. **这批实拍里一行「舰队返回」都没有。** 42 行全是「攻击报告」/「矮星系统战报」。
   而 09-12 那一夜白开的那 50 封主要是舰队返回。漂移这个机制与主题内容无关，
   但「舰队返回那四个字在这套配方下读不读得出」**这批语料答不了**——
   要等 §5 那条取证在实机上采回裁片。
2. **自对齐救不回来的那 10 行是另一个问题。** 列表上下沿真的只露了半行，
   以及背景透上来的幽灵字。配方那一侧还值不值得动，同样要等裁片。
3. **点击坐标仍然按名义行算**（`MAIL_FIRST_ROW_Y + index * MAIL_ROW_PITCH`）。
   真要换框，得一并想清楚「读的是第 i 行、点的是不是第 i 行」——离网格 +82 那一档
   上这两件事本来就已经不完全是同一行了（`_mail_time_bands` 的「残余风险」那一段）。
