# 回收接在调度的哪儿（设计，2026-09-10）

第四轮评审（Codex）指出：**六份文档一致地说了「触发点是航线释放」，却没有一份回答
「谁在什么时刻做这个决策、回收动作由哪个进程去点」。** 本文补这一页。

⚠️ **这是第 3 步（节奏 + 派遣链路）的前置**。在它写清楚之前，第 3 步的估时不可信。

---

## 1. 三条代码事实，决定了答案不能随便选

全部核对过（`main @ 1ed5582`）：

| 事实 | 出处 | 后果 |
|---|---|---|
| **「航线释放」是调度器每 tick 现算的状态** | `mission_scheduler._facts` / `_account_free_lines` | ⚠️ **运行器看不见它** —— 只有调度器能做 `acc` 决策 |
| **运行器一轮只站一颗出发星球** | `mission_scheduler.py:3522` 原话：「**『整轮只跑一颗星球』不是可以放宽的实现细节**。一个游戏窗口、一只鼠标」 | 回收要点游戏界面，只能发生在**某颗星球的某一轮里** |
| **哪颗星球轮到出兵按公平性决定** | `_origin_taking_its_turn`（3574）：「分到了目标的那些里，**上次出兵最久远的那颗**」 | ⚠️ **线刚空的那颗未必是下一轮** |
| 轮内已派数只数攻击成功 | `bot_loop.py:541` `if self._attack_once(...): dispatched += 1` | 回收派出后不计入 `max_dispatches`，**轮会超派** |

### ⚠️ 所以我先前那句话是做不到的

`流程图.md` v2 §3 写着「**用那一发攻击的出发星球、那一条刚空出来的线**」，
读起来像「线一空就立刻在那儿派回收」。**运行器做不到**：
它一轮只站一颗星球，而站哪颗由公平轮换决定，不由「谁的线刚空」决定。

## 2. 改成三段，中间加一个「回收作业」

    ① 调度器 tick
         对「已释放、且还没决策过」的攻击派遣做 acc 决策
         → 决策行落库（幂等键 = 来源 dispatch_id）

    ② 选中的那些
         → 生成一条**回收作业**：坐标、出发星球、来源 dispatch_id、生成时刻

    ③ 那颗星球**下一轮**运行器起来时
         命令里**先带回收作业、再带攻击目标**
         预算按**实际派遣**扣，不分任务类型

⚠️ 中间这个「回收作业」是新东西，但它是**必需**的：
决策发生在调度器、动作发生在运行器，而两者之间隔着一次公平轮换，
**没有一个持久的中间物就接不上**。

## 3. 五个问题的答案

### 3.1 决策在调度器哪个位置执行

**在 `_facts` 之后、`_launch` 之前，每 tick 扫一次。**

- 放 `_facts` 之后：那时航线占用刚算完，`_still_holding_a_line` 的结果现成
- 放 `_launch` 之前：决策要影响这一轮的命令
- **每 tick 扫**而不是只在起轮前：航线释放和起轮不同步，
  只在起轮前扫会漏掉「释放了但这一 tick 没起轮」的那些

⚠️ 扫的范围：**`mission_kind = ATTACK` 且已释放且没有决策行的**。
按 `dispatch_id` 左连决策表，取空的那些。

### 3.2 回收作业怎么进运行器命令

**`bot_command` 加一个 `--recycle` 参数**，与 `--targets` 并列：

    python -m evo_helper.tools.bot_loop --targets 9:243:7 9:252:5 --recycle 4:277:14

⚠️ **不新建 `MissionKind`**。理由：新建一种任务就要有自己的调度、自己的轮换、
自己的预算，而回收**必须和攻击共用同一条线、同一颗星球的同一轮**（用户口径）。
新建 kind 等于把它们拆开，正好和需求相反。

⚠️ 运行器里**回收先于攻击**执行：回收的目标是已知的、不用挑，
而攻击那一组还要过保护期等闸门；先做确定的那件，失败也不影响后面。

### 3.3 预算

**回收占用 `max_dispatches` 的一个名额**，并以 `mission_kind = RECYCLE`
写进 `attack_dispatches`。

这样两件事自动成立：

1. `_still_holding_a_line` 把它算进账号级空线数（它不看 `mission_kind`）
2. 下一 tick 的 `_account_free_lines` 自动少一条

⚠️ `bot_loop._sweep` 那个 `dispatched += 1` 要改成**按实际派遣计数**，
不分任务类型 —— 这就是评审 §1.5 说的「规则对两条入口通用」。

### 3.4 幂等键怎么传

    来源攻击 dispatch_id
      → 决策行（唯一键）
        → 回收作业（外键）
          → 回收派遣行 attack_dispatches.source_dispatch_id（新列）

⚠️ **每一段都带着它**，这样任意一段重放都不会重复派。
「空线」是现算状态不是事件，不这么串就防不住重启重放（评审 P2#5）。

### 3.5 作业过期吗

**要过期。** 决策做了但那颗星球好几轮没轮到时，残骸可能已经被别人收走。

⚠️ 但**过期不回退 `acc`**（同 `节奏滑块.md` §3.5 的口径：滑块管尝试不管成功）。
过期只是不再执行，并**记一条原因**，让页面上的「跳过原因」那一列分得出
「去了没残骸」和「压根没轮到」。

⚠️ **过期时长待定** —— 它取决于「残骸会不会衰减」，而那一条至今未知
（`设计.md` 表 1 第 8 项）。⇒ **先设一个保守值并落成可配置，不要写死。**

## 4. 顺带解掉了 README §6.2「要不要攒批」

**批就是「那颗星球的下一轮」。**

切星球那 37.8 秒是**每轮付一次**，不是每次回收付一次。
所以不需要另设计攒批机制 —— 三段结构自带批处理。

⇒ `流程图.md` §3 的 **R1「出发星球还在当前视图吗」在这个结构下恒为「是」**
（运行器开工时 `ensure_origin_planet` 已经切好了）。那个分支可以去掉。

## 5. ⚠️ 一个要写明的副作用

`last_dispatch_at(target_kind, *, origin)` 按 **`AttackIntentRow.target_kind`** 过滤，
**不看 `mission_kind`**（`repository.py:2166`，核对过）。

⇒ **回收派遣会刷新那颗星球的「上次出兵」时刻**，把它排到公平轮换的队尾。

这**大概是想要的**（它确实占了那颗星球的线、确实用掉了一轮），
但它是一个不写下来就没人知道的行为：拉高滑块会让**出兵频率在各星球间重新分布**。

## 6. 入口 A 走同一个 `acc`

评审 §4.2 的建议，采纳：

    攻击被拒（保护期）→ acc >= 1 ? → 是：acc -= 1，就地读面板找「回收」按钮
                                   → 否：跳过，照旧下一个目标

这样「滑块管尝试节奏」对两条入口语义一致，**`r = 0` 自动禁止入口 A**，
不需要给它单写一条规则。

⚠️ **未决：入口 A 的幂等键。** 攻击被拒时**没有 `dispatch_id`** ——
`attack()` 里的弹窗检查发生在 `_record_intent` **之前**，连意图 id 都还没有。
⇒ 只能用 `(坐标, protection_seen_at_utc)` 这一对。**这一条我没有验过它够不够唯一。**
