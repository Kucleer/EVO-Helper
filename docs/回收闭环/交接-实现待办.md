## ⚠️⚠️ Bug 1：`since` 拿「决策时刻」去比「派遣时刻」

### 代码

```python
# application/mission_scheduler.py，_scan_recycle_decisions
acc, last_decided = self._repository.recycle_acc_state()
since = last_decided or (now - timedelta(hours=1))     # ← last_decided 是**决策**时刻

# storage/repository.py:4164
orm.AttackDispatchRow.dispatched_at_utc >= since       # ← 比的是**派遣**时刻
```

**两个不同的钟。**

### 生产数据（2026-09-10 22:12 取）

```
唯一那条决策      21:13:30
之后的派遣        21:25  21:27  21:29  21:35  22:06
它们的航线释放    22:22  22:36  22:34  22:41  23:10
现在              22:12         ← 一条都还没释放
```

### 棘轮效应

一发攻击**约 1 小时后**才释放、才够格被扫到；而那时 `since` 已经被后来的决策
推到了它的**派遣时刻之后** ⇒ **它永远出局，再也不会被扫到。**

⇒ **`r = 1.0` 实际退化成「每个释放周期最多 1 条决策」（≈ 1 次/小时）**，
而不是每发攻击一次。22 发 → 1 条，数字完全对得上。

### 修法

开发方案 E2 原文就写着：**「开启时刻落库，作为决策记录的下界」** —— 是一个
**固定**的下界。现在的实现从 `last_decided` 推，于是它一直往前爬。

⇒ 落一个**启用时刻**（滑块从 0 调到非 0 的那一刻写一次），用它当固定 floor；
去重继续靠现成的 `id.not_in(decided)`，那一条本来就是对的。

### ⚠️⚠️ 改的时候必须注意

库里现在有 **3919 条**「已释放且未决策」的历史派遣。

    直接去掉 since  ⇒  一次生成 3919 条决策 ⇒ 3919 条待执行作业

**必须先把启用时刻落库再放开这个条件。** 已经打开着的这次，
启用时刻可以取「`rate_tenths` 被改成 10 的那一刻」附近的一个保守值
（比如那条唯一决策的 21:13:30），别取 0。

## ⚠️ Bug 2：两张新表的时刻列建成了 `timestamp WITHOUT time zone`

```
recycle_decisions.decided_at_utc    → timestamp without time zone   ⚠️
recycle_jobs.created_at_utc         → timestamp without time zone   ⚠️
attack_dispatches.dispatched_at_utc → timestamp WITH time zone      ✅（别的表都是）
```

迁移 `e5a8c3d2f1b4` 第 48 / 77 行写的是 `sa.DateTime()`，
而本仓其余时刻列用的是 **`UTCDateTime`**。

### 后果

写进去的 aware UTC 被按**会话时区**转成 `+08` 墙钟再丢掉时区 ——
库里那条存的是 `21:13:30`，而当时 UTC 是 `13:13:30`。

**现在靠「写和读走同一个会话时区」侥幸抵消掉了，没出错。**
⚠️ 但只要会话时区变一次，或者哪天拿它跟一个 aware 时刻在 Python 里比较，
就会错 **8 小时**；而列名叫 `_utc`、内容却不是 UTC，这本身就是个陷阱
（下一个读这段代码的人一定会当它是 UTC）。

⇒ 改成 `UTCDateTime`，配一个迁移把已有行按 `+08 → UTC` 修正。
⚠️ SQLite 上改列要 batch mode；**推前拿远端 `evo_helper_test` 单独验一次**。

### 附1. ⚠️⚠️ 三档生命周期的盲区 —— 三档生命周期有个盲区，而且它让 R23 失效

三档全塞在 `repository.pending_recycle_jobs()`（`repository.py:3994`）里，而那个查询是：

```python
.order_by(orm.RecycleJobRow.created_at_utc.desc())   # 新的先
.limit(limit)                                        # limit=10
```

⇒ **只有「最新 10 条」会被检查过期 / 跨周。**
第 11 条往后的旧作业**永远不会被读到，也就永远不会被标 `expired` / `cross_cycle`**，
以 `pending` 状态无限堆在库里。

⚠️ **最容易发生的正是这种情形**：某颗星球航线紧张、执行跟不上生成，
pending 攒过 10 条之后，**最老的那些进了盲区** —— 而按 `desc()` 排序，
被漏掉的恰恰是**最该过期的那批**。

⚠️⚠️ **后果直接顶掉一条用户裁决**：R23「作业不跨周」是用户亲自拍板保留的
（他知道代价还是选了保留），而对这批看不见的作业**它不生效**。

**修法（轻）**：把「清理」和「取待执行」拆开 ——

- 清理单独一趟、**不带 `limit`**、扫全表 `state='pending'`
- 挂在 `tick()` 里那一排「按 tick 算一次就够」的动作即可，
  和 `_scan_recycle_decisions()`（`mission_scheduler.py:2091`）并排
- `pending_recycle_jobs()` 回归单一职责：只查、不改状态

### 附4. 预算扣减：三处按任务类型分开记账

规格：`docs/回收闭环/设计.md` §7.2。
现状：回收计入 `dispatched` ✅、回收先于攻击 ✅，**但「三处预算分任务类型」没看到改动**。
