# 同一句中文，两个意思 —— `_DIALOG_KINDS` 怎么改（设计 v2，2026-09-10）

> ## ⚠️ v2 更正（Codex review P1#3，核过属实）
>
> v1 §5 写着「**生产代码只有一处调用点**」—— **那句话是误导的**。
> 「一处」说的是 `dialog_kind`，而它嵌在**共享**的 `_handle_dialog` 里，
> 后者有 **4 个调用点**：
>
>     pirate_loop.py:2533  _require_origin_before_dispatch
>     pirate_loop.py:2646  _launch
>     pirate_loop.py:2673  scout
>     pirate_loop.py:2751  attack
>
> ⇒ **只在分类那一处传 `purpose=ATTACK` 挡不住这个坑**。见 §5。

配套：[`流程图.md`](流程图.md) §5 · [`设计.md`](设计.md) §6

**这是回收上线前的硬阻塞。** 用户 2026-09-10 问「要如何修改」，本文是答复。

---

## 1. 现状

```python
class DialogKind(Enum):
    PROTECTED = "protected"    # 「没有可执行的任务。」——目标在保护期。只跳过这一个目标
    EXHAUSTED = "exhausted"    # 未选择任何战舰 / 同时派遣数已达上限。停下整轮

_DIALOG_KINDS: dict[str, DialogKind] = {
    DIALOG_NO_MISSION: DialogKind.PROTECTED,
    DIALOG_NO_SHIPS:   DialogKind.EXHAUSTED,
    DIALOG_LINES_FULL: DialogKind.EXHAUSTED,
}
```

处置在 `pirate_loop._handle_dialog` —— ⚠️ **它自己有 4 个调用点**（见 §5）：

```python
if pirate_ui.dialog_kind(message) is pirate_ui.DialogKind.PROTECTED:
    self._note_protection_period(coordinate)   # ← 往库里写 8 小时排除
    ...
    return False
raise RoundExhausted(message)
```

## 2. 病根：这个枚举把「游戏说了什么」和「我们该做什么」混在一起

`PROTECTED` 是**解释**，不是观测。游戏只说了「没有可执行的任务」；
「是不是保护期」是我们**根据当时在派什么**推出来的。

**那层推理被烧死在枚举名里，所以第二种含义放不进去。**

⚠️ 回收链路撞同一句话时意思是「**这颗没有残骸**」。照搬现有分支会
`_note_protection_period()` 往库里写一条 8 小时排除 ⇒
**一颗完全打得了的 bot 被排出攻击候选池 8 小时，而页面和日志上都看不出异常。**

⚠️ 更糟的是「攻击被拒就地改回收」那条（`回收残骸/待办.md` §10）会让两者
**在同一个坐标、同一分钟内先后发生**。

## 3. 改法：拆成两层

```python
class DialogMessage(Enum):
    """**观测**：游戏说了什么。不含任何处置含义。"""
    NO_MISSION = "no_mission"      # 「没有可执行的任务。」
    NO_SHIPS   = "no_ships"        # 「未选择任何战舰」
    LINES_FULL = "lines_full"      # 「同时派遣的舰队数量已达上限。」


class DispatchPurpose(Enum):
    """**这一次点击是为了派什么**。由调用方给，不从屏幕上猜。"""
    ATTACK  = "attack"
    RECYCLE = "recycle"


class DialogAction(Enum):
    """**处置**：我们该做什么。"""
    SKIP_PROTECTED = "skip_protected"   # 记 8 小时排除 + 跳过这个目标
    SKIP_NO_DEBRIS = "skip_no_debris"   # ⚠️ 只记一条观察，**绝不写排除**
    SKIP_NO_RECYCLERS = "skip_no_recyclers"  # ⚠️ 本不该发生（§3.4）：跳过这次回收，**攻击照跑**，并告警
    STOP_ROUND     = "stop_round"       # 资源耗尽，停下整轮


_ACTIONS: dict[tuple[DialogMessage, DispatchPurpose], DialogAction] = {
    (DialogMessage.NO_MISSION, DispatchPurpose.ATTACK):  DialogAction.SKIP_PROTECTED,
    (DialogMessage.NO_MISSION, DispatchPurpose.RECYCLE): DialogAction.SKIP_NO_DEBRIS,  # ← 就是这一格
    (DialogMessage.NO_SHIPS,   DispatchPurpose.ATTACK):  DialogAction.STOP_ROUND,
    (DialogMessage.NO_SHIPS,   DispatchPurpose.RECYCLE): DialogAction.SKIP_NO_RECYCLERS,  # ← §3.4
    (DialogMessage.LINES_FULL, DispatchPurpose.ATTACK):  DialogAction.STOP_ROUND,
    (DialogMessage.LINES_FULL, DispatchPurpose.RECYCLE): DialogAction.STOP_ROUND,
}


def dialog_action(message: str, *, purpose: DispatchPurpose) -> DialogAction: ...
```

### 3.1 封闭表这个性质**变强了**，不是变弱

从 3 格变 6 格。新增**一种弹窗**或**一种任务类型**，漏一格就 `KeyError` ——
现有那条口径（「漏掉一个新弹窗会 `KeyError`，**那正是想要的**」）原样继承，
而且现在它还管住了「任务类型」这个新维度。

### 3.2 ⚠️ `purpose` 必须由调用方传，不许从屏幕上猜

我们在点「攻击」还是「回收」是**自己发起的**，这个信息可靠。
而从弹窗上**永远**分不出来 —— 那正是这个坑的本质。

⚠️ 所以 `dialog_action` 的签名里 `purpose` 是**必填关键字参数**，没有默认值。
给默认值等于让漏传的调用方悄悄拿到攻击那一档的处置。
（同 `_still_holding_a_line` 的 `hold` 那条先例：「必填、没有默认值 ——
漏传就会静默退回到写死的 90 分钟」。）

### 3.3 `DispatchPurpose` 放哪

**放 `game.pirate_ui` 本地。**

⚠️ 不用 `vision.parsers.MissionType`：`pirate_ui` 现在只 import `domain`，
引 `vision` 是反向依赖。而且两者语义不同 —— `MissionType` 是
「**简报上写着**什么任务」（观测），`DispatchPurpose` 是
「**我们打算**派什么」（意图）。⚠️ 这两个恰恰不能混。
（⚠️ 回收这一版**不读简报页的类型**了，见 [`设计.md`](设计.md) §3 —— 但这两个概念
仍然不能混：攻击链路照旧读，而 `purpose` 管的是弹窗分流。）

### 3.4 ✅ `(NO_SHIPS, RECYCLE)` = `SKIP_NO_RECYCLERS`，不是 `STOP_ROUND`

v1 这一格照抄攻击侧写的是 `STOP_ROUND`（**停下整轮**）。**用户口径 2026-09-10 定了两条事实：**

> 回收和攻击就是两拨船，现实是不存在缺少回收无法派出的，
> 配置的舰艇是数量级多一位的存在的

⇒ 「未选择任何战舰」在两条链路上又是**同一句话、两个意思**：

| 链路 | 它的意思 | 处置 |
|---|---|---|
| 攻击 | 预设里那批船不够了 = **资源耗尽** | `STOP_ROUND` —— 停下整轮，等返航 |
| 回收 | ⚠️ **两拨船是独立的** —— 回收船不够跟攻击舰队没关系 | `SKIP_NO_RECYCLERS` —— **只跳过这一次回收，攻击照跑** |

⚠️⚠️ 照抄 `STOP_ROUND` 的后果：**一次「回收船不够」会把这一轮的攻击也一起停掉**，
而攻击舰队好端端地停在那儿。这正是本文 §2 那个病根的第二次发作 ——
把「游戏说了什么」当成「我们该做什么」。

### ⚠️ 但这一格**必须告警**，因为它本不该发生

用户口径：回收舰艇是**数量级多一位**的存在，「不存在缺少回收无法派出的」。

⇒ 这一支一旦真的走到，**最可能的解释不是「船不够」**，而是：

    · 我们根本不在回收的派遣页上（走错屏了）
    · `purpose` 说了谎 —— 想派回收却点到了攻击图标（§7）
    · 游戏版面变了，这句话现在是别的意思

⇒ **处置是「跳过」，但日志级别按异常写**：落 `system_log` 的 WARNING，
带上当时的屏、坐标、`purpose`。**跳过是为了不误伤攻击，不是因为这件事正常。**

## 4. 我排除的两个更省事的写法

| 写法 | 为什么不行 |
|---|---|
| **只加一个 `NO_DEBRIS` 枚举成员，不引入 `purpose`** | **做不到**。同一句中文要映射到两个值，字典键直接冲突 |
| **在 `_handle_dialog` 里 `if 是回收: ...` 特判** | 那等于把判据从封闭表挪进 `if`。下次再加一种任务类型或弹窗，漏了**不会报错** —— 而这张表存在的全部理由就是「漏了要炸」 |

## 5. ⚠️ 改动范围 —— `purpose` 必须贯穿四条共享路径

### 5.1 v1 在这里说错了

`dialog_kind` 确实全仓只有一处调用。**但它嵌在共享的 `_handle_dialog` 里**，
而那个方法有四个调用点：

| 行 | 函数 | 回收会不会走到 |
|---|---|---|
| 2533 | `_require_origin_before_dispatch` | ⚠️ **会** —— 配套设计明确要求回收复用起点核验 |
| 2646 | `_launch` | ⚠️ **会** —— 回收也要点「出发！」 |
| 2673 | `scout` | 不会（侦察） |
| 2751 | `attack` | 不会（攻击） |

### 5.2 ⚠️ 只改分类那一处会漏掉的具体路径

    回收派遣页 → 起点读不出来
      → _require_origin_before_dispatch 内部调 _handle_dialog
        → 若那里仍固定传 ATTACK
          → 「没有可执行的任务」照样判成保护期
            → 往库里写 8 小时排除 ❌

**六格表全部正确也挡不住。** 问题不在表，在**参数没接到底**。

### 5.3 改法：从顶层贯穿，不设默认值

    purpose 由「这一次操作是为了派什么」的**顶层发起处**决定，
    一路作为必填关键字参数传下去：

        attack(...)                        → purpose = ATTACK
        scout(...)                         → purpose = SCOUT
        recycle(...)（新）                  → purpose = RECYCLE
          ↓ 各自传给
        _require_origin_before_dispatch(coordinate, *, purpose)
        _launch(coordinate, mission, *, purpose)
          ↓ 再传给
        _handle_dialog(coordinate, *, purpose)
          ↓ 才轮到
        dialog_action(message, *, purpose)

⚠️ **每一层都不设默认值。** 给默认值等于让漏传的那一层悄悄拿到攻击那一档
（同 `_still_holding_a_line` 的 `hold`：「必填、没有默认值 —— 漏传就会静默
退回到写死的 90 分钟」）。

⚠️ **侦察那条现在怎么映射要一并写死。** `scout` 也会撞「没有可执行的任务」，
而它既不是攻击也不是回收 —— 不定义清楚，六格表就变成九格表里缺三格。

### 5.4 改动清单

    src/evo_helper/game/pirate_ui.py     三个 enum + 一张表 + dialog_action()
    src/evo_helper/tools/pirate_loop.py  _handle_dialog 及其 4 个调用点 + 各自的上游
    tests/                               三处引用现有 DialogKind 的用例

⚠️ **这已经不是「只有一处调用点」的小改动**。但它仍然**独立可发** ——
先把参数接通、行为一个字不变（全部传 ATTACK/SCOUT），回收接线时那一格已经在等着。

## 6. 变异验证（至少这两条要红）

| 把判据反过来 | 该红在哪 |
|---|---|
| 把 `(NO_MISSION, RECYCLE)` 改成 `SKIP_PROTECTED` | 「回收撞没残骸时不许写保护期排除」那条 |
| 把 `purpose` 维度整个拆掉（退回按消息单键查） | 「同一句话两条链路给不同处置」那条 |
| **让 `_require_origin_before_dispatch` 固定传 ATTACK** | ⚠️ **「回收起点被弹窗遮住」那条**（见 5.2）—— review 抓到的，v1 的用例覆盖不到 |
| 把 `(NO_SHIPS, RECYCLE)` 改回 `STOP_ROUND` | ⚠️ **「回收船不够不许停掉攻击」那条**（§3.4）—— 两拨船是独立的 |

⚠️ 还要两条**源码级**断言：

1. `_note_protection_period` 的调用点**全仓只有一处**，且只在 `SKIP_PROTECTED` 那一支里。
   理由同 `#288` 那条「`skip_known=True` 全仓恰好一处」—— 接线错了跑流程也看不出来。
2. ⚠️ **`_handle_dialog` 的每一个调用点都显式传了 `purpose`**。
   这一条要按**源码**断言，不能靠跑流程 —— 漏传的那一条路可能一年才走到一次。

⚠️⚠️ **只测查表、只断言保护期函数一处调用，都不够**（review 原话）。
必须有一条用例真的走「回收 + 起点读不出 + 弹窗」这条路。

## 7. ⚠️ 这一版之后仍然没解决的

**「没残骸」和「保护期」在游戏侧仍然是同一句话。** 我们靠
「自己知道在派什么」把它们分开 —— 这成立的前提是**意图与实际操作一致**。

**用户口径 2026-09-10（R21）：「你的流程是没办法把回收误派成攻击的。」**
⇒ 回收链路自始至终不与攻击合流（从「回收」按钮进、没有预设可选、舰队自动配），
所以 `purpose` 不会说谎。原先那道简报页类型闸因此**撤销**。

⚠️⚠️ **但这条保证是有前提的，而前提就落在这一句上：**

    入口必须真的是「回收」那个按钮。

⇒ 「**按标签文字定位、不写死坐标**」那条硬要求，在这次改造之后
**从「好习惯」升级成了这条保证的唯一支点**（`回收残骸/待办.md` §2：
图标集是动态的，写死坐标会点到隔壁那个真实操作）。
判据没了闸门兜底，定位错了就没有第二道防线。
