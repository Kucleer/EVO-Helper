## 1. 背景：那一行判据是干什么的

游戏信箱的「报告」标签下有一排二级按钮，其中「舰队」是一个**筛选开关**（不是页签）：
打开后列表里只剩「舰队返回 / 回收报告」两类；关掉则混着攻击报告等等。

- **读回收报告**那一趟需要它**开着**；
- **读攻击战报**那一趟需要它**关着**。

所以每次切换之后要判断「现在到底在哪一档」。判据只有一份，在
`PirateLoop._sub_tab_matches`，靠**读那一屏每行的主题**来认。

### ⚠️ 这里有一条从一开始就写在 docstring 里的警告

> 而「切错了」是这条链路**最危险**的失败形态：切错之后列表里的主题**都认得出**，
> 日志上一切正常，只是读的是另一个标签的信。

**两次事故我都读过这段话。**

## 2. 起因：#336 引入判据放宽（09-13 夜）

### 2.1 当晚要修的问题

实机取证查出「切不到舰队标签」是三个错叠在一起（坐标抄错、它其实是开关不是页签、
开关状态跨次记住而代码无条件先点再看）。这三条都修对了，**不是本次事故的成因**。

### 2.2 成因：第四处改动

修完之后剩一个问题：**「关掉筛选」这个方向永远判不成立**。
原判据两侧都要正面证据：

```python
good = (here > 0 and there == 0) if fleet else there > 0
#                                              ^^^^^^^^^ 要正面看到攻击报告
```

而攻击报告的**列表行**主题 OCR 读不准，实测关掉筛选后那 6 行经常整屏 `unknown`。
于是这一侧重试三次全败、整趟放弃。

我把它改成了：

```python
good = (here > 0 and there == 0) if fleet else here == 0
#                                              ^^^^^^^^^ 「没看见舰队类就算关掉了」
```

**当场验证**：五次切换全成，包括原先 100% 失败的那一侧。全量测试绿，CI 绿，合并上生产。

### 2.3 为什么这个改法是错的

「**没看见** X」在三种情况下都成立：

1. 真的是没筛过的列表 ✅
2. 列表还在重绘，一行都没读出来 ❌
3. 压根不在列表上（上一下点飞了）❌

后两种都会被判成「已经关掉了」。

## 6. ⚠️ 遗留风险（请 reviewer 重点看）

### 6.1 实机验收未做

#340 只经过代码验证。**真正的验收是重启之后看「轮次不再判失败」和「VICTORY 战报重新入库」**，
那要等下一次发布。在那之前，不能说事故 A 已经修好。

### 6.2 事故 A 的探测仍然不完整

`here > 0` 能在**屏幕读得出来**的时候 100% 认出卡住的筛选。但若某一屏整屏读不出
（`here == 0`），判据会认为「没开着」而放行 —— 那正是事故 A 的形状。

目前**没有**任何东西守着这个残余缺口。原本打算加的症状探测器
（「一封都没开而单子非空 ⇒ 喊」）**没有合入**，理由有二：

1. 那份代码当时有 43 个用例挂着；
2. ⚠️ 更根本的：**判据本身会在上游停摆时刷屏**。游戏侧航线收不回时，
   单子上那几发一直挂着不销（`outstanding > 0`），而信箱里本来就没有新战报可开
   （`opened == 0`）—— 两个条件同时成立，它会一直喊。
   一条会在上游停摆时刷屏的告警比没有告警更糟：它会把人训练成忽略它。

**这个问题目前没有答案，不建议硬做。** 需要一个能区分「读不到」与「没得读」的量，
而现有信息里没有。

回收读信开关目前**关着**（用户于 09-14 上午关闭）。开关关着时
`collect_recycle_hauls` 整个不跑，不会碰筛选 —— 所以事故 A 的触发条件当前不存在。
