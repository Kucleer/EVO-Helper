## 1. 背景：那一行判据是干什么的

游戏信箱的「报告」标签下有一排二级按钮，其中「舰队」是一个**筛选开关**（不是页签）：
打开后列表里只剩「舰队返回 / 回收报告」两类；关掉则混着攻击报告等等。

- **读回收报告**那一趟需要它**开着**；
- **读攻击战报**那一趟需要它**关着**。

所以每次切换之后要判断「现在到底在哪一档」。判据只有一份，在
`PirateLoop._sub_tab_matches`，靠**读那一屏每行的主题**来认。

### ⚠️ 这里有一条从一开始就写在 docstring 里的警告

> 而「切错了」是这条链路**最危险**的失败形态：切错之后列表里的主题**都认得出**，
> 日志上一切正常，只是读的是另一个标签的信。

**两次事故我都读过这段话。**

## 2. 起因：#336 引入判据放宽（09-13 夜）

### 2.1 当晚要修的问题

实机取证查出「切不到舰队标签」是三个错叠在一起（坐标抄错、它其实是开关不是页签、
开关状态跨次记住而代码无条件先点再看）。这三条都修对了，**不是本次事故的成因**。

### 2.2 成因：第四处改动

修完之后剩一个问题：**「关掉筛选」这个方向永远判不成立**。
原判据两侧都要正面证据：

```python
good = (here > 0 and there == 0) if fleet else there > 0
#                                              ^^^^^^^^^ 要正面看到攻击报告
```

而攻击报告的**列表行**主题 OCR 读不准，实测关掉筛选后那 6 行经常整屏 `unknown`。
于是这一侧重试三次全败、整趟放弃。

我把它改成了：

```python
good = (here > 0 and there == 0) if fleet else here == 0
#                                              ^^^^^^^^^ 「没看见舰队类就算关掉了」
```

**当场验证**：五次切换全成，包括原先 100% 失败的那一侧。全量测试绿，CI 绿，合并上生产。

### 2.3 为什么这个改法是错的

「**没看见** X」在三种情况下都成立：

1. 真的是没筛过的列表 ✅
2. 列表还在重绘，一行都没读出来 ❌
3. 压根不在列表上（上一下点飞了）❌

后两种都会被判成「已经关掉了」。

## 4. 事故 B：每轮自杀 57 分钟

### 4.1 因果链

```
非舰队类主题读不出（常态）
   ↓
「至少看见一封确凿的非舰队类」永远不成立
   ↓
_select_mail_sub_tab(fleet=False) 返回 False
   ↓
#339 的前提检查抛 RuntimeError
   ↓
调用方升级：关窗重开，再翻一次 —— 还是 False
   ↓
这一轮判为失败
   ↓
任务 2/6/8/9/10/11/12 一起挂 → 判为「环境故障」
   ↓
攻击、扫描、读信，全都轮不到
```

### 4.2 数据（出处：`system_log`）

```
窗口：10:48:39 → 11:45:54（57 分 15 秒）
42 次：这一轮判为失败：开工翻不了信箱：重开之后仍然翻不了
       （舰队筛选关不掉，拒绝在筛过的列表上翻战报）
```

⚠️ **这个数我一开始写成 216，是错的**（复核 §5 指出）。216 是**含那句话的日志行数**，
一轮会打好几行。逐句数：

| 匹配 | 行数 |
|---|---|
| 含「舰队筛选关不掉」的任意日志行 | 216 |
| **其中「这一轮判为失败」的行** | **42** |
| 「拒绝在筛过的列表上翻战报」那句 | 130 |

⚠️ 而且 42 是**匹配这一种失败原因**的轮次数，**不等于**「期间所有任务轮次都失败」——
我没有分任务统计成功 / 失败 / 跳过，那个断言收回。

判据当时看到的是：

```
二级标签「舰队筛选关」内容对不上（舰队类 0 行、非舰队类 0 行、共 6 行）
```

⚠️ **舰队类 0 行。** 系统因为「证明不了它关着」而自杀。

⚠️⚠️ 我原先在这里写「所以筛选根本没开着」，**这个推论收回**（复核第二轮指出）：
本报告自己在 §2.3 就列过「空屏 / 不在列表上 / OCR 全失败」这些替代解释，
`here == 0` 分不出它们。能确定的只有「判据拿不到正面证据」，
而那已经足以解释自杀 —— 筛选当时到底开没开，这份日志回答不了。

### 4.3 处置

用户发现后回滚到 `a57d3c5`（#338 合并点），11:47:33 重启。

⚠️ 「恢复」这个词我用得太满（复核第二轮）：我看到的是重启之后 12h–14h 每小时
10–15 发派遣，但**没有取当次的成功证据**（首次成功轮次、首次战报入库时刻）。
准确说法是：**重启后派遣量回到事故前水平；链路各环是否全部恢复未逐项核实。**

⚠️ 我当时给用户的「回滚安全」理由是：该版本带着事故 A 的 bug，但那个 bug 需要

⚠️⚠️ **这个理由不完整**（第三轮复核指出，与 §6.3 的更正冲突）：开关关掉只能阻止

回滚版同样会在筛过的列表上静默读空。**当时我没有取证据确认筛选在哪一档。**

### ⚠️⚠️ 那个「188」不能用（2026-09-14 第三轮复核催出来的）

复核指出我的统计 SQL **没有限定事故窗口**。照着去查，结果是：

⚠️ **所以阈值的真实依据是 28 条 vs 16 条**，不是 28 vs 188。
两侧仍然不重叠（4~6 对 0），但证据强度**远比我先前写的弱**。
⚠️ 而且两侧都**没有按页面去重**，也都仍是循环分类（见 §9.2）。

两侧之间是个大空档，所以：

```python
on = here > 0 and other == 0

```

- 「筛选开着」= 正面证据，**这是唯一拿得到正面证据的方向**；

⚠️ 复核时我一度把它收紧成「整屏全中」（`here == len(kinds)`），
依据只是前一晚几次观察。已推翻。

⚠️ **推翻的理由要改写**（第四轮复核指出）：我原先写「那会漏掉 54% 的卡住筛选」——
那是**把日志计数比例当成了真实状态的漏检率**。这批样本没有独立状态标签，

三个数**窗口内外完全一致**，因为那句日志只在 #339 上生产的 57 分钟里存在过 ——
数字是对的，但当初的写法只是**碰巧**对。

```sql
-- 窗口：[2026-09-14 10:48+08, 2026-09-14 11:46+08)
SELECT count(*) FROM system_log
WHERE message LIKE '%舰队筛选关不掉%'
  AND logged_at_utc >= TIMESTAMPTZ '2026-09-14 10:48+08'
  AND logged_at_utc <  TIMESTAMPTZ '2026-09-14 11:46+08';                                  -- 216
-- 同样加窗口后：
--   message LIKE '这一轮判为失败%舰队筛选关不掉%'      -- 42
--   message LIKE '%拒绝在筛过的列表上翻战报%'          -- 130

-- 窗口边界
-- ⚠️ 这一条**故意不加时间条件** —— 它要问的正是「这句日志存在于哪个区间」，
--    加了窗口就等于先假定答案。它是**边界发现**查询，不是计数查询。
SELECT min(logged_at_utc), max(logged_at_utc) FROM system_log
WHERE message LIKE '%舰队筛选关不掉%';   -- 10:48:39 → 11:45:54
```

⚠️ 42 是**匹配这一种失败原因**的日志行数，**不等于**「期间所有轮次都失败」；
我没有分任务统计成功 / 失败 / 跳过。

### 11.3 §5.2 的两组计数分布（28 / 188）

⚠️ **原写法没有窗口，第二条因此把 172 条故障期日志算了进来**（见 §5.2）。

```sql
-- 「问开着？」共 28 行。⚠️ **第四轮复核指出这条仍无时间条件**。

SELECT message FROM system_log
WHERE (message LIKE '%二级标签在「舰队」上%'
    OR message LIKE '%二级标签「舰队」内容对不上%')
```

## 12. ⚠️ 一条把我自己带偏过的方法错误：边改文件边跑全量

写这份报告的过程中发现的，**它污染过我至少一个结论**。

### 12.1 现象

我习惯把全量测试丢到后台跑，然后**在它跑的时候继续改代码和文档**。
2026-09-14 下午有一次这样跑出 **16 个失败**，而且跑了 17 分钟（平时 5 分钟）。
文件稳定之后把那几个文件重跑：**50 passed，一个都不挂。**

⚠️ **「pytest 读到了半截文件」只是我的解释，没有证实**（第三轮复核指出）。
我能证明的只有两件事：**同一批用例在文件稳定后全部通过**，以及那次跑用了
17 分钟而平时 5 分钟。至于此前失败的真实原因 —— 半截文件、导入缓存、
还是别的什么 —— **我没有留下那次的失败详情，无法判定**。

⚠️⚠️ 这一节本身因此也要降级：**「边改边跑会造假失败」是一个未证实的假说**，
不是已确立的事实。它足以让我**不再信任**那两次测量（43 与 16），
但不足以让我断言它们的成因。

### 12.2 它污染了哪个结论

同一天更早，我用同样的方式跑出 **43 个失败**，并据此在复盘里写下
「⚠️ **代码没写好**」，把它列为我当天的第四个错误。

**那个结论现在站不住了。** 我试过重放去复算（`git stash apply` 那份代码再跑），
但基线已经过了好几个提交、与演进后的用例文件冲突，**没能干净复现**。
所以正确的说法是：**那份代码质量未知**，不是「没写好」。

⚠️ 另一次「39 个失败」我当时具体诊断过（新加的探测自己要读一屏，
把夹具 pop 的那一屏吃掉了）并针对性修好，那一次的因果是清楚的；
但⚠️ 我**没有**验证过「修之前它确实挂」，所以严格说那一次也只是**修法合理**，
不是「已证实的因果」。

### 12.3 教训

- **跑全量的时候不许改文件。** 这条本该是常识，我连着犯了好几次。
- 更一般地：**我用一次未受控的测量，下了一个关于自己代码质量的结论，还把它写进了两份文档。**
  这和本报告 §7.2 那张「当场看着对不等于对」的表是同一个毛病 ——
  只不过这次错在**过度自责**的方向，性质一样：**没有把测量条件控制住就下结论**。
