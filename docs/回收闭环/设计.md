## 2. 闭环 = 数据链不断

    ①攻击打掉舰队 → ②残骸生成 → ③按累计战损排序 → ④水位线闸
         → ⑤派出回收 → ⑥记账 → ⑦舰队返航 → ⑧回收邮件
         → ⑨读回实收 → ⑩存档三元组 ──┐
                    ↑                  │
                    └──────────────────┘

**现状：只有 ① 和 ② 是自动发生的，③–⑩ 一步都不存在。**

⚠️ ③ 存在的理由是**排序**（2,279 个坐标逐个飞过去看，光导航约 24 小时），
**不是估值** —— 而排序只要 `Σ defender_losses`，不需要 k（§0.3）。

## 3. ⚠️ 派遣的三态，以及承重闸门在哪（review #1）

用户口径（2026-09-09）：

> **「派遣回收不会失败，前提是你确认的是派遣回收。」**

⇒ **承重闸门是简报页那道类型闸，不是出发之后的弹窗识别。**

    简报页读到「回收」   →  点出发  →  ✅ 成功（按用户口径，不会失败）
    简报页不是「回收」   →  ❌ 不点出发，记「拒绝」
    简报页读不出        →  ❌ 不点出发，记「未知」

### 3.1 三态的定义与处置

| 态 | 什么时候 | 处置 | ⚠️ |
|---|---|---|---|
| **成功** | 简报页确认「回收」后点了出发 | 记一发派遣，占航线 | |
| **拒绝** | 简报页之前被拒（弹窗、没残骸…） | 记一条**观察**，**不记派遣、不占航线** | 见 §6 撞名 |
| **未知** | 简报页读不出类型 | **不点出发**；记一条「未知」，**不重派** | |

> ⚠️ **「未知」的处置是「根本不点」，不是「点了之后不知道结果」。**
> 风险被前移到了简报页，所以这条链路不需要「派出后确认」。

### 3.2 这条口径同时解释了 09-08 那次采样

那次实机走到**派遣页点绿✓ 之后、进简报页之前**被拒，
**从来没到过一个写着「回收」的简报页**。
⇒ 不是「回收派遣失败了」，是根本没通过前置条件，与用户口径不矛盾。

## 5. 存储（review #3：v2 那句「只加一列」是错的）

### 5.1 ⚠️ 先更正：`mission_kind` **早就存在**

`AttackDispatchRow.mission_kind`（`storage/models.py:372`）已经有了，
而且候选查询在**六处**都钉着它（见 §8）。

v2 写「唯一要新增的是『这一发是攻击还是残骸』这一列」——**那句话本身就是错的**。
⇒ 回收派遣**直接用现有列的新取值**，不加列。

### 5.2 但四类数据确实没有落点

| 数据 | 现在能放哪 | 结论 |
|---|---|---|
| **只看了面板、没派**（观察） | ❌ 派遣表要求真派出去了 | **要新表** |
| **被拒记录**（没残骸/弹窗） | ❌ 同上 | **同一张新表** |
| **三元组**（面板读数 / 派遣 / 实收） | ❌ 资源表 `battle_report_resources` 靠**战报外键**，没有战报就挂不上 | **要落点** |
| **解析状态** | ❌ | **同上** |

⇒ 新增一张**观察表**（暂名 `salvage_observations`），一行 = 一次「看了某坐标一眼」：

    坐标 / 观察时刻 / 回收按钮在不在 / 残骸框三格读数 / 读数解析状态
    / 有没有转成派遣（外键，可空）

派遣与实收仍走现有两张表，三元组靠外键串起来。

### 5.3 ⚠️ 「实收为零」和「没读到」必须分得开

    实收 = 0        →  真的飞过去了，残骸没了（别人抢先 / 读数本来就不对）
    实收 = 没读到    →  邮件没找到、或找到了解析失败

**用可空字段 + 独立的解析状态列表达，不许用 0 表示「没读到」。**
（同 `recovery_rate` 那条先例：分母为 0 时返回 `None` 而不是 0 ——
「回收率 0%」在一发没派时是句假话。）

## 8. 认领的任务类型隔离（review #4）

现有候选查询在**六处**都钉着 `mission_kind == MISSION_KIND_ATTACK`
（`storage/repository.py:1640 / 1694 / 1748 / 2242 …`）。

- 直接复用 ⇒ **漏掉回收派遣**（永远认不上）
- 简单取消过滤 ⇒ **可能把回收邮件串认到攻击派遣上**

### 规则

    回收邮件  只匹配  mission_kind = 回收 的派遣
    攻击战报  只匹配  mission_kind = ATTACK 的派遣      ← 现状，一个字不改

⚠️ 三条现有口径**必须保留，不许简化**：

1. **多候选歧义 → 一发都不认**（`AMBIGUOUS`）。认错一发比认不上更糟。
2. **重复读取要幂等** —— 同一封邮件读两次不许挂两笔。
3. **补认领**（`rematch_unlinked_reports`）要覆盖回收，且**同样按类型隔离**。

⚠️ 回收报告**没有 VS 块**，所以认领只能靠「坐标 + 预期到达时刻」——
和 `战报认领-目标错读/待办.md` 那第 4 档同类问题，**可以一起想，
但不许共用同一段代码**（类型隔离是硬要求）。
