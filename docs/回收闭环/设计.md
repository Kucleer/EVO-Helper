## 2. 闭环 = 数据链不断

    ①攻击打掉舰队 → ②残骸生成 → ③按累计战损排序 → ④水位线闸
         → ⑤派出回收 → ⑥记账 → ⑦舰队返航 → ⑧回收邮件
         → ⑨读回实收 → ⑩存档三元组 ──┐
                    ↑                  │
                    └──────────────────┘

**现状：只有 ① 和 ② 是自动发生的，③–⑩ 一步都不存在。**

⚠️ ③ 存在的理由是**排序**（2,279 个坐标逐个飞过去看，光导航约 24 小时），

## 3. ⚠️ 派遣的两态，以及承重闸门在哪（review #1 · R21 改）

用户口径（2026-09-09）：

> **「派遣回收不会失败，前提是你确认的是派遣回收。」**

⚠️ **v5 更正：「确认的是回收」靠的不是简报页，是入口本身。**
用户口径 2026-09-10（R21）：

> 到派遣页点勾，就视为已经发出了回收，后续你不需要考虑。
> **你的流程是没办法把回收误派成攻击的**

⇒ **承重闸门是「这条链路从『回收』那个按钮进来」**，不是简报页上的类型文字。
回收链路自始至终不与攻击链路合流：没有预设可选、舰队是游戏按残骸量自动配的。

    点回收按钮 → 残骸框 → 绿✓ → 派遣页（舰队已选好） → 点勾
      ⇒ **记账上到这里就算已发出**
      → 简报页（⚠️ 通用的一屏，各任务类型共用）→ 点「出发！」

⚠️ **简报页和出发按钮照走，只是不再是闸门。** 用户 2026-09-10 确认
「这个简报页是有的，通用的」；R21 那句「点勾就视为已发出」说的是**记账口径**
（后面不设失败分支），不是「链路到此为止」。

### 3.0 ⚠️ 任务类型**照读** —— 它不是闸门，但它是免费的探针（R22）

我一度写成「不读任务类型」。**用户 2026-09-10 反问：「这个页面你是能读到回收的，
你之前为什么不去读」—— 没有正当理由，改回来。**

**成本是零，而且比零还小 —— 那个字段已经在返回值里了：**

    MissionType.RECYCLE = "recycle"                        parsers.py:700
    _MISSION_LABELS = { …, "回收": MissionType.RECYCLE }     parsers.py:708
    DispatchBriefing(mission_type=…, flight=…, arrival_at_utc=…)

读飞行时间调的就是 `parse_dispatch_briefing`，`mission_type` **同一次解析就拿到了**。
不读它不是省了一步，是**把已经到手的字段扔掉**。

| 读到什么 | 处置 |
|---|---|
| **「回收」** | 点「出发！」 |
| ⚠️ **明确是别的类型**（攻击 / 运输 / 探索 / 侦察） | **不点出发** + **WARNING**。这是 R19 那条「走错屏 / `purpose` 说了谎」唯一的实锤探针 |
| **读不出**（`UNKNOWN`） | ⚠️ **照点出发**，只记一条 WARNING |

⚠️ **「读到别的类型」和「读不出」必须分成两档**，同「实收为零 vs 解析失败」那条：
前者是**真信号**（入口出问题了），后者只是 OCR 偶发。闸门已经不承重（入口保证了类型），
为一次 OCR 抖动白费一趟不划算。

⚠️⚠️ **记账落点因此要说清**：**记一发派遣是在真的点了「出发！」之后**。
R21 的「点勾即算已发出」是指**点勾之后不设失败分支** —— 而上表中间那一行
不是「失败」，是**我们自己决定不点**，它落在「未派出」，并且必须告警。

### 3.1 两态的定义与处置

| 态 | 什么时候 | 处置 |
|---|---|---|
| **已派出** | ⚠️ **点了「出发！」** | 记一发派遣，占航线 |
| **未派出** | 没走到那一步（没按钮 / 弹窗 / 简报读到别的类型） | 记一条**观察**，**不记派遣、不占航线** |

⚠️ **「已派出」的定义是「点了出发」，不是「点了勾」**（第七轮评审 §1）。
R21 那句「点勾即算发出」是**记账口径的解释** —— 点勾之后**不设失败分支** ——
**不是状态定义**。写成「点了勾且没弹窗」的话，「点了勾、但简报读到别的类型」
会同时落进已派出和未派出两格。

⚠️ **v4 那个「未知」档取消了。** 它的定义是「简报页读不出任务类型 ⇒ **不点出发**」，
而现在**读不出就照点出发**（§3.0），所以不再需要第三态。
⚠️ 注意不是「不读类型了」—— 类型照读，只是降级成探针。

### 3.2 这条口径同时解释了 09-08 那次采样

那次实机走到**派遣页点绿✓ 之后、进简报页之前**被拒，
**从来没到过一个写着「回收」的简报页**。
⇒ 不是「回收派遣失败了」，是根本没通过前置条件，与用户口径不矛盾。

### 5.3 ⚠️ 「实收为零」和「没读到」必须分得开

    实收 = 0        →  真的飞过去了，残骸没了（别人抢先 / 读数本来就不对）
    实收 = 没读到    →  邮件没找到、或找到了解析失败

**用可空字段 + 独立的解析状态列表达，不许用 0 表示「没读到」。**
（同 `recovery_rate` 那条先例：分母为 0 时返回 `None` 而不是 0 ——

## 7. 调度接在哪（review #7：v2 自相矛盾）

### 7.2 ⚠️ 预算扣减 —— 入口 A **不能**绕过它先上线

v3 写着「入口 A 不依赖这三条，可以先做」。**Codex review P1#4 说这是错的，核过属实。**

源码事实（`bot_loop.py:541`）：

    if self._attack_once(coordinate):
        dispatched += 1          ← 只有攻击**成功**才算进本轮已派数

而保护期那条路 `_attack_once` 返回 **False** ⇒ **不计数、继续试下一个目标**。

⇒ 当本轮只剩 1 条空线、攻击被拒、而回收**已经占走了那条线**时：

    照旧返回 False  →  runner 以为预算没用  →  继续试攻击  →  撞「航线已达上限」
    草率改成 True   →  被当成一次攻击成功记账 ❌

⇒ **入口 A 接入之前，必须先能表达「攻击被拒、但回收已派出」这个结果**，
并按**实际派遣**统一扣减本轮 / 账号 / 起点三处预算，**任务类型分开记账**。

⚠️ 另外：**入口 A 没有一发「已完成的攻击」作为滑块的计数来源**
（它是在攻击被拒的那一刻发生的，那条线还没释放过）。
⇒ 它怎么受那唯一一个滑块约束，**必须补齐**；至少 **r = 0 时禁止新增回收**这一条要覆盖 A。

> **⇒ 「入口 A 可以先做」这句话撤回。**

⚠️ **而且这条规则不是入口 A 专属**（第四轮评审 §1.5）：
滑块那条路同样会在轮内派回收、同样要计入 `dispatched`。

⇒ **两条入口共用一条规则：按实际派遣、分任务类型扣三处预算。**
接线细节见 [`调度接线.md`](调度接线.md) §3.3。

### 7.3 ✅ 航线记账：照抄攻击那一套（用户 2026-09-10，R18）

> 回收的飞行时间读法和攻击完全一样，只是任务类型不一样

⇒ 简报页读飞行时间 → `line_free_at_utc = 派出时刻 + 单程 × 2`，
和攻击**同一段代码、同一个 `FlightEstimate`**，只有 `mission_kind` 换成回收。

### ⚠️ 我原先那条担心是错的，核过了

C7 v4 写着「距离公式那个系数是按攻击舰队标定的，回收船速度不同（简报上 20.475）」。
**源码不是这样**：

    flight_coefficient(origin, mission_kind, fleet_speed)      repository.py:1501

系数**本来就按 `(出发星球, 任务类型, 舰队速度)` 三元组分开学**，而且
docstring 明写「只看飞行时长**是读出来的**那些……天然不会拿公式自己的输出去标定公式自己」。

⇒ 回收传自己的 `mission_kind` 和自己的 `fleet_speed_raw`，**攻击那把尺子根本套不到它头上**。
「读不到宁可不派」这条**撤回**：照攻击那套，读不到就记 NULL。

### ⚠️ 但有一条要照实说：回收刚上线时公式回退是空的

系数从**历史实测**里学。回收一发都没派过 ⇒ 它自己那一档**学不出系数**，
`flight_coefficient` 返回 `None`。

⇒ **开头那几趟，简报页读不出飞行时间就只能记 NULL**，

⚠️ 后果**在回收侧更值得看**：那 90 分钟里这条线被当成占用，

它会随样本积累自愈，但**别把它当故障**。

## 8. 认领的任务类型隔离（review #4）

现有候选查询在**六处**都钉着 `mission_kind == MISSION_KIND_ATTACK`

- 简单取消过滤 ⇒ **可能把回收邮件串认到攻击派遣上**

### 规则

    回收邮件  只匹配  mission_kind = 回收 的派遣
    攻击战报  只匹配  mission_kind = ATTACK 的派遣      ← 现状，一个字不改

⚠️ 三条现有口径**必须保留，不许简化**：

1. **多候选歧义 → 一发都不认**（`AMBIGUOUS`）。认错一发比认不上更糟。
2. **重复读取要幂等** —— 同一封邮件读两次不许挂两笔。
3. **补认领**（`rematch_unlinked_reports`）要覆盖回收，且**同样按类型隔离**。

⚠️ 回收报告**没有 VS 块**，所以认领只能靠「坐标 + 预期到达时刻」——
和 `战报认领-目标错读/待办.md` 那第 4 档同类问题，**可以一起想，
但不许共用同一段代码**（类型隔离是硬要求）。
