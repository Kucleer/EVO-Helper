## 一、病根（最后才查明）

信箱「报告」底下第二排 **战斗 / 侦察 / 舰队 / 系统** 是**四个可以同时选中的筛选**，
不是四选一的页签，也不是单个开关。而**选中态直接写在按钮底色上**。

2026-09-15 量了 65 张失败现场图（每张三块、共 195 个读数）：

    未选中 R = 3 – 30        选中 R = 59 – 190        中间 30→59 是空档

四种状态与列表内容全部对得上：

| 按钮 | 列表 |
|---|---|
| 一个都不选 | 「没有符合当前筛选条件的邮件。」 |
| 只选战斗 | 全是攻击报告 |
| **战斗 + 舰队** | **两类交错混排** ← 失败现场最多的一档（23/65） |
| 战斗 + 侦察 | 也能同时亮 |

**所以「盲点一下舰队」永远到不了位**：

    战斗开着 → 点舰队 → 两个都开（混排）→ 再点 → 舰队又关掉 → 回到只剩战斗

在两种错的状态之间来回翻，而代码把「混排」读成了各种别的东西。

## 二、经过

### 第一阶段：三个错叠在一起（#336，09-13）

原先代码点「战斗」切回战报，但坐标抄错（用了 **897**，那是**侦察**的 x）。
我没去查坐标，而是从「点了没反应」推出「战斗按钮不响应」，进而推出
「这一排只有舰队有反应、它是个开关」，把切回战报改成「再点一次舰队取消」。

**一个观察错误 → 一个机制结论 → 一个错误的代码模型。**

### 第二阶段：在错模型上左右横跳（#336 → #339 → #340）

| PR | 改法 | 后果 |
|---|---|---|
| **#336** `73552a4` | `good = … else here == 0` —— 放松成「没看见舰队类就算关掉」 | 筛选卡在舰队上没人发现，**攻击战报断流 9 小时** |
| **#339** `bf06f2b` | `good = … else other > 0` —— 改严成「必须正面看见非舰队类」 | 那一侧主题本来就读不出 ⇒ 每轮在开工那步自杀，**全线停摆 57 分钟** |
| **#340** `333b7cb` | `good = on if fleet else not on` —— 修好 | 恢复 |

⚠️ **这三行的 PR 号我原先整体错了一位**（把放宽记在 #339、改严记在 #340）。
git 逐条核过，上表是订正后的。（Codex 复核 P2-5 指出。）

两次方向相反，两次都上了生产。共同点：**都在拿列表内容反推筛选状态**。

### 第三阶段：清掉一串真实的堵点（#342 – #347，09-14）

这一段是有价值的，每一条都由实测支撑：

- **#343** 主题读不出就不开。原始口径：**那批 601 次开封记录里 522 次列表主题是 UNKNOWN（86.9%）**，75 条完整可读、4 条部分可读。改用**未读色**当闸。
  ⚠️ 不能改称「87% 的回收报告被挡死」——UNKNOWN 没有独立类型标签，开封次数也不是去重后的邮件数。（Codex 复核 P2-6。）
- **#345** `FLEET_TAB_KINDS` 少列了两种（矮星系统战报 / 部署报告），舰队标签第 0 行常驻一封矮星战报 ⇒ **6 趟里 4 趟**切不到。
- **#346** 登录后 7 秒就开工，在**登录页**上一行行开幻影邮件，整轮卡死。
- **#347** 「取消舰队 = 显示全部」是错的，**取消之后什么都不显示**；切回战报要点「战斗」。

### 第四阶段：在时序上打补丁（#348 – #351，09-14 夜 → 09-15 晨）

这四个 PR 全是同一类：**以为混排屏是「列表还没画完」**。

| PR | 改法 | 结果 |
|---|---|---|
| #348 | 点完先重读几次再判 | 有用（真有重绘延迟） |
| #349 | 等待窗口 8s → 16s | 有用，但**给的理由是错的**（「污染行集中在底部⇒自上而下重绘」；后来发现顶部也污染） |
| #350 | 混合帧「只等不点」 | **必败**。上生产后第一趟回收三次尝试全读到混合帧 ⇒ 一次没点 ⇒ 干等 106 秒放弃 |
| #351 | 等不到就照常点 | 救回 #350，但仍在错前提上 |

### 第五阶段：另一条真实的堵点（#352，09-15）

查「回收为什么还是入不了库」时发现：**读到了实收却认不出是哪一发派遣** 60 次，

而时刻分得清清楚楚（最近 1–3 秒、次近 10–253 秒，中间空档）。改成「最近且明显最近」。

### 第六阶段：取证定案（#353，09-15）

用户把生产机的现场图拉回本地。量按钮底色，一次性推翻前面所有的机制假设。

## 三、踩过的坑（按类型）

### 1. 拿观察下机制结论，没有验证它能否**持续成立**

- #336：「点了一次没反应」⇒「这个按钮不响应」。实际是坐标错。
- #350：「两帧相隔 2 秒都是混排」⇒「混排是瞬态重绘」。
  实际那一屏能**稳定存在 100 秒**，两行「攻击报告」一字不变。

**判瞬态要证明它会自己消失，不是看它出现过。**

### 2. 在错的抽象层上反复打补丁

#348 → #349 → #350 → #351 四个 PR 都在调「等多久」「等不到怎么办」。
而病根不是时序。**连着四个补丁都没让指标真正好转，就该停下来问「是不是前提错了」。**

### 3. 放宽判据以求通过

#339 把「筛选关掉了」放松成「没看见舰队类」。
「没看见 X」和「看见了非 X」不是一回事 —— 前者在读不出/半加载/空列表时**全都成立**。

### 4. 改严判据时没查它依赖的东西读不读得出

**#339** 要求「正面看见非舰队类」，而当时列表主题读出率很低
（同一批 601 次开封里 522 次 UNKNOWN）。判据写得漂亮，生产上每轮自杀。
⚠️ 「非舰队类主题 87% 读不出」是**借了别的分母**——那批样本没有按类型标注。

### 5. 引用数字前没查出处

一夜之内发布过四个错数字：「停摆 3.5 小时」（实为 57 分钟）、「37 发无战报」（实为 27）、
「216 轮判失败」（216 是日志行数，实为 42）、「27 份永久损失」（不成立，已撤回）。

### 6. 监控工具本身出错，导致误判

- `find` 搜的是本机，而生产在另一台机器。
- 战报**分两步写**，`outcome IS NULL` 的行被算成攻击战报 ⇒ 误报过一次「全绿」。
- `count(*)` 跨 join 到截图表**重复计数** ⇒ 改用 `count(distinct b.id)`。

### 7. 用例把 bug 断言成正确行为

- 源码文本扫描 `assert "aborted=True" in body` 同时命中**注释里的反面例子**，
  删掉真参数用例仍然全绿。
- `test_two_recycles_arriving_together_are_both_left_alone` 用「0 秒 + 30 秒」，
  正是 #352 要修的那一类，它把「丢掉」钉成了正确行为。

### 8. 差一点造出更狠的 bug

#353 第一版把「系统亮着」当成「有不许碰的筛选开着，收手」。
而**系统几乎一直亮着** ⇒ 每一趟都收手 ⇒ 回收读信整条掐死。跑了一遍才发现。

## 四、最终方案

### 筛选状态：读按钮底色

    MAIL_SUB_TAB_SAMPLES   四个按钮左侧一小块纯底色（躲开图标与文字）
    MAIL_SUB_TAB_LIT_R = 45    落在实测空档 30→59 内；到暗档上沿 15、到亮档下沿 14

⚠️ 我原先写「两侧各 15 以上余量」是**算错了**，最小余量是 **14**（Codex 复核 P2-7）。
⚠️ 标定样本是 65 张**失败现场图**（client 1920×917），不是全部生产状态的代表；
判别函数目前也没有拒绝尺寸不符/非信箱的截图。测试用的是合成底色，未回放这 65 张实图。

### 切换：按差异开关

不再「盲点目标」，而是读出当前状态后**该关的关、该开的开**，每一下有明确目的。

### 两条安全边界

- **只点「战斗」「舰队」**（`ALLOWED_MAIL_CLICK_LABELS` 守着）。
  侦察/系统是用户自己配的，一下都不点。
- **「系统」亮着忽略**（那档里没有信，实拍角标为空）；
  **「侦察」亮着收手**（它有信，会污染这一趟），并把话说清楚让人工去关。

### 回退路径

读不到截图（单元测试的桩驱动大多只有 `click`/`wait`）时，回退到旧的列表判据。
旧路径**原样保留** —— 否则一改就是整批用例失去意义（不是变红，是测了个不存在的东西）。

### 回收实收认领：最近且明显最近

    窗口里恰好 1 发  → 认领（一个字没动）
    窗口里 ≥2 发     → 最近 ≤5s 且领先次近 ≥7s → 认领；否则整封丢掉

「纯增量」的**准确范围**：不覆写任何已写入的记录，且在**固定的库状态**下
原有的「窗口唯一」分支逐字未改。

⚠️ 它**不能**证明整个邮件序列的认领结果不变（Codex 复核 P1-4）：新认下来的一发会从
后续候选集合里被排除，于是下一封信可能从「两发候选」变成「唯一候选」而走另一条分支。
序列级正确性要靠顺序回放或真实归属来验。

⚠️ 同理「已认领的 58 份」是**旧规则的产物**，称作 ground truth 也缺独立验证；
25 份歧义样本的间隔只证明**候选在时间上可分**，不等于最近者就是正确归属。
置信度 0.8 是**来源标记**，不是实测 80% 准确率。

## 五、待验收

⚠️ `#353` 的实机证据尚未取得，**本文不宣布已恢复**。生产重启之后盯这几个数：

    ⛔ 切不到「舰队」二级标签        基线 41%（09-15 全天 16/39 趟）→ 应显著塌下去
    ⛔ 读到了实收、认不出是哪一发     基线 60 次/夜 → 应显著下降
    ✅ 回收实收入库                 基线 30 份/夜 → 应同步上升

另有 **53 封**（按 `mail_time` 去重）曾被丢弃的回收信，日志显示合计被重开 110 次。

⚠️ **不能据此承诺「会自己补上、不需要补数工具」**（Codex 复核 P1-3）：
回收那一趟带 `skip_read_unknowns=True`，主题读不出**且已读**的行会在查库之前就被跳过，
而「开过一次但因认领歧义未入库」的信可能正好落在这个组合里；
另有翻页深度、开封预算、以及仍不满足「最近且明显最近」等限制。
准确说法：**其中仍能被扫描到、且满足认领条件的那部分有机会自动补录**，补录情况要单独追踪。
