# 读回收邮件拿「实收」—— 可行性与成本评估

> 2026-09-12。用户问的两件事：**系统复杂性**、**游戏内时间消耗**，以及
> **要一个开关**（担心花太多时间）。
>
> ⚠️ 本文所有结论都来自**当天实拍 + 生产库实测**，不是推算。
> 实拍图按规矩不进 Git，留在主仓 `var/game-probe-*.png`。

---

## 0. 一句话

**现在这条链路的成本是 0**——不是因为便宜，是因为 **bot 根本翻不到那个标签**。
要读实收，代价主要不是「多花几秒」，而是**要么多跑一趟信箱，要么从现在
天天满载的 8 封开封预算里抢名额**。

---

## 1. ⚠️ 最要紧的一条实拍事实：回收邮件在另一个二级标签里

信箱有两排页签：

```
个人 │ 报告(99+) │ 探索(99+) │ 收藏
战斗(1) │ 侦察 │ 舰队(99+) │ 系统(99+)
```

`_open_mail`（`pirate_loop.py:4722-4744`）**只点一级的「报告」**，
仓库里**没有任何二级标签的坐标常量**。实拍确认：点完「报告」之后停在
**「战斗」**上，列表里清一色「攻击报告」。

⇒ **回收报告和舰队返回都在「舰队」标签里，bot 从来没点过。**

这直接推翻了几份旧文档里的担心（`回收残骸/待办.md:228-243`、
`评审-第四轮:97-108`）：那里说「回收报告主题落 `UNKNOWN` ⇒ `may_be` 为真 ⇒
每封被白开 20 秒」。**没有发生**，因为翻不到。今天的账面是 0。

## 2. 两种邮件分别是什么（实拍）

### 「回收报告」= 抵达通知

```
主题：回收报告                                12/09/2026 05:47:04
你的回收舰队（[8:117:6] Nalra）已抵达 [8:361:15] bot_8_361_15's Planet 轨道。
打捞无人机正在部署，以回收残骸区域的资源。
货舱   7.2M · 4.05M · 586.6K
战舰   回收船 592
```

### 「舰队返回」= 回港通知，**攻击和回收共用这一个主题**

```
主题：舰队返回                                12/09/2026 05:51:08
你的舰队已从前往 [2:12:9] … 的攻击任务返回 [2:391:16] Jangbi。
货舱   494.78K · 273.94K · 231.28K
战舰   深空吞噬者 150 · 钛能守卫者 100
```

```
主题：舰队返回                                12/09/2026 05:42:48
你的回收舰队已从 [1:171:20] … 附近的残骸区域返回 [1:55:6]，并带回了从残骸中打捞的珍贵资源。
货舱   6.16M · 3.48M · 408.45K
战舰   回收船 503
```

⚠️ **主题分不出攻击返回和回收返回，必须打开读正文。**

### 两封信的数字是不是同一个

实拍三封回收信，**货舱合计都正好等于「回收船数 × 20K」**：

| | 回收船 | 货舱合计 | ÷ 船数 |
|---|---|---|---|
| 抵达 05:47:04 | 592 | 11.84M | 19,994 |
| 抵达（用户截图） | 551 | 11.02M | 19,998 |
| 返回 05:42:48 | 503 | 10.05M | 19,980 |
| 返回 05:40:20 | 291 | 5.81M | 19,966 |

而攻击返回那封：250 艘只装了 1.0M，**远不满**。

⇒ **回收舰队是按残骸量配船、原样装回的**，所以抵达信的数字和返回信的数字
应该是同一个。**但没有直接验过同一趟的一对**（我开的四封分属不同趟）。

⚠️ 语义上只有返回信保证是实收（「**并带回了**从残骸中打捞的珍贵资源」）；
抵达信说的是「舰队到了、无人机正在部署」。若别人先捞走一部分，抵达信会高估。
**要不要接受这个近似，是个取舍，不是技术问题。**

## 3. 成本账

### 3.1 单封

| 口径 | 数值 | 出处 |
|---|---|---|
| 纯 sleep 下界 | 4.4s | `MAIL_OPEN_WAIT_S 2.4` + `MAIL_BACK_WAIT_S 2.0` |
| 代码口径「开封-返回」 | ≈8s | `pirate_loop.py:378` |
| 实测「开封 + 读时间」 | 4.1s（174 次均值） | `任务耗时优化/方案.md:106` |
| **实测全成本**（含解析 + 查重） | **≈20s** | `方案.md:433` |
| 生产实测每封墙钟（本次量） | **6.6s 中位** | 160 轮 `system_log` |

### 3.2 每天有多少封

按生产库实测（档位 r=1.0 时攻击与回收约 1:1）：

| UTC 日 | 攻击 | 回收 | 舰队标签里的邮件 |
|---|---|---|---|
| 09-11（满天） | 102 | 101 | 舰队返回 ~203 + **回收报告 101** |
| 09-10 | 169 | 21 | 舰队返回 ~190 + 回收报告 21 |

实拍抽样的混合比例约 **2 : 1**（舰队返回 : 回收报告），与结构推算一致。

### 3.3 三种口径的总账

| 方案 | 每天多花 | 说明 |
|---|---|---|
| **只读回收报告，舰队返回在列表页就跳过** | **≈33 分钟** | 100 封 × 20s。+ 每趟切标签 2–4s |
| 连舰队返回一起读 | ≈100 分钟 | 300 封 × 20s。⚠️ 而攻击那一半的收获**战报里已经有了** |
| 什么都不做 | 0 | 现状 |

对比：读战报这一整级 2026-09-07 当天占游戏内时间 **127.8 分 / 34.3%**
（`方案.md:70`）。⇒ **只读回收报告这一档，等于把「读信」的开销再加四分之一。**

### 3.4 ⚠️ 但真正的代价不是秒数，是抢名额

`pirate_loop.py:423-424` 实测：「**「真开」的封数正好都是 8 = `MAIL_MAX_OPENS`，
3/3 趟撞上限**」。日常那趟的预算**天天满载**。

⇒ 回收报告不是「加 33 分钟」，而是**每挤掉一封战报，那一发派遣就要多等一趟**。
真实代价是**战报入库延迟**，而那会连锁影响选靶（读数新鲜度）和配额对账。

**所以回收报告必须走自己的一笔预算，不能和战报抢同一个 8。**

## 4. 系统复杂性：要动七处

| # | 改动 | 难度 | 说明 |
|---|---|---|---|
| 1 | 二级标签坐标 + 点击 + 等待 | 小 | 照 `_open_mail` 的「先认屏再点」序列 |
| 2 | `ReportKind` 加 `RECYCLE` / `FLEET_RETURN` | 小 | `parsers.py:127-159` |
| 3 | `classify_report_subject` 加两条子串 | 小 | 「回收报告」「舰队返回」 |
| 4 | 回收正文解析器 | 中 | 坐标两个 + 三个资源数 + 船数。⚠️ 资源是 `7.2M` 这种**缩写**，要走现有的近似值那一套（`ResourceTotal.approximate`） |
| 5 | `_already_in_library` 放开非战报类型 | 中 | 现在 `row.kind is not RECONCILE_KIND: return False` ⇒ 回收报告**每趟都会被重开**，这是最贵的一处 |
| 6 | 第四笔开封预算 | 小 | 照现有三笔的形状 |
| 7 | 落表 + 认领 | 中 | 回收没有 VS 块，只能按「坐标 + 抵达时刻」认领（`设计.md:413`） |

### ⚠️⚠️ 最大的技术风险：切错标签查不出来

`pirate_loop.py:601-604` 明写：标签行的小字被未读角标压住，`--psm 7` 读成
`'oe. se. eee ee'`，**不能当判据**。

⇒ 「点了『舰队』有没有点中」**现有手段无法验证**。切错了会静默地读一整个
错列表 —— 而列表里的主题都认得出，日志上看着一切正常。

**这一条必须先解决再动手。** 可行的判据：列表首行主题是不是「舰队返回 /
回收报告」之一（舰队标签里不会出现「攻击报告」）——这是个**内容判据**，
比读标签文字可靠。

### 会不会打乱现有规则

会，两处：

1. **未读色判据锚在时刻格墨迹上**（`mail_unread.py`、`回收残骸/待办.md:262-263`）。
   实拍确认舰队标签的行**有时刻格、格式一样**，所以这条风险**不成立**。✅
2. **`may_be` 对 `UNKNOWN` 返回 True** ⇒ 一旦开始点舰队标签，
   「舰队返回」会跟着被开。**必须同时把它加进分类器**，否则 12 封未读预算
   会被舰队返回吃光（2:1 的比例下，回收报告一封都轮不到）。

## 5. 开关怎么做

**好消息：这条路已经趟过一遍。** `recycle_rate_tenths`（回收节奏滑块）就存在
`military_attack_config` 上（`models.py:1148`），一个可空列 + 一次迁移 + 一个
页面控件。**加 `read_recycle_mail` 是同一个形状，不是新基建。**

建议做成**三档而不是开关**，理由同节奏滑块：

| 档位 | 行为 | 每天成本 |
|---|---|---|
| `off`（默认） | 不点舰队标签 | 0 |
| `limited` | 点，但每趟最多开 N 封（N 可配，默认 3） | ≈ N × 趟数 × 20s |
| `full` | 有多少读多少 | ≈33 分钟 |

⚠️ **默认必须是 `off`**：这是加功能不是修 bug，默认开会让所有人在不知情的
情况下多付 33 分钟。

## 6. 我的建议

**先做第 2、3 条（分类器认出这两种主题），单独一个 PR，不碰其它。**

理由：那是**零成本的纯收益**。现在「舰队返回」和「回收报告」都落 `UNKNOWN`，
一旦哪天有人点到舰队标签（或者游戏改了默认标签），它们会立刻开始吃开封预算。
先把分类器补上，等于给后面所有方案上一道保险。

**然后再谈要不要读。** 读不读是个**成本换信息**的决定，而那个信息
（「这一趟实收多少」）目前**没有任何下游在用** —— 概览页的「残骸实收」
一直显示「未知」（`README.md:79-85`），页面上也没有别的地方消费它。

⇒ 建议先想清楚**拿到实收之后要用它做什么判断**。如果只是「想看见」，
那 33 分钟/天买的是一个观感；如果要拿它调节奏滑块（比如实收太低就降档），
那它就值这个钱 —— 但那需要先有那条决策链路。
