# 信箱未读色 —— 方案 v2（**已标定，已通电**）

**一句话**：列表页未读邮件的字体颜色与已读不同，这是比「列表页时刻」**更强**的信号；
拿它把「未读必开」做进翻信箱那一趟，能堵住 `MAIL_MAX_OPENS` + 早停留下的**漏数据**口子。

**2026-09-08 已在实机实拍上标定，判据开始给真答案。**
`vision.mail_unread.CALIBRATION` 那一组量于当晚四屏信箱列表页实拍（未读 4 行 /
已读 20 行，覆盖「对齐网格」一屏 + 「离网格」三屏）。这一版同时**改了取样的几何**：
从「整行」换成「**自对齐的标题带**」，分离度 1.7× → 40×（见 §3.1）。

`None`（判不出）仍旧是这条链路的安全底座：换了游戏版面就把 `CALIBRATION` 撤回
`None` 重采，那一刻整条链路逐字节退回改动之前的行为。

v1 与 v2 的差别只有四处，其余章节原样成立：

| | 改了什么 | 在哪一节 |
|---|---|---|
| 取样几何 | 整行 → 自对齐的标题带 | §3.1 |
| 标定 | `None` → 实拍量出来的一组 | §5 |
| `mean_luminance` | 候选信号 → **纯诊断字段**（依据是看错的） | §0.1 |
| 未读预算 | 写死的模块常量 → `_scan_mail_rows` 的参数，补录传大值 | §3.5 |

## 0. 来源与「每个数字的强度」

本文所有数字都带标注，四档：**实测** / **查出来的** / **推算** / **推理**。

**领域事实来源**（权威，用户口径 2026-09-08）：

> 「邮箱中未读邮件（前 4 个），字体颜色是与已读邮件不一致的，你在开未读邮件时，
> 需要把这些内容都阅读了。」

> 「注意 正常情况下 是连续的未读批量 而不是现在读的稀稀拉拉」

**第二句口径改了结论的形状**：正常版面是「顶部一段**连续**的未读」。当晚量到的稀疏
分布（未读散在约 24 / 30 / 36 / 72 行深处）是 `MAIL_MAX_OPENS` + 早停一趟趟留下来的
**历史空洞**，不是常态。这条口径管着策略层，整段在 §3.5。

**颜色**（2026-09-08 实拍，标题「攻击报告」四个字 ROI 内最亮 40 个像素的均值）：

| 行 | 状态 | RGB | r − b |
|---|---|---|---|
| 1 | 未读 | (229, 188, 10) | **+219** |
| 2 | 未读 | (237, 193, 6) | **+231** |
| 3 | 已读 | (227, 230, 232) | −5 |
| 4–7 | 已读 | (220–231, 224–232, 228–234) | −3…−8 |

| 观察 | 强度 |
|---|---|
| 未读行标题偏黄/橙，已读行标题是白色 | **实测**（上表，两侧隔着两百多） |
| ~~未读行整行底色比已读略亮~~ | **撤回**，见 §0.1 |
| 那一屏未读集中在最上面 4 行 | **查出来的**（就是用户那句「前 4 个」） |
| 信箱按时间倒序 ⇒ 未读天然聚在顶部 | **实测**（`_scan_mail_rows` 的早停判据就建在倒序上） |
| 正常形态是顶部一段连续的未读 | **查出来的**（用户口径，权威） |

### 0.1 撤回：「未读行整行底色略亮」是**看错了**

v1 把它记成第二个候选信号，依据是肉眼看图。**实测反过来**：底色是整块面板的
**渐变**，和读没读过无关。

    行1 未读 底色亮度 45      行4 已读 78
    行2 未读 底色亮度 59      行5 已读 59
    行3 已读 底色亮度 88      行6 已读 49 / 行7 已读 43

已读的第 3 行（88）比两行未读（45 / 59）都亮。**标题色是唯一的信号**，
`MailRowColor.mean_luminance` 因此降级成**纯诊断字段**（判据不许看它），
类的 docstring 里也照这条改了。留着这一格只为让「颜色量出来了没有」在日志里有个
旁证，以及换版面时能从存量日志看出亮度整体漂了多少。

## 1. 现状链路（读代码得出）

### 1.1 日常那条路（占绝大多数）

    PirateLoop.run()
      → _reconcile_if_due()          两次翻信箱之间的冷却
      → reconcile_today()            开工：读战报 + 数今天几发
      → _scan_for_reconcile()        不传 should_open
      → _scan_mail_rows()            真正翻信箱的那一份

### 1.2 控制台「开始」按钮那条路

    web/app.py → persistent_service → tools/backfill_reports
      → PirateLoop.backfill_reports()   **传** should_open
      → _scan_mail_rows()

两条路的差别（读 `backfill_reports` 的 docstring 与 `_scan_for_reconcile` 的注释得出）：

| | `_scan_for_reconcile`（日常） | `backfill_reports`（点「开始」/ 手工补录） |
|---|---|---|
| 预算 | 8 屏 / `MAIL_MAX_OPENS`=8 封 | 12 屏 / 60 封 |
| 未读预算 | `MAIL_UNREAD_MAX_OPENS`=12 | 同上；`--exhaustive` 用 `BACKFILL_UNREAD_MAX_OPENS`（§3.5） |
| `skip_known`（#288 时刻跳过） | **开** | **刻意关** |
| `should_open`（预计时刻窗口） | 不传 | 有欠账时传 |
| 早停 | `_stop_after_known()` | 同一份；`exhaustive=True` 时不走 |

### 1.3 现有三道「不开这一封」的闸（按顺序）

`_scan_mail_rows` 循环里的顺序：

1. `not_before` ⇒ **break 整趟**（列表倒序，往下都是旧的）
2. `collected`（早停）⇒ 不再开封
3. `opened >= max_opens` ⇒ 不再开封
4. `may_be(wanted)` 主题闸 ⇒ 这一封不是本趟要的类型
5. `skip_known` + `_already_in_library()`（#288）
6. `should_open()` 预计时刻窗口

`_stop_after_known()` **每封重查待补清单，清单空了才停**。

### 1.4 列表页现在读到什么

- `_mail_list_rows()` → `ImageReportScreens.mail_rows()`
  → `parsers.parse_mail_rows_v2` / `mail_row_from_text`
- 文字那一路读出主题、时间、由主题得来的分类（`MailRow`）
- 颜色那一路读出每行**标题带**的暖色直方图（`mail_row_colors()`，§3.1）
- 行几何：`report_layout.LIVE_LAYOUT`，`mail_first_row=Region(700,205,1220,290)`、
  `mail_row_pitch=86`、`mail_visible_rows=6`

## 2. 未读色能改进哪几处

### 2.1 第一处也是唯一要紧的一处：**漏数据**

`MAIL_MAX_OPENS`=8 加上早停，**可能留着未读邮件不开**。而漏开一封未读邮件
**不是耗时问题**——它有一条通往「再也读不回来」的路：

1. 这一趟预算被别的邮件占满 ⇒ 没开它；
2. 下一趟它排在别人后面，如果预算仍然不够 ⇒ 还是没开；
3. 反复几趟之后它掉到**扫描下限**以外（`_routine_scan_floor`，日常那趟默认
   「现在往回 6 小时」，攻击配置页可配）⇒ `not_before` 在翻到它之前就 break，
   **日常那趟永远翻不到它**；
4. 与此同时那一发派遣掉出 `due_attack_dispatches` 的 6 小时单子 ⇒ `should_open`
   那道窗口也没了。

剩下的唯一出路是人手动 `--exhaustive` 补录。

⚠️ **有一句话 v1 第一版写错了，写在这里免得下一个人重复**：
「下一趟它已经是已读、会被 #288 那道时刻闸正确地跳过」是**错的**。
`_already_in_library` 比的是「库里该秒份数 ≥ 同屏该秒行数」，而这一封根本没入库
⇒ `0 >= 1` 不成立 ⇒ 它照开。真正把它埋掉的是**扫描下限**，不是 #288。

**强度：v1 是推理，v2 是实测** —— 生产库把这条因果链变成了数字，见 §6。

未读色直接堵住这个口子：未读 ⇒ 定义上还没开过 ⇒ **必开**，不与那 8 封抢预算。

### 2.2 第二处：把 #288 那个**近似**换成**观测**

`_already_in_library` 是拿「时刻 + 同屏同秒行数」去近似「这一封读过了没有」。
它的残余缺口写在自己的 docstring 里（同秒两行被翻页切开，历史 0.034%，
**用户已明确接受**）。未读色是直接读到同一件事：

- 未读 ⇒ 库里不可能有 ⇒ 无条件开（**不查库**，省一次查询）
- 已读 ⇒ 确实开过 ⇒ 走现有时刻闸

⚠️ **本方案（v2 也一样）没有拿未读色去替换 #288。** 已读那一侧一个字都没改，理由：
「已读 ⇒ 直接跳过、不查库」一旦标偏就会**丢战报**，而这组数只在一台机器、一个
游戏版面、四屏实拍上验过。等实机看几趟 `unread_unknown` 之后再谈（§5.3）。
**强度：推理**。

### 2.3 收益预期

| | 数 | 强度 |
|---|---|---|
| 每趟能多读回来的未读战报 | 0–4 封 | **推算**（拿用户那句「前 4 个」当量级） |
| 每封多花的时间 | 约 20 秒 | **实测**（#288 的 docstring：一封约 20 秒） |
| 最坏一趟多花 | `MAIL_UNREAD_MAX_OPENS`=12 × 20s = 4 分钟 | **推算** |
| 当前欠着的战报 | 当天到点无战报 19 / 213 发（8.9%） | **实测**（生产库，§6） |
| 省下的查库次数 | 每个未读行 1 次本地 SELECT | **推理**（可忽略） |

⚠️ 那 8.9% **不全是**这个洞造成的（也可能是战报读不出、目标错读）。见 §6。

## 3. 已落地的部分

### 3.1 取样：**自对齐的标题带**（这一版改的核心）

| 东西 | 位置 |
|---|---|
| `MailRowColor` / `MailUnreadCalibration` / `classify_unread` | `vision/mail_unread.py` |
| `CALIBRATION`（**已标定**） | `vision/mail_unread.py` |
| 定位 + 量色 `mail_row_colors()` / `_mail_time_bands()` / `_title_color()` | `vision/optional/report_screens.py` |
| 原分辨率裁片 `mail_row_crops()` | 同上 |
| `MailRow.unread: bool \| None` | `pirate_loop.py` |
| 接线 `_mail_row_unread()` | 同上 |

**为什么必须换掉「整行」。** 同一批四屏实拍、27 行样本上三种取法：

| ROI 做法 | 面积 | 未读最小占比 | 已读最大占比 | 比值 |
|---|---|---|---|---|
| 整行（v1 的 `report_layout.mail_row`） | 44,200 px | 0.0153 | 0.0092 | **1.7×** |
| 标题带，按**名义行顶**取 | 1,296 px | 0.0000 | 0.0000 | **分不开** |
| **标题带，自对齐** | 1,296 px | **0.2137** | **0.0054** | **40×** |

- **整行只有 1.7×**：黄字「攻击报告」只有约 **434** 个墨迹像素，而整行 ROI 是
  **44,200** 像素 —— 一个 R−B ≈ +220 的强信号被稀释到 1%。**实测**。
- **按名义行顶取会归零**：滚轮滚过之后列表**离网格**，四屏实测漂移
  **+11 / +23 / +38 / +82** 像素，而标题带只有 18 像素高。对齐网格那一屏取到
  0.233，离网格那两屏取到 **0.000** —— 于是「未读最小」被拉到 0。**实测**。

⚠️ **这同时解释了为什么 `mail_rows()` 的 OCR 在离网格时还能工作**：那个 ROI 有
85px 高，装得下十几像素的漂移。**颜色判据没有这份余量。**

**自对齐怎么做的**（`_mail_time_bands`）：

1. 扫这一行右侧**时刻格**的墨迹带（`x 1060..1200`、灰度 ≥ 200、连续 ≥ 6 行）
   —— 每一行都有时刻，白字高对比，整屏最好定位的东西；
2. 标题带 = `(818, 时刻带顶 − 26, 890, +18)`（四屏 27 行一致）；
3. 在这条带上算暖色直方图，其余判据一个字不变。

**三条边界，都是实测出来的，不许调**：

| 边界 | 为什么 |
|---|---|
| **不许按名义行顶取** | 离网格就归零，两侧分不开（上面那张表） |
| **x 不许往左到 792** | `x 792..812` 是信封上那个**红色角标**，也是暖色、**每一行都有**，收进来会把已读那一侧整体抬起来 |
| **时刻带定位不到的行交回 `None`** | 回落到名义行顶 = 在离网格那几屏上给出一个确定的错答案 |

**列表区之外的半行也要排除。** 实拍 `sample-mailunread-03` 顶上那条时刻带在
y=203（属于已经滚出列表的上一行），照它算出来的标题带是 177..195，已经出了列表区，
量到 **0.0054** —— 那是全部已读样本里**唯一的非零值**（捞到的是页签上的橙色角标）。
排除的判据是「时刻带的顶端落在哪一名义行的纵向范围里」，落不进任何行的整条丢掉。

⚠️ **归位判的是时刻带的顶端，不是标题带。** 对齐那一屏第 0 行的标题带是 203..221，
比名义行顶（205）还高 2 像素 —— 按标题带归位会把一行真未读整条丢掉。

**判据形状**（`vision/mail_unread.py` 的模块头写得更全）：

- 量的是标题带内**全部像素**的 `clamp(R−B, 0, 255)` 直方图（16 桶 × 16 宽）。
- **测量这一步不带任何阈值**：不先挑「墨迹」。自对齐**定位**用的那个灰度门槛不算
  —— 它决定「量哪一块」，不是「暖不暖」。
- 判据是「暖色占比 ≥ `unread_min_share` ⇒ 未读；≤ `read_max_share` ⇒ 已读；
  **中间那段 ⇒ `None`**」。两档之间必须有空档，`MailUnreadCalibration.__post_init__`
  在构造时就拦。
- 为什么量 R−B 而不是转 HSV：**这个量在本仓标定过一次**——胜负横幅就是量在 R−B 上的
  （`OUTCOME_INK_THRESHOLD`：横幅峰值 155/192，幽灵文字与面板背景不超过 10，
  **实测**七张详情页）。同一块半透明面板、同一套配色。

**`None` 有五种来源，下游是同一件事（退回现有行为）**：没标定 / 取图侧没这个能力 /
**时刻带定位不到** / `pixels == 0` / 落在空档里。

### 3.2 标定那一组数

    CALIBRATION = MailUnreadCalibration(
        min_warmth=16,
        unread_min_share=0.1443,
        read_max_share=0.0748,
        measured_on="2026-09-08 实拍 4 屏（自对齐标题带）",
    )

空档 0.0748..0.1443，两侧实测 **0.2137 / 0.0054** —— **门槛落在空档里，不在钢丝上**。

⚠️ **这两个数比「照现在的取样复算」略往外让了一点，是刻意的。** 现在的取样把列表区
之外那半行整条丢掉了，于是已读那一侧的实测上界从 0.0054 掉到 **0.0000**，照它复算
会得到 **0.1425 / 0.0712**。**没有采用**：那个 0.0054 是页签上的橙色角标漏进标题带
量出来的，而「哪天某个版面又让一块暖色角标漏进某一行」正是这道闸会遇到的错法。
用样本更全的那一组，已读那一侧就多一层余量，而代价只是几行「判不出」
（= 退回改动之前的行为）。

### 3.3 策略层：**第三笔预算**

改在 `_scan_mail_rows`。`forced = row.unread is True`：

| 闸 | 未读越过？ | 为什么 |
|---|---|---|
| `not_before`（整趟下界） | **不越过** | 它是整趟唯一的时间边界；越过等于放开无界翻页。残余风险见 §7 |
| 早停 `collected` | 越过 | 早停假定「往下都读过了」，对未读不成立 |
| `opened >= max_opens` | 越过 | 未读不与「可能已读过」的那 8 封抢预算 |
| `may_be(wanted)` 主题闸 | **不越过** | 「必开」的范围是本趟要的那几类；一封未读的侦察报告下一趟照样开得到。这也是「必开」有界的第二道保障 |
| `skip_known` / `_already_in_library` | 越过（**且不查库**） | 一个推测不该否掉一个观测 |
| `should_open` 预计时刻窗口 | 越过 | 同上 |

撞上未读上限的行**退回去和别人抢常规预算**（不是直接丢），并记进
`MailScan.unread_over_budget` ——那一格不为 0 就是告警。

**跨屏那一条**：未读在倒序列表里是**连续的一段**（用户口径），可能正好被屏幕下边缘
切开。所以「收齐了就收工」多了一个条件：**这一屏有未读且未读预算没用满时不收工**。
下一屏没有未读时立刻不成立，所以它不是无限往下翻。

### 3.4 上界为什么不能省

一组标偏的阈值（把已读判成未读）会让每屏六行全进这条路，4 屏 × 6 行 × 20s ≈ 8 分钟，
而日志上看着一切正常。**推算**。

### 3.5 ⚠️ 重审：「开到第一行已读为止」为什么**没有**取代这个上限

用户口径（2026-09-08）「正常情况下 是连续的未读批量」把正常形态定成了「顶部一段
连续的未读」。既然连续，「从顶往下开、开到第一行已读为止」看着**自带界**，
比一个写死的 12 更贴事实。**审过之后没有采用**，三条理由：

1. **它是停止条件，不是预算。** 这个上限存在的唯一理由是「一组标偏的阈值把已读判成
   未读」，而那种失效恰好让「第一行已读」**永远不出现** —— 停止条件在它最该起作用的
   那一刻正好失效。上限必须**在标定错的时候仍然成立**，所以它不能建在「颜色读得对」
   这个前提上。
2. **它读偏的方向是贵的那一侧。** 一行读偏（或者一封别类型的已读邮件插在中间）就把
   整段未读堵在第 0 行，而漏开一封未读的代价是「再也读不回来」——正是这道闸要修的
   那件事。上限读偏只多花时间。
3. **「连续」这条事实已经用在该用的地方了。** §3.3 那个「这一屏有未读就再翻一屏、
   第一屏没未读就收工」就是**屏粒度**的「开到第一行已读为止」。它落在**继续翻**
   那一侧，猜错只多花翻一屏的两秒；把同一条事实搬到「停止开封」那一侧，猜错就丢战报。

**于是这条口径在这里只改一件事：它把 12 从推理变成了有出处的数。**
12 = 两屏的行数（一屏 `MAIL_SCAN_ROWS` 行）；取两屏而不是一屏，是因为连续的那一段
正好被屏幕下边缘切开时一屏装不下 —— v1 写的是推理，现在有口径。

**改的是另一件事：上限成了 `_scan_mail_rows` 的参数，补录那条路传大值。**
存量的历史空洞（散在 24–72 行深处、时刻早就不在任何 `should_open` 窗口里的那些未读）
原先**两条路都到不了**：日常那趟够不到（掉出扫描下限），而补录虽然有 60 封的预算，
未读那一档仍旧封在 12，撞了之后剩下的**退回常规预算**、又被时刻闸拦住。所以：

    BACKFILL_UNREAD_MAX_OPENS = BACKFILL_MAX_OPENS   # 60

⚠️ **只给 `--exhaustive`，不给控制台「开始」那一档**：「开始」每按一次都跑一趟
（而且按约定要读完战报才放行任务），把它的最坏时长翻一倍是不能接受的。
最坏时长仍然有界：两笔预算加起来也开不过**看得到的行数**（12 屏 × 6 行 = 72 行），
72 × ≈20 秒 ≈ 24 分钟 —— 与这个入口原本 15 分钟的量级同档，而且只有「整个信箱都是
未读」时才摸得到，那种情形下这 72 封正是人手动跑补录想开的东西。

### 3.6 `MAIL_UNREAD_MAX_OPENS` 属于哪一类

**运维旋钮**（不是标定常量）：活动期间信箱一次堆几十封未读时用户会想调大它。
v1 暂时写死的理由是「`CALIBRATION` 还是 `None`，这条分支一次都走不到」——**那个理由
现在没有了**。这一版把它变成参数（两条路各取各的默认值），但**还欠一个配置页旋钮**：
挪上去要给攻击配置表加一列（`storage/models.py` 那张表 + 一次迁移），这一版刻意不碰
库结构。欠账连同要写给用户的那句话（「调大 = 少丢战报、多花时间」）记在常量的注释里。

### 3.7 日志（本仓硬要求：出事时能只靠库里 `system_log` 定位）

**人话**（`say_mail_unread_tally`），两条路各打一次（`_scan_for_reconcile` 与
`backfill_reports`）：

- 没标定：`未读色：还没标定，这一趟 N 行全按「读不出」处理（判据没通电）`
- 标定之后：`未读色：判成未读 A 行、读不出 C 行（共看了 N 行）；因未读越过上限与早停开了 D 封`
- 撞上限：`warn()` 一条 `…行未读撞上未读开封上限（<这一趟真用的那个数>）…；可能漏了未读邮件`
- 量不出来：`列表页颜色量不出来（…）；未读判据这一趟起全部退回按时刻处理`
- **定位不到时刻带**（这一版新增）：`列表页有 N/M 行定位不到时刻带；那几行的未读色判不出`
  + 一条 WARNING `列表页未读色定位不到时刻带`

后两条**一个进程只说一次**，否则每屏一条把真东西淹掉。

**结构化**（`mail_unread_payload`），拌进两条现成的汇总日志：

| 键 | 回答什么 |
|---|---|
| `unread_calibrated` | **只有新代码写得出的键**——分得出「新版本但没标定」和「旧版本」 |
| `unread_measured_on` | **生产上跑的是哪一组数**（库里查不到代码分支，只有这个键分得出） |
| `unread_seen` | 判成未读几行 |
| `unread_opened` | 因未读越过上限/早停开了几封（= 要是没这道闸，这几封本来会被漏掉） |
| `unread_unknown` | **体检指标**：没标定时必然 == `observed`；标定后居高不下 ⇒ 那组数在实机上不成立 |
| `unread_over_budget` | 可能漏了未读邮件 |
| `unread_budget` | 这一趟未读那一档的预算（日常 12 / 补录 60）——撞的是哪个上限 |

探针那条日志（`信箱列表页未读色标定探针`）的每一行另加一个 `located` 键：
分得出「这一行是白的」和「这一行根本没定位到」。**定位不到的行也照样进 `rows`**，
否则 `rows` 会和 `mail_row_png_base64` 错位（那两个列表靠下标对起来）。

⚠️ **`unread_unknown` 分不出「定位失败」和「落在空档」**，两者处置完全不同（前者去看
版面几何，后者去重采重标）。分辨办法是看有没有那条 `定位不到时刻带` 的 WARNING。

## 5. 标定是怎么做的，以及还欠什么

### 5.1 三步（工具：`tools/mail_unread_probe.py`）

1. **采**（实机上，跑一趟任务就够）：

       set EVO_HELPER_MAIL_UNREAD_PROBE=1

   `_record_mail_unread_probe` 会把每屏六行的**原分辨率裁片 + 颜色读数**记进
   `system_log`（message = `信箱列表页未读色标定探针`，一个进程最多 6 屏）。
   ⚠️ **落库不落文件**：实机在另一台机器上，本地 `var/logs` 跨机取不到。
   ⚠️ **存裁片不是整帧缩略图**：这里事后要从图上读的是**颜色**，1920→480 会把
   半透明面板上的黄字和白字混成同一团灰。

2. **看**（只读 SELECT，落 PNG）：

       python -m evo_helper.tools.mail_unread_probe --out var/fixtures/vision/mail-unread

   文件名自明：`<日志id>-row<行号>.png`。人眼认出哪几行是未读。

3. **算**：

       python -m evo_helper.tools.mail_unread_probe --out ... --unread 8891:0,1,2,3 --unread 8934:

   它在 16 个桶边界上挑落差最大的那一档，两侧各让 1/3 落差留出空档，
   **分不开就拒绝出数**（只给两组数字）。

   ⚠️ **标签只认人给的**：只有 `--unread` 点到的那几条记录参与标定，其中没列出的行
   算已读；没点到的记录**一行都不参与**（「这一屏我没看过」≠「这一屏全是已读」）。
   `8934:`（冒号后面空着）= 「看过，全是已读」。

### 5.2 2026-09-08 那次实际走的路

那次是**前台实机授权**下直接采的四屏实拍（`var/logs/sample-mailbox-221612.png`、
`sample-mail-down4-221810.png`、`sample-mailunread-03-221918.png`、
`sample-mailunread-04-221919.png`），走 `propose_calibration` 离线算的。
⚠️ **实拍图一律不进 Git**（`/var/` 被 `.gitignore` 挡着），所以这四张图**只在主仓的
`var/logs` 里**，worktree 里没有；本文档引它们只是为了留出处，任何用例都不许依赖它们。

标注由**两条独立证据**定（逐像素目视 + 整屏黄墨迹扫描），不是从占比反推的。

### 5.3 还欠什么

1. **配置页旋钮**（§3.6）：要加一列 + 一次迁移，这一版刻意不碰库结构。
2. **上机看几趟日志的 `unread_unknown`：它必须掉下来。** 居高不下 = 那组数不成立；
   分不清是定位失败还是落在空档时，看那条 `定位不到时刻带` 的 WARNING。

## 6. 这个洞有多大 —— **生产库实测（2026-09-08）**

v1 这一节写的是「我查不了，要用户来查」；现在查过了。

**① 撞开封上限的趟数**：当天 3 趟进信箱（#288 之后有日志的那 3 趟）跳过
2 / 12 / 1 封，而**「真开」的封数正好都是 8 = `MAIL_MAX_OPENS`，3/3 趟撞上限**。

**② 深处躺着的未读**：信箱约 24 / 30 / 36 / 72 行深处有 4 封未读的攻击报告，
时刻 09:54:02 / 09:53:47 / 08:44:07 / 05:45:04。按 ±5 秒查 `battle_reports`：

    09:54:02  库里 0 份  缺
    09:53:47  库里 0 份  缺
    08:44:07  库里 0 份  缺
    05:45:04  库里 0 份  缺

**4 封全缺**，躺了 8.5–16.7 小时，从没被开过。

**③ 到点无战报**：当天派遣里 **19 / 213 发（8.9%）**。

⚠️ **③ 数出来的不全是这个洞造成的**（也可能是战报读不出、目标错读）。要把这个洞
单独摘出来，得看 ①② 与 ③ 在**同一趟**里是否同时出现 —— 那一步还没做。

⚠️ **②「4 封全缺」和用户口径合起来才读得对**：正常形态是顶部一段连续的未读，
所以这 4 封散在深处本身就是**历史空洞**的样子，不是常态。它们归补录管（§3.5）。

以下四条**只读** SELECT 是把这条因果链继续量下去的口子（时间窗自己调）：

```sql
-- ① 撞开封上限的趟数占比
SELECT count(*) FILTER (WHERE (payload_json::json->>'opened')::int >= 8) AS 撞上限,
       count(*)                                                          AS 总趟数
FROM system_log
WHERE message = '开封前按时刻跳过已入库的邮件'
  AND logged_at_utc >= now() - interval '14 days';
```

```sql
-- ② 早停触发的次数
SELECT count(*) FROM system_log
WHERE message LIKE '%往下都是更旧的报告，不再开封%'
  AND logged_at_utc >= now() - interval '14 days';
```

```sql
-- ③ 撞上限那句话的次数（分子分母都要，别只看分子）
SELECT count(*) FROM system_log
WHERE message LIKE '%到上限；剩下的留给下一趟%'
  AND logged_at_utc >= now() - interval '14 days';
```

```sql
-- ④ 真正的「漏了几份」：判成「战报永远不会来了」的派遣数。
-- 判据是 storage/intel.py 现算的（not report_received AND
-- dispatched_at <= now - MAX_REPORT_AGE），库里没有这个标记列。
SELECT count(*) FROM attack_dispatches d
JOIN attack_intents i ON i.id = d.intent_id
LEFT JOIN battle_reports r ON r.dispatch_id = d.id
WHERE d.accepted
  AND r.id IS NULL
  AND d.dispatched_at_utc <= now() - interval '6 hours'
  AND d.dispatched_at_utc >= now() - interval '14 days';
```

⚠️ **④ 的分母是同期 `accepted` 的总派遣数**，请一并取出——只报分子的话
「14 天丢了 N 发」既可能是 0.3% 也可能是 30%。

**标定落地之后还要看的一条**：`unread_opened` 每趟不为 0 就说明这道闸在救东西，
而 `unread_unknown` 必须掉下来（§5.3）。

## 7. 残余风险 / 明确不做的事

1. **未读比 `not_before` 还旧的那些读不到。** 日常那趟的下界是「现在往回 6 小时」
   （可配）。让「必开」越过它等于放开无界翻页，而 `not_before` 是整趟唯一的时间边界。
   出路是人手动 `--exhaustive` 补录，而补录那条路现在有自己的未读预算（§3.5）。
   **这条是有意留的**。
2. **未读超过预算时可能漏。** 见 §3.3。日志会喊（`unread_over_budget` + `warn`，
   而且报的是这一趟真用的那个数）。
3. **这组数可能随游戏版面失效。** 体检指标是 `unread_unknown`（§3.7）。
   四屏 24 行上定位成功率是 24/24，所以那条 `定位不到时刻带` 的 WARNING
   一出现就意味着版面变了。
4. **离网格很深时，一行的名义 ROI 里装着的是它自己的标题、却可能是上一行的时刻文字**
   （那一行的时刻带贴着 ROI 下沿被切掉）。那是名义行 ROI 本身的老毛病（点击坐标也按
   名义行算），**不是这一版引入的**；日常那趟每次进信箱都先拖回顶部正是为了压住它。
5. **不动 #288 的已读那一侧。** 见 §2.2。
6. **不改 `MailRow.identity`。** 未读不进跨屏身份：它是会变的（开过一封之后
   那一行就变已读），拿会变的东西当身份会让同一封邮件跨屏认不出来。
7. **没写 `.changes/` 片段**（编号 = PR 号，PR 还没开）。
