## 2. 需求逐条分析

### 需求 1：可配置多个出发星球 + 各自航线数，不校验总数

**现状缺口**：`mission_tasks` 一行只有**一个** origin。

**⚠️ 问题 1.1：多出发星球是「一个任务多个 origin」还是「多个任务各一个 origin」？**

看需求 2——「提取 50 个最高军力 bot 坐标后，根据**已配置的出发星球**……」——
50 个是**一个共享的池子**，由多个 origin 分着打。多个任务各自取自己的前 50 会重叠，
同一个 bot 被两颗星球同时打。

> **建议：一个任务，多个 origin。** 新表 `mission_task_origins`
> （`task_id, galaxy, system, position, fleet_lines, enabled`），
> `mission_tasks` 上原有的单 origin 三列保留给区域攻击那一支（不要动它，
> 那是用户配好在跑的）。

**⚠️ 问题 1.2：「不必校验总航线数」是什么意思？**

两种读法：(a) 不检查各 origin 航线数之和 ≤ 全局上限；(b) 连游戏本身的同时派遣上限也不管。

> **建议：按 (a) 实现。** 每个 origin 各有各的预算，程序不做求和校验。
> 但游戏的硬上限该撞还是会撞——`RoundExhausted("同时派遣的舰队数量已达上限")`
> 这条路径**必须保留且必须被当成正常收尾**（`_sweep` 的注释里记着：
> 它曾经从这里漏出去，让调度器连撞三次就把整条 bot 链路自动停用了）。

### 需求 2：按出发星球坐标，选择最优攻击时间

**⚠️ 问题 2.1：「最优的攻击时间」有三种互不相同的解释。**

| 解释 | 目标 | 算法 |
|---|---|---|
| (a) 每发都最快 | 每个目标各自挑最近的 origin | 贪心，可能把所有目标堆到同一颗星球 |
| (b) 整批总时间最短 | 最小化总飞行时间 | 带容量的指派问题 |
| (c) **整批最早打完** | 让所有航线都别闲着 | 按航线容量分配，近的优先 |

> **建议：按 (c)。** 用户反复表达过的诉求是「一夜多打几发」
> （2026-08-14：「怎么样的选择可以减少每个轮次的等待时间尽快发出」）。
> (a) 会让一颗星球排满队而另一颗闲着。
>
> 具体做法：目标按军力取前 N → 每个目标算出到**每个** origin 的环形距离 →
> 用「最小剩余容量优先 + 距离最近」把目标指派给 origin，直到航线用完。

**⚠️ 问题 2.2：绝对飞行时间算不出来，但「谁更近」算得出来。**

`domain/distance.py` 模块头里有实测拟合的公式：

    飞行秒数 = 2 + 26.5165 × √D
    D = 同银河 1162 + 31.71×恒星系环形距离 / 跨银河 20000×银河环形距离

八个实测点全中（±1 秒）。**但那 `26.5165` 里裹着舰队速度（14.520），
只在那一套编组上验过。** 而需求 4 要按档换预设，不同预设速度不同。

> **建议：不要去算绝对时间，只用距离排序。** 排序是**纯序**的，对任何速度都成立
> （同一套编组下，距离近的一定飞得快）。这也是 `domain/distance.py` 模块头
> 「这里**不**算飞行时间」那一段写着的界限——**不要为了这个需求去突破它**。
>
> 真要算时间，另开模块、显式收 `speed` 参数、并用多套编组的实测标定系数。
> 那是独立的一件事，不在本次范围内。

**⚠️ 问题 2.3：换出发星球是有成本的。**

派遣前要在游戏里真的切到那颗星球（`game.planet_list.PlanetSwitcher`，
`tools.pirate_loop.ensure_origin_planet`），实测约 20 秒并且会失败。

> **建议：按 origin 分批下发，不要逐个目标交替。** 指派算完之后，
> 命令行按 origin 分组，一组打完再切下一颗。交替下发的话，
> 每一发都要付一次切换。

### 需求 3：航线释放后，扫描时间 ≥6 小时（可配）才重扫榜单

**⚠️ 问题 3.1：「上次扫描时间」是哪个？**

三种可能：整趟采集的完成时刻 / 每个 bot 各自的 `military_score_at_utc` /
榜单前 N 名那一段的最新时刻。

> **建议：用「候选池里最旧的那个 `military_score_at_utc`」。**
> 理由：我们只关心**将要打的那批**新不新鲜，整张榜有没有重扫无所谓。
> 用整趟完成时刻的话，一次断线中止的采集会让「上次扫描」永远停在很久以前。

**⚠️ 问题 3.2：重扫一趟到 bot 区要约 6 分钟，这段时间航线闲着。**

实测（2026-08-15）：开榜 18 秒 + 盲拖 40 屏 168 秒 + 检测段 38 屏 166 秒 ≈ **6 分钟**
才够到第一个 bot；而关掉面板再打开**列表回顶部**（用户实测），所以这 6 分钟
每次都要重付。

> **建议：把重扫做成「先判断、再决定要不要等」，并且把等待如实打进日志。**
> 不要静默地让航线闲 6 分钟——那正是用户 2026-08-13 抱怨过的「等待间隙没干活」。
>
> 更好的做法（如果实现得动）：航线释放时**先用手上的数据发出攻击**，
> 同时把「该重扫了」记下来，交给调度器在下一个空隙里跑 RANKING 任务。
> 军力值不是每秒都在变（见下），晚几分钟刷新的代价远小于让航线空转。

**⚠️ 问题 3.3：军力值多久真的会变？**

- **每周一 UTC+0 随机刷新**（用户口径 2026-08-14）——一周之内基线不动
- 但**你自己打完之后对方军力会掉**，从而跌出前 50

> 所以 6 小时重扫的真正价值是**把已经打瘫的 bot 从池子里换掉**，
> 不是追踪刷新。这条要写进注释——否则下一个人会以为可以调成 24 小时。

**⚠️ 问题 3.4：谁来触发重扫？**

RANKING 是独立的 `MissionKind`，由调度器调度；BOT 任务**不能**自己起一个 RANKING。

> **建议：BOT 任务只读 `military_score_at_utc` 判新鲜度，不触发扫描。**
> 数据太旧时它照常按手上的数据打（见 3.2），调度器会在下一个空隙里自然跑 RANKING。
> 让一条链路去启动另一条，会绕开调度器的串行与抢占——那正是「两个进程抢鼠标」
> 这个坑（本次通宵实机踩过）。

### 需求 4：按军力分档选不同预设

**⚠️ 问题 4.1：档位阈值必须可配，不许写死。**

两个理由：

1. **现在的数据还不够干净。** 撤回 30 个错读之后，顶端是 93,920，而前 7 名
   挤在 93,050–93,920——除以 10 正落在 P50–P75。**这一批仍然存疑**，
   要等下一轮带名次入库、拿降序复核之后才敢用。
2. **军力每周一刷新**，写死的阈值下周就要重标。

> **建议：阈值放任务参数里**（`{"tiers": [{"min": 20000, "preset": "CCC"}, ...]}`），
> 页面上可改。代码里**不许有默认阈值常量**——有默认值就一定有人不改它。

**⚠️ 问题 4.2：预设标题也必须可配。**

预设是用户在游戏里自己维护的。本仓刚被这件事咬过：`BOT_ATTACK_PRESET = "BBB"`
写死在代码里，而 2026-08-15 那一夜预设条读不出 BBB，整晚一发没派。

> 已有的硬规矩（`domain.bot_round.BOT_ATTACK_PRESET` 注释里）：
> **存的必须是标题原文**，派遣时按标题在预设条上 OCR 找。
> 助手**不读也不校验预设内容**（用户口径 2026-08-14：「选游戏内预设只认标题，
> 不读不校验不讨论内容」）。

**⚠️ 问题 4.3：分档与上限是同一件事的两面。**

用户 2026-08-14：「军力确实要设置上限」「高军力的 bot，不是 AAA/BBB 这个预设
能打得动的」。

> **建议：上限 = 最高档的上界。** 军力高于所有档位覆盖范围的目标**直接不进池**，
> 而不是用最强的预设去试。`strongest_then_nearest` 已经有 `max_score` 参数，
> 复用它，由分档配置推导出来。

**⚠️ 问题 4.4：预设必须记进派遣台账。**

`attack_intents.preset`（name + signature）已经有了。分档之后**每发用的是哪个预设
必须如实写进去**——否则事后没法回答「CCC 打这一档打得动吗」，而那正是分档要验证的东西。

**⚠️ 问题 4.5：只在军力攻击下生效。**

区域攻击那一支保持「一律 BBB」不变。这是用户明确划的界，也是最小风险路径。

### 需求 2 补充：⚠️ **前 50 名会把这一轮卡死**

这一条需求里没提，但不改一定出问题。

现在 `strongest_then_nearest(targets, origin, take=50)` 是把**整张表**截断到 50。
这 50 个一旦本轮都打完，池子就空了——而库里还有四千多个 bot。任务会一直报
「还剩 0 个未完成」然后收工，**而且不报错**。

> **建议：截断前先滤掉「本轮已经处理过的」。** 判据现成：
> `domain.bot_round.phase_of(repository.bot_dispatch_facts(target, since=round_started_at_utc))`
> ——只把 `NEEDS_ATTACK` 那些放进候选，再取前 50。
>
> 注意这会让每次选靶都多问一遍库（每个目标一次）。现在 `_bot_remaining` 已经这么做了，
> 照它的形状来。

## 3. 建议的设计

### 3.1 数据模型

```
mission_task_origins
    id, task_id -> mission_tasks.id
    galaxy, system, position
    fleet_lines        每颗星球自己的航线预算
    enabled            临时停用某颗星球而不删配置
```

`mission_tasks.origin_*` / `fleet_lines` 保持不动（区域攻击在用）。
军力攻击的任务从 `mission_task_origins` 读；一行都没有时回落到 `mission_tasks` 上那一颗。

### 3.2 任务参数

```json
{
  "by_military": true,
  "top_n": 50,
  "rescan_after_hours": 6,
  "tiers": [
    {"min_score": 20000, "preset": "CCC"},
    {"min_score": 5000,  "preset": "BBB"},
    {"min_score": 0,     "preset": "AAA"}
  ]
}
```

- `tiers` 按 `min_score` 降序，**没有默认值**：不配就退回「一律 BBB」并在日志里说明
- 上限 = `tiers[0].min_score` 对应档的上界；军力高于最高档覆盖范围的不进池
- `rescan_after_hours` 可配，默认 6

### 3.3 算法

```
1. 候选 = 库里所有 bot，滤掉本轮已处理的（phase != NEEDS_ATTACK）
2. 滤掉军力超过上限的（读不出军力的**保留**——不知道多强 ≠ 一定太强）
3. 按军力降序取前 top_n
4. 新鲜度：池子里最旧的 military_score_at_utc 超过 rescan_after_hours 就打日志
   （**不阻塞**，见 3.2 的建议）
5. 指派：按「航线剩余容量 + 环形距离」把目标分给各 origin
6. 每个目标按军力查档、定预设
7. 按 origin 分组下发，一组打完再切星球
```

### 3.4 命令行

`bot_command` 现在是 `--targets ... --origin ... --attack`。多 origin 之后
一条命令只能带一颗星球，所以：

> **建议：一次派遣一颗 origin 一组目标**，调度器按组多次起 runner，
> 而不是让 runner 自己去切星球循环。理由：runner 中途被杀时，
> 「切到一半」比「没开始」难收拾——而实机上被杀是常态。

预设按目标不同，所以命令行要能逐目标带预设：
`--targets 2:140:2=BBB 2:400:1=CCC`（或另开一个参数，形状由你定，
但**必须让 `mission_runs.command` 事后回答得了「哪一发用了哪个预设」**）。

## 4. ⚠️ 不许做的事

这些每一条都是本仓踩出来的，违反了不会报错，只会静默出错。

1. **不许把距离存成列。** 距离是 `(目标, 出发星球)` 的函数，多出发星球正是它存在的
   理由（`domain/distance.py` 模块头）。存成列的那天，第二颗星球会拿着按主星算的距离排序，
   **而且完全不报错**。
2. **不许用 `abs(a - b)` 算坐标距离。** 银河与恒星系**都是环**（实测：从 2:137 打
   `2:499` 只要 1969 秒，比 `2:287` 的 2042 秒还快）。用 `galaxy_gap` / `system_gap`。
3. **不许在 `domain` 里算飞行时间。** 见问题 2.2。
4. **不许给档位阈值和预设标题写死默认值。** 见问题 4.1 / 4.2。
5. **不许让 BOT 任务去启动 RANKING 任务。** 见问题 3.4。
6. **不许把「读不出军力值」当成 0 分。** 0 分是读到的事实，None 是不知道。
   这个仓有一条硬规矩：**猜出来的数不许长得像量出来的**。
7. **不许动用户已经配好的区域攻击那一支**（`mission_tasks` 上的单 origin、
   `first_system`/`last_system`、一律 BBB）。
8. **不许删掉 `RoundExhausted` 那条路径**，见问题 1.2。

## 5. 自测要求

### 5.1 四道闸门（CI 一致，缺一不可）

```bash
.venv/Scripts/python.exe -m pytest tests -q
.venv/Scripts/python.exe -m ruff check src tests
.venv/Scripts/python.exe -m ruff format --check src tests
.venv/Scripts/python.exe -m mypy src
```

注意 `ruff format --check` 也在 CI 里；`mypy` 的参数是 `src`（不是裸跑）。

### 5.2 ⚠️ 变异测试是真正的质量闸

**测试全绿不算数**——绿的测试可能什么都没测到。本次开发中变异测试抓到过：

- 掩膜函数写对了，但 `name_words` 忘了调用它（单测掩膜的用例全绿）
- 停滞确认次数被写死成 1（常量的单测全绿）
- 仓储的「更新已有行」分支完全没覆盖（只测了新建路径）

**做法**：每条护栏改坏一次，确认测试变红，再还原。

⚠️ **过期 `.pyc` 会让变异测试撒谎**：改动只换几个字符、文件长度不变时，
Python 会读旧字节码（pyc 只按 mtime 秒 + 长度校验），于是**改坏了也是绿的**。
`-B` 没用（只阻止写、不阻止读）。**每次变异前删 `__pycache__`。**

### 5.3 本次必须逐个改坏验红的护栏

| 改坏什么 | 期望 |
|---|---|
| 前 50 名不滤掉本轮已处理的 | 红 |
| 指派时不按距离，随便给一个 origin | 红 |
| 指派时忽略航线容量，全堆到一颗星球 | 红 |
| 分档阈值写死一个默认值 | 红 |
| 军力读不出的目标被上限扔掉 | 红 |
| 军力读不出的目标被当成 0 分归到最低档 | 红 |
| 新鲜度判断阻塞了派遣 | 红 |
| 距离用 `abs` 而不是环形 | 红 |
| 多 origin 时命令行不分组（交替下发） | 红 |
| 派遣台账里不记预设 | 红 |
| 区域攻击那一支被军力逻辑影响 | 红 |

### 5.4 实机验证

代码闸门过了**不等于能跑**。本次开发必须实机验的：

1. 多 origin 真的切得过去（`PlanetSwitcher` 回读确认「起点」）
2. 分档真的选中了对应预设（**读到名字 ≠ 点中它**，2026-08-15 刚踩过）
3. 航线用完时 `RoundExhausted` 被当成正常收尾而不是崩溃

⚠️ **启动游戏需要用户当次授权**，不跨场次继承。工作日 UTC+8 工作时间内尤其如此。
写完停下来等授权，不要自己拉起游戏。

## 6. 开发规范

- **中文注释与文档**，源文件 `# -*- coding: utf-8 -*-`，读写一律 UTF-8
- 控制台是 GBK：输出里不要放 `✓`/`✗`，会 `UnicodeEncodeError`（仓里有
  `make_console_encoding_safe()`）
- **注释写「为什么」，不写「是什么」。** 本仓的注释密度很高而且都在解释
  取舍与事故，照着周围的写。特别是：
  - 每个「看起来可以简化」的地方，说明为什么不能简化
  - 每个魔数，说明它是**量出来的**还是**推出来的**（推出来的要标 ⚠️）
  - 每条实机踩出来的规矩，带上日期和现象
- 可选依赖（pytesseract 等）缺失时**降级运行而不是报错**
- 新常量放 `domain` 或 `game.*_ui`，**不要散在 `tools` 里**
