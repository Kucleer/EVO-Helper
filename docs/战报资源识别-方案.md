# 战报资源识别 —— 评估与实现方案

用户需求（2026-08-17）：「你能识别并记录战报中这些资源的数量么」，并提示「这些资源可能显示 `123`、`2.51K`、`25M`、`1.2B`」。

**结论：能做，工作量中等，但有三个必须先解决的判据问题，其中一个还没验证。**

## 一、要读的是哪一块

战报详情页（未滚动那一屏）从上到下：

```
获得资源:                       ← 12 格（4 列 × 3 行），每格 = 图标 + 数字
  [图标] 0   [图标] 0   [图标] 0   [图标] 0
  [图标] 0   [图标] 0   [图标] 0   [图标] 0
  [图标] 0   [图标] 0   [图标] 0   [图标] 0
残骸:                           ← 3 格
  [图标] 300  [图标] 100  [图标] 0
舰队回收              20%
生成卫星概率           0%
```

资源类型的对照表在「太空舱 → 材料」页：暗能量、合金碎片、银河素、晶体矿石、能量凝胶、泰坦立方、收割者碎片、湮灭之星核心、弹头许可证、贸易许可证。

`battle_reports` 现在存的是：胜负、双方单位数、双方损失数、匹配状态。**没有任何资源字段**——这是新增。

## 二、三个判据问题

### ⚠️ 问题 1（最大的未知，必须先验）：网格是不是固定的

用户提供的那份 FAIL 战报里 **12 格全是 0 也全都显示出来了**，这**暗示**布局是固定网格、固定顺序——那样「位置 → 资源类型」就是常量映射，**不需要做 12 个图标模板匹配**，工作量差好几倍。

**但这只是一份样本，而且是零收获的那种。** 必须拿**一份真正打赢、有非零收获的战报**确认：会不会只显示有收获的那几种、导致格子位移。

**这个前提验不掉就不要动手**——猜错的话整套位置映射会把资源类型全对错，而且错得很安静（数字都对，只是安在了别的资源名下）。

### ⚠️ 问题 2：数字格式有两套，而且会打架

用户提示的是 `123` / `2.51K` / `25M` / `1.2B`。但太空舱那一页显示的是：

```
暗能量      5.388.122      ← 点是千分位分隔符 = 5,388,122
能量凝胶    1.349.631      ← 同上
```

所以 `1.349` 是**歧义**的：可能是 1349（分隔符），也可能是 1.349（小数）。

**判据只能是**：

> 带 K/M/B 后缀 → 点是**小数点**；不带后缀 → 点是**千分位分隔符**

（资源数量都是整数，所以「不带后缀时点是小数点」这个解读天然不成立。）

⚠️ **必须拿五种真实样本一起验**：`5.388.122`、`1.349.631`、`2.51K`、`1.2B`、`123`。只测其中一种，另一种就会静悄悄读错三个数量级。

### ⚠️ 问题 3：带后缀的值是四舍五入的，读回来就丢精度

`2.51K` 的真值在 2505–2514 之间。

**这个坑仓库里已经踩过并记在案**——`storage/models.py` 里 `battle_reports.attacker_units` 的注释写着：

> 大舰队的数量显示成 `5.36K` 这样的四舍五入值，**逐行相加凑不出精确总数**

所以带后缀读回来的资源值**必须标成近似**，不能和精确值混在一起累加。本仓硬规矩：猜出来/约出来的数不许长得像量出来的（同一条规矩在军力值 `military_score_estimated` 上已有先例）。

## 三、实现方案

### 1. 解析器：扩展现有的，不要另写一份

`tools/ranking_scan.py:63` 的 `parse_score` 已经处理了 K/M 后缀，而且 PR #152 刚把它改成走 `Decimal`（`float("64.96") * 1000` 会得到 `64959.99999999999`，那批脏值已经落进过库）。

新解析器要在它的基础上加两件事：**B 后缀** 和 **千分位分隔符**，并**同样走 `Decimal`**。

建议把它下沉成一个共用函数（例如 `domain/quantities.py`），军力榜和战报都用同一份——两份实现迟早分家，而分家的那天不会有人发现。

返回值要带**精度标记**：`(数值, 是否为近似值)`。带后缀 = 近似，纯数字 = 精确。

### 2. 存储：新开一张明细表，不要在 `battle_reports` 上加 15 列

```
battle_report_resources
  report_id   FK -> battle_reports.id
  kind        'GAINED' | 'DEBRIS'        ← 获得资源 / 残骸
  slot        0..11                       ← 网格位置，即资源类型
  amount      BigInteger
  approximate Boolean                     ← 见问题 3
```

理由：资源种类会随游戏更新增减，加列的话每次都要迁移；而且 12 格里大多数是 0，明细表可以只存非零的（**但要在文档里写明「没有行 = 0」，否则会被读成「没读到」**）。

⚠️ 存 `slot` 而不是资源名：**位置是观测到的事实，名字是解释**。解释错了以后能靠 slot 重新映射，把名字硬编进去就找不回来了。资源名放一张常量表，页面上再翻译。

`舰队回收 %` 和 `生成卫星概率 %` 两个百分比直接加在 `battle_reports` 上（各一列即可，不会再增）。

### 3. 采集时机：接在战报截图那条路上

PR #158 已经在读战报时截图（`Region(700, 105, 1220, 800)`，WEBP q90 约 39 KB，写进 `system_log.payload_json`）。**资源识别接在同一趟里**，不额外开一次导航——那一屏本来就已经在眼前了。

### 4. 顺序：先验前提，再动手

1. 拿一份**有非零收获**的战报，确认网格布局固定（问题 1）
2. 用同一份截图标定 12 + 3 个数字格的 ROI
3. 写解析器 + 用五种格式的真实样本做用例（问题 2）
4. 落库 + 页面展示（攻击日志那一行点开能看）

第 1 步验不掉就退回图标模板匹配——那要为 12 种资源各做一个模板，工作量翻几倍，而且图标小、容易误匹配。

## 四、值不值得做

**值得，但不紧急。** 它的价值是回答「这一发到底赚了多少」——目前只知道胜负，不知道收益。有了它才谈得上「哪些目标值得打」。

但排在这些后面：战报读取本身刚修好（PR #158）还没实机验证；**没有战报的时候，资源识别无事可做**。
