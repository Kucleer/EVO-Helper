# 军力榜盲滚改滚轮 —— 设计（2026-08-22）

盲滚段从「慢拖 70 屏、每屏等 2 秒」改成「滚轮单格连拨、末尾统一等一次滑行」。
口径从「屏」统一到「行」，新增运维旋钮 `blind_scroll_rows`。

## 〇、这份设计依据的实测（2026-08-22，本机实机）

`docs/军力榜翻页-滚轮实测.md` 的主结论「**滚轮一次调用最多走约 14 像素，替代不了
慢拖**」**被推翻**。那个 14px 是真的，但它量的是**单个大 delta 事件被封顶**，
不是滚轮的能力上限。

判据是事件形状，不是幅度：

| 发的 | 实际 `dwData` | 折合 | 列表推进 |
|---|---|---|---|
| 文档 `scroll(1)` | 1 | 1/120 格 | 1px（文档记成「1 格 = 1 像素」，其实是 1/120 格） |
| 文档 `scroll(800)` | 800 | 6.7 格 | 14px（**单个事件被封顶**，这条成立） |
| 助手 `scroll(-10)×40` | −10 | 1/12 格 | 约 9 行 |
| 助手 `scroll(-1)×80` | −1 | 1/120 格 | 0–3 行 |
| **用户手动（硬件）** | **−120** | **1 格** | **151 行** |

根因：`pyautogui.scroll(n)` 在 Windows 上把 `n` **原样**当 `dwData` 传给
`mouse_event`，**不乘 120**。用底层鼠标钩子（`WH_MOUSE_LL`）录到的证据：
助手发 `scroll(-1)` 钩子看到 `delta=-1`，用户硬件是 `delta=-120`。

按 `dwData=-120` 单格、16ms 间隔重发之后：

| 格数 | 推进 | 每格 | 拨完用时 | 滑行到停 |
|---|---|---|---|---|
| 40 | 44 行 | 1.10 行 | 0.7s | 1.6s |
| 80 | 85 行 | 1.06 行 | 1.3s | 2.3s |

三条性质都成立：**线性可预测**（1.10 vs 1.06）、**惯性有界**（1.6–2.3 秒停）、
**不缩放背后的画布**（面板外两条背景带逐像素零变化）。

对照基线（两次独立运行一致，且与生产日志吻合）：慢拖 `settle=2.0s` =
**7.3 行/拖、4.23 秒/拖、1.73 行/秒**；生产盲拖段实测 294.6 秒 / 70 屏。

## 一、目标与非目标

**目标**：盲滚段 294.6 秒 → 约 11 秒。按实测 30–41 轮/天，省约 2.6 小时/天鼠标时间。

**非目标**：
- **检测段与采集段一律不动，继续用慢拖。** 滚轮会把列表停在**非整行位置**
  （实测偏离标定网格约 12px），而 `vision` 那边是按 `ROW_FIRST_Y + k×ROW_PITCH`
  **逐行裁剪**的——偏了就横跨两行，名字全糊。实测过一次：画面清晰、
  `rows_from_image` 只读出 2 个名次。⚠️ 这是接线时最容易漏、漏了整段读不出的一条。
- 不改攻击链路、不改采集口径、不动任何与派遣有关的东西。

## 二、口径：一律用「行」

现状是「屏」，而屏只是慢拖的副产品（1 屏 ≈ 7.3 行）。滚轮没有「屏」这个概念，
而安全边界（bot 起点）天然是行。所以统一到行，屏退化为**显示单位**。

| 量 | 值 | 来源 |
|---|---|---|
| `ROWS_PER_NOTCH` | 1.08 行/格 | 本次实测（n=2），**标定常量** |
| `ROWS_PER_SCROLL` | 7.3 行/屏 | 本次实测，与生产日志吻合 |
| bot 起点 | 约 548–591 行 | 生产日志「实测 75–81 屏到达 bot 区」× 7.3 |
| 检测段单价 | 约 4.6 秒/屏 | 生产日志（总时长 − 盲拖段）÷ 检测屏数 |

⚠️ **余量不是免费的**：盲滚少走的距离由检测段接手，而检测段 4.6 秒/屏。
滚轮变快之后正确的取舍是**盲滚尽量走到安全上限**，把昂贵的检测段压到最短。

## 三、接线

改在**循环这一层**，不在 `scroll_blind()` 内部。现状是 `ranking_scan` 跑 70 次
`scroll_blind()`，每次末尾 `wait(SCROLL_SETTLE_WAIT_S)`；只换内部而保留每次等待的话，
70 × 2 秒原样还在，等于白改。

```
现在：  for _ in range(70): 慢拖一屏 + 等 2.0s              → 294.6s
改后：  连拨 N 格（16ms 一格、中间不等）+ 等一次滑行 2.5s    → 约 11s
```

| 层 | 改动 |
|---|---|
| `game/ranking_ui.py` | 新增 `WHEEL_DELTA=120`、`WHEEL_GAP_S=0.016`、`ROWS_PER_NOTCH=1.08`、`GLIDE_SETTLE_S=2.5`。**都是标定常量，不是运维旋钮** |
| `game/ranking_nav.py` | `RankingDriver` 加原语 `wheel_notch()`；新增 `spin_blind(rows) -> int`（返回实拨格数）。**格数与间隔的循环放在 game 层**，同 `_slow_drag` 分步的理由：放 `tools` 会让 `game` 反过来 import `tools` |
| `tools/scan_coordinates.py` | 驱动实现 `wheel_notch()`：`dwData=-120`。⚠️ 必须显式 `pyautogui.PAUSE = 0`，否则每格被撑成 117ms、攒不起动量 |
| `tools/ranking_scan.py` | 盲拖循环换成一次 `spin_blind(rows)`；行数记账；日志改口径 |
| `domain/ranking.py` | 自标定与余量判据从屏改行；日志正文解析跟着改 |
| `storage/models.py` + 迁移 | 新列 `blind_scroll_rows` |
| `web/` + `settings.html` | 旋钮 + 「≈N 秒」与「距 bot 起点还剩多少行」实时显示 |
| `application/mission_scheduler.py` | 取值、校验、变化时记日志 |
| `domain/missions.py` | `ranking_command` 换参数 |

## 四、配置

| 项 | 定法 |
|---|---|
| 列 | `military_attack_config.blind_scroll_rows`，**可空、无默认值** |
| 为什么可空 | 照 `blind_scrolls` 的先例：给了默认值就分不开「没配」和「配了 0」 |
| 代码默认值 | **700 行**（用户口径 2026-08-22；最终值由用户在页面上定） |
| 上界 | 硬拦在 bot 起点保守估计（548 行）之上仍允许，但**页面标红**并写明后果 |
| 0 | 合法（「一格都不拨」是最保守取值），负数不合法 |

⚠️ **默认 700 行已越过 bot 起点**（548–591 行）。后果是盲滚拨过 bot 区起点，
把榜首那批军力最高的 bot 整段跳过，**而且是静默的**——采回来的数只会少一截，
页面上看不出异常。用户已知悉并明确要求按 700 落地（「默认值我会最终配置」）。
设置页因此必须把「距 bot 起点还剩多少行」实时算出来并在越界时标红。

`blind_scrolls`（屏）**保留不动**，不删列、不删页面项，作为一键回滚：
`blind_scroll_rows` 置空即退回慢拖，无需改代码。

## 五、安全不变量

1. **只有盲滚段用滚轮**；检测段、采集段继续慢拖（见第一节非目标）。
2. **单个事件不许超过一格**。一次发大 delta 会被游戏封顶（实测 800 格只走 14px），
   而封顶是静默的——发出去了、没走到。
3. **`pyautogui.PAUSE` 必须显式置 0**，否则间隔被撑成 117ms、动量攒不起来，
   症状同样是「拨了但没走」。
4. **拨完必须等滑行停**（`GLIDE_SETTLE_S`），否则后面的检测段会在移动中的画面上读行。
5. 盲滚段**一次点击都不发**，`allow_actions` 全程为假。

## 六、日志（落 `system_log`，不落文件）

每轮盲滚记一条，`payload_json` 带：`rows_requested` / `notches_sent` /
`rows_measured` / `spin_seconds` / `glide_seconds` / `rows_per_notch_observed` /
`rows_to_bot_area` / `source`（手填还是默认）。

⚠️ **`rows_per_notch_observed` 是这条日志的要害**：`ROWS_PER_NOTCH=1.08` 只有 2 个
样本，而它一旦漂了，盲滚距离就静默地变了。把每轮的实测值记进库，才能在事后回答
「这个标定还成不成立」，而不是等到某天发现 bot 少采了一截再回头查。

## 七、测试

- **单元**：`spin_blind` 的格数换算（行 → 格，边界 0 / 1 / 越界）；`wheel_notch`
  发的 `dwData` 恒为 ±120；间隔不小于 `WHEEL_GAP_S`；`PAUSE` 被置 0。
- **单元**：自标定与余量判据改行之后的换算，含「屏样本 → 行」的兼容。
- **集成**：配置页存取一次往返，新旋钮进「所有旋钮一起存一起读」那张表。
- **迁移**：升级/降级各跑一次，存量行 `blind_scroll_rows` 为 NULL。
- **变异测试**：至少覆盖「换算符号反了」「越界不拦」「PAUSE 没置 0」
  「单事件发成大 delta」四处。

## 八、上线闸门

⚠️ **`ROWS_PER_NOTCH = 1.08` 只有 2 个样本、1 台机器、1 次会话。**
偏大就会拨过 bot 起点，而那是静默故障。

上生产之前必须：在实机上复测**至少 5 组**（格数覆盖 40/80/160/320/480），
确认线性仍成立且 `1.08` 落在样本区间内。复测不过就不上，先改标定值。

迁移 `blind_scroll_rows` 由生产自己在重启时升，本次**不对任何生产库执行
`alembic upgrade`**。
