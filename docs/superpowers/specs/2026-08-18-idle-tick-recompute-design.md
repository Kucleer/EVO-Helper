# 「没活干」的 tick 不该重算四遍

2026-08-18

## 缺陷

`MissionScheduler._launch()` 用同一个 `False` 表达了三件语义完全不同的事：

| 情形 | 含义 | 次序变了吗 |
|---|---|---|
| `row is None` | 决策与这一刻之间任务被删了 | 没变（这一轮作废） |
| `MissionIdle` | 这会儿没活干（军力池凑不出目标、航线预算刚好用完） | 没变（谁都没动） |
| `MissionParamError` | 刚把这条链路就地停用了 | **变了**（顺位该让给下一条） |

`_act()` 最后一行 `return not self._launch(...)` 把三件都翻成「值得再算一次」，
而 `tick()` 是 `for _ in range(len(MissionKind)): if not self._step(): return`。
于是**每一个「没活干」的 tick 都把 `_step` 转满 4 圈，每圈跑一次完整的 `_facts()`**。

`_act()` 自己的 docstring 写的是「作废一律返回『不必再算』……只有『刚把某条链路
就地停用』才值得重算」——**代码和它自己的合同对不上**。

## 代价（已实测，不用重量）

- 本地 SQLite（体量按生产摆到约两倍，`bot_targets` 10,725 行）：一次
  `_military_pool_reading` 4 条 SQL / 约 179 ms；一次 `_facts` 16 条 SQL / 约 194 ms。
  `_facts` 自己的注释记的生产实测是 0.32 秒。乘以 4 就是每个空转 tick 近一秒钟
  全花在重算全库候选池上。
- 生产 `system_log` 实测 2026-08-18 16:00 那一小时，「军力候选池」这条日志同一秒内
  最多重复 4 次——与这里的 4 圈正好对上（PR #188 把日志压住了，成因还在）。

## 这一次量到的关键事实：**那 4 圈一发都派不出去**

探针（`tests/integration/application/` 的真库夹具，军力 BOT 的候选全都强过
`max_score`，SCAN 开着）：

    _facts 调用次数 = 4
    起了谁 = []
    BOT disabled_reason = None

原因是结构性的：`MissionIdle` 不写库、不停用、不起进程，`decide()` 又是
`(tasks, facts)` 的纯函数。第二圈读的是同一份库、按同一个排序键挑出**同一个**
任务，于是原样再抛一次 `MissionIdle`。**后面那 3 圈不可能有别的结果。**

推论：把「没活干」改成「不必再算」，**派遣次序一个字都不会变**——今天让不让
下一条链路上位，答案本来就是「不让」。这不是行为变更，是把已有行为的浪费去掉。

## 修法

不加缓存。真正的失效条件（新军力读数写入、新派遣写入、配置变化、窗口边界随时间
移动）说不清，而缓存会让调度器拿着过期的候选池去派遣，比多花 CPU 糟得多。

让 `_launch` 返回一个显式的四态 `LaunchOutcome`，`_act` 只在 `DISABLED` 那一档
返回「值得再算」：

```python
class LaunchOutcome(Enum):
    STARTED = "started"    # 子进程起来了
    VOID = "void"          # 决策已作废（任务被删）
    IDLE = "idle"          # 这会儿没活干
    DISABLED = "disabled"  # 刚把这条链路就地停用了
```

四态而不是三态：`row is None` 和 `MissionIdle` 虽然对 `_act` 是同一个答案，但
「决策作废」和「正常间歇」在排障时是两回事，合并成一个成员就没人分得出来了。
`_act` 的判据写成 `outcome is LaunchOutcome.DISABLED`——**白名单，不是
`is not IDLE` 那种黑名单**：将来加第五个成员时，忘了改这一行的后果是少重算一次
（浪费一个 tick），而不是每秒空转四圈。

## 派遣次序的口径（写进注释、用用例钉住）

**`MissionIdle` 之后，本 tick 到此为止；下一条链路等下一个 tick（1 秒后）。**

- 依据是上面量到的那件事：本 tick 再转也只会挑中同一个任务、抛同一个
  `MissionIdle`。让位是假的，浪费是真的。
- 「顺位立刻让给下一条」这条规则只对**停用**成立，因为只有停用真的改了候选集
  （`disabled_reason` 落库 → `decide()` 的候选里少一个）。`test_a_bad_radius_yields_
  its_turn_in_the_same_tick` 钉的就是它，这次改动必须让它继续绿。
- 一个已知的相邻问题**不在这次范围内**：`has_work()` 是粗判据，军力优先那一支
  可以长期「看起来有活干、实际抛 `MissionIdle`」，而它排在填空隙的 SCAN / RANKING
  之前，于是能一直挡着刷新池子的那条链路。改它要动 `has_work` 的判据，是另一件事、
  另一个 PR。这次改动**不改变**这件事的成立与否（今天也是一样挡着）。

## 用例

1. 「没活干」的 tick 只跑一次 `_facts`（今天是 4 次）。
2. 「没活干」的 tick 一个子进程都不起、任务不被停用——**和今天一样**，这一条是
   防止修法顺手改掉次序的那道闸。
3. 「刚停用了谁」的 tick 仍然重算，下一条链路当场上位（已有用例，继续绿）。
4. 任务被删（`row is None`）的 tick 不重算，也不起任何进程。
5. `tick()` 转的圈数上界仍然由「停用」撑着：连着停用两条时两条都当场让位。
