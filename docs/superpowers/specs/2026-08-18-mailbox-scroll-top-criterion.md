# 拖回信箱顶部：判据被 OCR 噪声打穿，收尾那句话是假的

2026-08-18

## 缺陷有两层

### 第一层：停止判据挂在读不稳的那一格上

`tools/pirate_loop.py` 的 `_scroll_mail_list_to_top` 停止条件是「拖一下之后
行还是那几行」，比的是 `MailRow.identity` —— **主题 + 时间**。

主题那一格在实机上根本读不稳。邮件面板是半透明的，背后那一页的字
（`-TOTAL CREWS`、`-17003`、`personnel`）透上来落进同一块窄 ROI。生产日志上
同一封邮件连着两次读成：

```
'大 Sw GEF攻击报告 bad'    'EN SEFATing bad Za once'
'4d [全SGEF攻击报告 bas'   '一一 bad . Za ORs'
```

噪声大到同一屏连读两次都不相等，于是「拖不动了」**永远不成立**，
必然走满 `MAIL_SCROLL_TO_TOP_MAX_DRAGS = 40`。

### 第二层：走满上限时那句话说了它并不知道的事

```
INFO  tools.pirate_loop   往上拖满 40 次仍没到顶；这一趟看到的不是信箱最新的几封
```

用户当场核对：**实际进入邮箱就在顶部**，看到的正是最新的几封。
把「判不出来」说成一个事实，撞在 CLAUDE.md 的
「日志说假话比不说更糟」上（`_say_still_waiting` 那次教训）。

## 代价（生产数据，不用估）

| 事实 | 出处 |
|---|---|
| `往上拖满 40 次` 2026-08-18 一天出现 **17 次** | `system_log`，`message like '%往上拖满%'` |
| 一趟耗时 **230 秒**（20:30:07 进信箱 → 20:33:57 放弃） | `system_log` 相邻两条 |
| 单次「读一屏 + 慢拖」≈ **5.8 秒** | 230 ÷ 40 |
| 那一趟第 0 行是 `18/08/2026 11:12:00`，正是当时在等的最新一发的战报 | 20:33:59 的开封日志 |

也就是说：**每一趟都在已经到顶的位置上白拖 40 次、烧掉近四分钟。**

## 实拍量的判据前提

`var/logs` 下 **31 屏真信箱列表、186 行**，跑 `mail_rows()` + `mail_row_from_text`：

| 读什么 | 读得对的行数 |
|---|---|
| 时间（形如 `DD/MM/YYYY HH:MM:SS`） | **174 行（93.5%）** |
| 主题（一字不差） | **0 行（0.0%）** |

时间那一格是等宽数字，比中文主题稳一个量级。判据只能挂在它上面。

## 修法

1. **停止判据改比时间列**（`mail_times_settled`）：逐位比较，**严格多数**相同
   才算没动（6 行里 ≥4 行）。分母是**总行数**而不是「读出来的行数」——
   烂屏（只读出一两行）自动落在「照拖不误」那一侧。「整屏读空不算到顶」
   从旧实现原样留着。
   - 为什么阈值不在钢丝上：往上拖一次走 400px ≈ 4.6 行，一屏 6 行；
     真没到顶时两屏逐位重合的行数是 0，离「多数」很远。
2. **收尾如实描述**：拖了几次、最后一屏第 0 行是什么时候的、多少行读出时间、
   判据是什么；到没到顶——**说不知道**。走
   `infrastructure.system_log.record_system_log`（WARNING）落库，
   `payload_json` 带整屏时间列，下次再出这一句时能直接分出
   「列表真的深」和「时间也读不出来了」——原先这两种混在一句话里。
3. **开工那句补上期望时刻**：「库里有 N 发到点还没战报」后面加
   「最晚一发的期望战报时刻 …… UTC」，与紧接着的
   「第 0 行是什么时候的邮件」并排可查。这是用户口径
   「应首先验证邮件时间与待读战报」在日志上的落点。
   有发没读到飞行时间时**照实说说不出上界**，不拿其余几发的最大值冒充。

## 没做的那一层：「已在顶部就一次都不拖」

用户提的是「重新登录 / 启动任务默认都在顶部」。这条**没做**，理由是找不到
可靠的正面证据，而判错方向的代价极不对称：误判「已在顶部」而其实不在
= 漏战报（2026-08-13「17 发攻击 0 份战报」正是这个形态，两天排障），
误判「不在顶部」= 多花几秒。

「刚登录过」是**没有反证**，不是证据。库里拿得到的两个正面证据候选，
都被生产数据否掉了：

### 候选一：第 0 行时间 ≥ 库里已知的最新战报时间

2026-08-13 那一夜库里当天**一份战报都没有**。这个判据会空真、跳过拖动——
正好**制造**那次事故。它根本不是「顶部」的证据，只是「库里空不空」的证据。

### 候选二：第 0 行时间 ≥ 在等的那几发的期望时刻

`expected_report_at_utc` = 「点完『出发』记下的时刻」+「OCR 读到的飞行时间」，
与战报真正的时刻对不齐。生产库 112 份已认领战报实测：

| 样本 | 实际 − 期望 |
|---|---|
| 全部 112 份 | −4 s … **+1498 s**（中位 +16 s） |
| 2026-08-14 起 33 份 | −4 s … **+219 s**（中位 −1 s，p90 +50 s） |

要让判据成立，得留 ≥ 219 秒余量（而 219 只是**观测到的**最大值，不是上界）。
偏偏 2026-08-18 20:33 那一趟：

- 第 0 行 = `11:12:00 UTC`
- 在等的 5 发里最晚的期望 = `11:12:02.761 UTC`

**第 0 行比它早 2.8 秒。** 留够余量 → 判据不触发，一点不省；不留余量 →
等于拿「漏一份战报」去赌飞行时间读得准，而那正是漏战报的方向。

### 结论

省下来的是**一次**读屏加一次拖动（≈6 秒），赌注是一份战报。不做。

判据修好之后，本来就在顶部的那种情形只付「两屏一拖」——从近四分钟降到
**约 12 秒**，用户报的那个症状已经没了，而漏战报那一侧一点没让。
